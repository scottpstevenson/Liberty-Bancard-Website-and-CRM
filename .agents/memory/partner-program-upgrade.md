---
name: Partner program upgrade decisions
description: Commercial-approval gating and application/credential/consent rules for the two-path partner program (referral partner / sales agent).
---

- Referral percentage is never static content or in the client bundle. It reaches pages only through the server projection of an admin-approved policy version; absent approval the default is "confirmed in your written agreement". Referral 25% / strategic 30% stayed proposals until the owner records approval. Agent 50% is worded only for qualifying self-sourced full-cycle business.
- An application is a reviewed request: no credential, session, agent role or commission (explicit null, not the legacy column default). Acceptance is not marketing consent.
- Credential eligibility is application-aware and shared: an application that is not accepted can never obtain a login, password reset or invitation; legacy credentialed partners keep login/reset. Any route that issues, consumes or honors a partner credential must use that shared check.
- A partner-session route is unreachable unless the central partner allowlist in the main route registration also names it; a route-level auth check alone does not make it reachable. Prove new partner routes with a real partner session, not only role-denial cases.
- In-site partner links must go through the shared attribution helper; plain `<Link>`/`href` to a partner route silently drops ref/UTM. Prove attribution by real clicks in a browser, not by reading link props.
- Partner funnel analytics are inert when the build carries no measurement id (the id is inlined at build time, so it cannot be injected at runtime in tests). Report consent-granted events as not exercised rather than passed.
- All six `/partners*` pages and `/affiliate` are server-rendered (`server/routes/partner-pages.ts`, `server/ssr/partners.ts`), `no-cache`, and the renderer must not import db/storage/policy services (policy arrives as a projection). One title/h1 record is read by the document and the React page. The public perf harness is valid on an isolated preview of the compiled build; do not count a missing LCP as zero.
- Attribution: the current touch's whole allowlisted set wins; otherwise the session's first touch (`lb_partner_first_touch`, first write wins); never merge keys. Browser proof must include a full page load with no query string.
- Review work: history is append-only and written in the decision transaction; reopen is in place and refused for accepted/credentialed/terms-holding cases; "needs information" is status only (no message). Introduction decisions never create commission, move attribution or merge companies. Identity evidence needs a website/email domain; a shared phone alone is not evidence.
- Hero images are generated W-D scenes (owner approval pending); three professions use an `approximate` scene with the gap named in `shared/partner-page-media.ts`. Report that, never call them photographs of the profession.
- Production `/partner-login` has pre-existing a11y/tap-target findings unrelated to this program.
- Partner section headings (`H2.public-h2` inside `.marketing-theme .partner-page`) are a deliberate display-serif moment; the font check allows exactly that and nothing wider. Card-title h2s stay sans.
- `test-partner-ssr-pages` and `test-partner-page-media` are mandatory in pre-deploy and the CI manifest; the certification-fixture suites (lifecycle, review-workflows, approval-delivery, resume, crash-boundaries, program-migration) run only by name. `partner_introductions.contact_id` is `manual_block` in the contact-merge manifest (append-only evidence), and migration 0385's checkpoint backfill is a registered historical one-time seed.
- Never statically import the partner client module (zod application schema) from `App.tsx`: it added ~82 KB to the main bundle and slowed the C1 useful-list timing assertion. It is loaded on demand only on `/partners*` and `/affiliate`.
- Failing roster suites: export clean HEAD to /tmp, build it, rerun each failure alone through the disposable runner, and compare messages. About 46 of 56 failed identically on clean HEAD (CRO-03, SFP, stage3 and similar), so they are not caused by partner work. The `/learn` static pages' shell-design findings and the C1 useful-list timing also fail on clean HEAD.
- Starting the isolated preview adds a `.replit` port block, and `.replit` is part of the build identity, so remove that block before the next `--reuse-build` start or it refuses with "rebuild required".

**Why:** the owner's brief treats unapproved percentages and any pre-approval access as release blockers, and partner sessions are walled off from the CRM by that central allowlist.
**How to apply:** touching partner copy, calculator, intake, approval, login/reset or any new partner-session route.
