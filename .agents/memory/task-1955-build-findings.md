One "confirmed" audit claim turned out to be stale, and one BUILD-time verification claim turned out to be wrong for a different reason — both reinforce "verify, don't trust," but the second one is the more important lesson:

- **CORRECTED — do not trust this claim, it was wrong:** an earlier version of this note claimed the drifted CHECK constraints (`businesses.record_class` missing `'canonical'`, `cro03_source_subjects.subject_type` missing `'business'`) were "already repaired by existing migrations (0240, 0250)" based on a live `psql` check. That check connected to the **development** database (`heliumdb`) and was mislabeled as production. The true production database (`neondb`, reachable only via the platform's production-environment query path, not the shell's default `DATABASE_URL`/`psql`) does **not** have either value — migrations 0240/0250 exist in the repo and dev has received them, but production has not been Published since before they were added. The original audit's drift claim was correct. See [migration 0266](../../migrations/0266_repair_record_class_subject_type_constraints.sql) for the repair. **Lesson: a shell/`psql` check of "live" state on this project defaults to the dev database; verifying an actual production claim requires the production-scoped query path, never ad-hoc `psql`/`DATABASE_URL`.**
- **A claimed "N consecutive failures" can be stale.** sla-worker's audit-cited 184 consecutive failures did not match live `background_jobs.consecutive_failures` (was 0), and its query (`getSlaConfigs()`) ran cleanly in isolation against live data. The job simply wasn't ticking (excluded from the active `BACKGROUND_JOB_PROFILE=selective:*` group) — a stale/inactive worker is not evidence of an active code defect. Check `background_jobs` (consecutive_failures, last run time) and reproduce the exact call in isolation before trusting a failure-count claim or writing a fix for it.

`scripts/check-bounded-schema-drift.ts` (a bounded Drizzle-vs-live-DB column diff for a specific short table list) found real, unrelated drift on `contacts` and `businesses` columns. This was fixed: see [contacts/businesses NOT NULL convergence](contacts-notnull-convergence.md).
