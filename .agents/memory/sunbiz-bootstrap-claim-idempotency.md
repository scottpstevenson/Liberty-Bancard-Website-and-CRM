---
name: Sunbiz bootstrap claim-based idempotency
description: Durable lessons on claim-row idempotency, lease-fencing, and preview/confirm token binding for bounded admin-run batches over huge tables.
---

Idempotent bounded-batch materialization (e.g. building canonical business rows from an external registry corpus) is best anchored on a durable claim row keyed on the natural external identifier, inserted with an idempotent insert (ON CONFLICT DO NOTHING) BEFORE any expensive resolution/matching work. A retried or resumed batch that re-selects the same source record gets zero rows back from the claim insert and skips, independent of whether downstream dedup logic would have caught the duplicate on its own.

**A foreign key on a lineage/link table scoped to "registries with an adapter row" will reject a source that has no adapter.** When adding a new source to a system originally built for a narrower set of registries, check whether link/provenance tables assume every source has a corresponding adapter row; if not, the FK-target column must be nullable and left NULL for sources without one.

**Candidate-selection queries ordered by an ever-increasing key (e.g. `ORDER BY id LIMIT n`) never reach freshly-inserted rows once the table has a huge existing corpus** — new rows sort last and are invisible at any small LIMIT. Bounded-batch selectors over huge tables need either an optional narrowing filter for targeted testing, or a partial index matching the selection predicate (otherwise the anti-join against the huge table times out). A narrowing filter should be a range-bound clause (`col >= lower AND col < upper`), not a LIKE/prefix filter — LIKE forces a full scan when the match is late-inserted rows in an id-ordered walk, because the planner can't short-circuit; a range clause lets it seek a plain btree index instead.

**Claim-based idempotency needs a lease-fencing token, not just a status/timestamp check.** A staleness window (letting a `'claimed'` row age into reclaimable) is necessary but not sufficient: every later write (success, deferred, failure) must also be conditioned on the exact lease value (e.g. a `claimed_at` timestamp) granted at claim time, via compare-and-swap (`WHERE key = ... AND lease_token = <token>`). Without that fence, a stale claimant that resumes after being reclaimed by someone else can overwrite the new claimant's terminal result — status/timestamp staleness alone only decides who *may* reclaim, not who's allowed to *finalize*.

**Why:** a claim/lease system that lets any holder of the row key write to it — rather than only the holder of the currently-valid lease — degrades to no real mutual exclusion at all once a claimant can outlive its own lease.

**Idempotent side-effect inserts (e.g. provenance/lineage rows) must run on every finalize branch of a resolve-or-match flow, not just the "newly created" branch.** If the side effect and the primary write aren't atomic, a crash between them means a later retry resolves via the "already exists" branch and silently skips code gated on the "created" branch alone — run such idempotent inserts unconditionally across all successful finalize paths.

**A preview/confirm endpoint pair must bind confirmation to a snapshot from the preview call itself (a short-lived, single-use token), not to a value each endpoint independently recomputes.** Recomputing the same "confirm this count/phrase" value at execute time reopens the exact race the confirmation step exists to prevent: state can change between preview and execute, silently invalidating a phrase the caller was just shown. The token must also be validated (peeked) before it is consumed/deleted — deleting on first validation attempt means a caller-side input mistake (e.g. a typo in the confirmation phrase) burns the token and forces a fresh, possibly-different snapshot just to correct the typo.

**Why:** treating "attempted to use the token" and "successfully used the token" as the same event punishes input mistakes by discarding otherwise-valid state, and any UI wired to auto-refresh on failure will silently replace a still-good token — the refresh trigger itself must distinguish "this token is dead" from "this input was wrong."

**Binding execution to a previewed snapshot must be all-or-none inside one transaction, not "select fresh, compare to the snapshot, then claim members one at a time."** A select-then-compare-then-claim sequence still leaves a window between the comparison and each individual claim: two callers who were both shown the same snapshot can each pass the comparison before either claims anything, then split the claimed rows between them, so each executes a partial subset that was never independently reviewed as such. The comparison and every claim it depends on must happen inside a single transaction that re-verifies live eligibility per member as part of the claiming statement itself, and rolls back entirely — zero durable writes — if any single member can't be acquired.

**Why:** a snapshot-binding check that passes before claiming, rather than as an atomic part of claiming, only proves the snapshot was valid at comparison time — not that it stayed valid through execution. Verify the exact race with two real concurrent callers against the same expected set, not just a single sequential "claim it out from under you first, then run" scenario.
