---
name: Immutable-trigger tables silently break backfill migrations only where rows exist
description: Row-level immutability triggers (RAISE EXCEPTION on UPDATE/DELETE) only fire when a DML statement actually touches a row, so a backfill UPDATE in a migration can pass cleanly on dev/disposable DBs with zero matching rows and fail 100% of the time in production where matching rows exist.
---

A table protected by a `BEFORE UPDATE OR DELETE ... RAISE EXCEPTION` trigger (the SFP evidence-immutability pattern from migration 0288, applied to `sfp_classification_evidence` and `sfp_paid_candidate_evidence`) makes any later backfill `UPDATE` against it a landmine: Postgres triggers are per-row, so an `UPDATE` that matches zero rows never fires the trigger and succeeds silently, while the identical statement against a database that actually has matching rows fails every time.

**Why:** Migration 0301 added a backfill `UPDATE ... WHERE taxonomy_version = 1 AND classifier_version <> 1` on `sfp_classification_evidence`. It ran clean in dev and in a from-scratch disposable-DB reproduction (0 matching rows in both), giving false confidence the migration was sound, while production (98 matching rows) failed the deploy's `db:migrate` step on every retry with only a generic "Failed query" message (see `drizzle-migration-error-swallowed-cause.md` for why the real Postgres error was invisible). The eventual proof came from directly counting rows matching the backfill predicate in production via read-only `executeSql`, then confirming the immutability trigger existed on that exact table.

**How to apply:** Before writing any migration that mutates (UPDATE/DELETE) a table, grep for `BEFORE UPDATE OR DELETE` / `RAISE EXCEPTION` triggers on it. If one exists and the mutation is a legitimate one-time schema-migration backfill, wrap it: `ALTER TABLE t DISABLE TRIGGER <name>; UPDATE ...; ALTER TABLE t ENABLE TRIGGER <name>;` in the same migration file. Never trust a migration's success on dev/disposable-DB alone when the affected table is row-count-sensitive (immutability triggers, partial unique indexes, check constraints keyed on existing data) — check production's actual row counts against the migration's WHERE predicate first via read-only `executeSql`.
