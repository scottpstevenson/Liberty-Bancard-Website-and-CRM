- **Installed schema, release and rollback — fixture proven; production schema objects present, ledger lagging.** Migrations `0380` and `0381` apply cleanly on the disposable database and `check-migration-integrity` passes (journal text-appended, `0380` not edited after it was applied). Read-only evidence on 2026-11-05 (aggregate catalog/count queries only, no writes): the production database already has all five `0381` columns on `underwriting_condition_chases` and the index `idx_uw_condition_chases_owed_next`; `underwriting_condition_chases` has 0 rows, so the `0381` backfill UPDATE has nothing to act on; `underwriting_conditions.created_by/updated_by` are `varchar` (the `0380` result) with 0 conditions. The production Drizzle ledger (318 rows, newest `created_at` 1800000013301) has **no** entry for `0380`/`0381` (development: 429 rows, three at or after `0380`). So the objects exist while the ledger does not record those two migrations; this reflects the Publish schema diff, not a ledger-applied migration, and the ledger discrepancy is reported, not repaired here. Rollback: `0381` is additive and old code ignores the new columns, so reverting the application does not require reverting the schema. `0380` is not reversible by an application rollback: its `ALTER … USING NULL` discards any populated `created_by`/`updated_by` values (the migration's stated intent is that the only non-null values ever written were contact ids, not actors) and reverting code cannot restore them. **Risk and verified facts are separate:** the present objects, empty tables (0 conditions, 0 chases) and missing ledger entries do NOT prove the destructive statement ran against production actor data (the Publish schema diff may have produced the same column type; with 0 rows nothing could have been discarded). No ledger stamp, replay or startup DDL was performed. Real actor evidence for later commands is in `audit_logs` and the string actor columns.
