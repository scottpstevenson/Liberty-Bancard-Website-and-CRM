Act as a senior full-stack engineer, QA lead, product manager, UX strategist, UI reviewer, security reviewer, and deployment auditor.

Your job is to perform a COMPLETE pre-deployment audit of this entire application and determine whether it is truly ready for production.

You are reviewing this like a real launch sign-off for a production SaaS app.

Your goals are to confirm that the app is:

1. Fully functional with no broken core features
2. Properly wired end-to-end across frontend, backend, database, auth, and integrations
3. Logically aligned with its intended product and workflow
4. Visually polished and consistent
5. Intuitive and usable for real users
6. Safe, reliable, and secure enough for production
7. Configured correctly for deployment
8. Resilient enough for real-world usage after launch

DO NOT give a shallow or generic answer.
Be highly specific.
Reference exact files, components, pages, hooks, routes, services, jobs, functions, database interactions, and workflows wherever possible.

--------------------------------------------------
SECTION 1: PRODUCT PURPOSE + WORKFLOW ALIGNMENT
--------------------------------------------------

1. Infer the intended purpose of the application from the codebase
2. Identify all major user types, roles, and states
3. Map all core workflows from start to finish
   - onboarding
   - authentication
   - dashboard usage
   - key object creation/edit/update/delete
   - approvals
   - notifications
   - messaging
   - admin actions
   - reporting
   - any other important flows in the codebase
4. Confirm whether each workflow is:
   - complete
   - logically sequenced
   - realistic for a production user
   - aligned with the intended product behavior
5. Find:
   - broken workflows
   - missing steps
   - dead ends
   - redundant flows
   - disconnected frontend/backend handoffs
   - screens that suggest functionality not actually supported
   - flows that work only in demo conditions but not real usage

--------------------------------------------------
SECTION 2: FEATURE INVENTORY + END-TO-END FUNCTIONALITY
--------------------------------------------------

1. Identify every major feature visible in the app
2. For each feature, trace:
   - frontend entry point
   - state handling
   - API call or server action
   - backend route/service
   - database persistence
   - returned UI state
3. Confirm whether each feature is:
   - fully working
   - partially implemented
   - broken
   - UI-only
   - backend-only
   - inconsistent across pages
4. Verify real create/read/update/delete behavior where applicable
5. Confirm users get the result they expect after each action
6. Find silent failures where an action appears to succeed but does not actually persist or complete

--------------------------------------------------
SECTION 3: FRONTEND ↔ BACKEND ↔ DATABASE ALIGNMENT
--------------------------------------------------

Audit full-stack alignment in detail.

Check for:
1. Frontend API calls that do not match backend routes
2. Mismatched request payloads
3. Inconsistent response formats
4. Backend routes with no frontend consumer
5. Frontend assumptions the backend does not support
6. Database writes that do not update UI correctly
7. Missing cache invalidation or stale client state
8. Race conditions
9. Duplicate submissions
10. Improper optimistic updates
11. Records not refreshed after mutation
12. Broken object linking or foreign key issues
13. Data shown in the UI that does not reflect actual persisted state

--------------------------------------------------
SECTION 4: FORMS, CRUD, DATA INTEGRITY
--------------------------------------------------

Audit all forms and data operations for production safety.

Check:
1. Required vs optional field handling
2. Validation correctness
3. Form submission behavior
4. Disabled/loading states
5. Duplicate submission prevention
6. Error handling on submit
7. Create/update/delete persistence
8. Partial-save risks
9. Data duplication risks
10. Record merge/linking risks
11. Broken delete behavior
12. Inconsistent edit vs create behavior
13. Any risk of silent data corruption, orphaned records, or misleading success messages

--------------------------------------------------
SECTION 5: AUTH, PERMISSIONS, USER STATES
--------------------------------------------------

Audit authentication and authorization across the stack.

Check:
1. Signup
2. Login
3. Logout
4. Session persistence
5. Password/token handling
6. Route protection
7. API protection
8. Admin vs non-admin permissions
9. Role-based UI visibility vs backend enforcement
10. Unauthorized access risks
11. Deactivated/inactive user behavior
12. Partially onboarded user behavior
13. Broken auth edge cases
14. Missing checks that could expose restricted data or actions

--------------------------------------------------
SECTION 6: ERROR HANDLING + SILENT FAILURES
--------------------------------------------------

Find every place where the system can fail unclearly.

Audit:
1. Missing try/catch in important routes
2. Inconsistent API error responses
3. Empty catch blocks
4. Swallowed exceptions
5. Background jobs with weak logging
6. Webhooks with silent failure
7. Third-party integrations with hidden failure
8. Email sending failures
9. AI or external API failures
10. Success messages that return even when the action actually failed
11. Frontend mutations that fail without clear feedback
12. Fallback logic that hides real production failure
13. Partial failure paths that leave inconsistent state

Confirm whether both operators and end users would clearly understand when something failed.

--------------------------------------------------
SECTION 7: CODE QUALITY + LAUNCH SAFETY
--------------------------------------------------

Review the codebase for production risk.

Look for:
1. Hardcoded secrets
2. Unsafe fallback credentials
3. Dead code
4. Duplicate logic
5. Fragile conditionals
6. Unsafe env var assumptions
7. Poorly named logic that increases break risk
8. Large files with mixed responsibilities
9. Brittle code that technically works but is risky to deploy
10. Areas where one change could easily cause regression
11. Unused routes/components/services that may confuse future maintenance
12. Dev-only code paths leaking into production behavior

Do not over-focus on style alone.
Prioritize real launch risk.

--------------------------------------------------
SECTION 8: UI CONSISTENCY + VISUAL READINESS
--------------------------------------------------

Review the UI as a launch-ready product.

Audit:
1. Layout consistency
2. Spacing consistency
3. Typography consistency
4. Form consistency
5. Table/list/detail consistency
6. Button style and action hierarchy
7. Modal/drawer consistency
8. Empty states
9. Loading states
10. Error states
11. Disabled states
12. Scanability
13. Information hierarchy
14. Mobile responsiveness
15. Accessibility basics
16. Overall polish and trustworthiness

Identify any page, component, or pattern that feels unfinished, inconsistent, or visually weak.

--------------------------------------------------
SECTION 9: UX + USABILITY
--------------------------------------------------

Review this app from the perspective of:
- a first-time user
- a repeat user
- an admin/operator

Evaluate:
1. Clarity of purpose
2. Ease of navigation
3. Learnability
4. Task efficiency
5. Clarity of labels and calls to action
6. Number of clicks required for key tasks
7. Friction in forms and workflows
8. Visibility of next steps
9. Feedback after actions
10. Confidence/trust when using the app
11. Recovery from errors
12. Presence of dead ends or confusing transitions
13. Whether users always understand:
   - where they are
   - what just happened
   - what they should do next

Flag anything that makes users stop and think unnecessarily.

--------------------------------------------------
SECTION 10: EDGE CASES + REGRESSION RISK
--------------------------------------------------

Audit for unusual but realistic failure cases.

Check:
1. Empty datasets
2. Null/undefined values
3. Partial records
4. Expired sessions
5. Slow/failing network requests
6. Duplicate clicks
7. Double submits
8. Missing related records
9. Deleting linked objects
10. Permissions edge cases
11. Missing env vars
12. Third-party outage scenarios
13. Retry behavior
14. Stale state after rapid updates
15. Cases where changes in one area may break another

Identify high-regression-risk areas before deployment.

--------------------------------------------------
SECTION 11: SECURITY, RELIABILITY, PERFORMANCE
--------------------------------------------------

Audit for production safety.

Check:
1. Authentication safety
2. Authorization enforcement
3. Secret handling
4. CSRF/session safety if relevant
5. Unsafe exposed admin behaviors
6. Rate limiting
7. In-memory-only protection that won't survive restart
8. Webhook verification
9. Background job safety
10. Heavy queries
11. Missing pagination
12. Re-fetch storms
13. Unnecessary rerenders
14. Large payloads
15. N+1 query risks
16. Timeout/retry handling
17. App behavior under real-world traffic/load
18. Any likely production instability

--------------------------------------------------
SECTION 12: DEPLOYMENT + ENVIRONMENT READINESS
--------------------------------------------------

Review the app for actual deployment safety.

Check:
1. Required environment variables
2. Missing or inconsistent env var usage
3. Unsafe fallback values
4. Dev-only URLs or mocks in production paths
5. Build/start assumptions
6. Database migration safety
7. Seed logic safety
8. External integration requirements
9. Logging/observability readiness
10. Anything that could allow deploy to succeed technically while the app still fails operationally

Also create a manual deployment checklist:
- required env vars
- third-party integrations
- database setup
- seed/setup caveats
- anything needing manual configuration

--------------------------------------------------
SECTION 13: FINAL DEPLOYMENT DECISION
--------------------------------------------------

After reviewing everything above, give a strict and decisive launch recommendation.

OUTPUT FORMAT:

## 1. Product Summary
- What this app appears to do
- Who it serves
- What the core workflows are

## 2. Core Workflows Identified
List all major workflows discovered.

## 3. Feature Inventory
List all major features discovered.

## 4. 🔴 Critical Deployment Blockers
Anything that can:
- break core functionality
- corrupt or misrepresent data
- expose data or permissions incorrectly
- create major silent failure risk
- make production deployment unsafe

For each blocker include:
- issue
- why it matters
- exact files/routes/components/functions involved
- exact fix recommendation

## 5. 🟡 Important Fixes
Problems that may not completely block deployment but will likely cause:
- broken edge cases
- poor UX
- stale data
- confusion
- reliability issues
- operational pain

For each include:
- issue
- why it matters
- exact files/routes/components/functions involved
- exact fix recommendation

## 6. 🟢 Minor Improvements
Smaller polish, maintainability, and UX improvements that are not launch blockers.

## 7. 🔧 Exact File-Level Fixes
Give a clean table or structured list with:
- file path
- function/component/route
- exact problem
- exact change needed

## 8. Verified Strong Areas
Call out the parts of the app that appear robust and production-quality.

## 9. Manual Deployment Checklist
List:
- required env vars
- required third-party services
- integrations to verify
- database or migration steps
- operational checks before launch

## 10. Launch Risk Level
Choose one:
- Low
- Medium
- High

## 11. Final Recommendation
Choose exactly one:
- Ready for deployment
- Ready after small fixes
- Not ready for deployment

## 12. Reasoning
Give a direct explanation of why.

IMPORTANT REVIEW RULES:
- Be specific, not generic
- Do not praise the app unless the code supports it
- Do not assume a feature works just because UI exists
- Confirm real wiring across frontend, backend, and persistence
- Treat silent failures as serious
- Treat stale data and misleading success states as real problems
- Think like the person responsible for approving production launch

At the end, include a final section:

## 13. Post-Audit Fix Plan
Prioritize the top fixes in the exact order they should be addressed before launch:
1. highest-risk fixes first
2. then important alignment fixes
3. then polish items
