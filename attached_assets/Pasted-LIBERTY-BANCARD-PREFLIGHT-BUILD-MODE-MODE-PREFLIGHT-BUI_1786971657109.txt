LIBERTY BANCARD — PREFLIGHT + BUILD MODE


MODE
PREFLIGHT + BUILD
First verify the task against the current codebase.
Then, if the task is materially valid and safe after corrections, continue directly into implementation in the same run.
Do not stop after producing another plan unless a real blocker exists.
Do not:
* blindly trust the task description;
* assume old file paths or line numbers are current;
* redesign architecture unnecessarily;
* create competing source-of-truth systems;
* perform speculative refactors;
* clean up unrelated code;
* expand scope without identifying why;
* use db push;
* weaken tests to make the task pass.
Stop before implementation only if:
* the finding is false;
* the proposed fix targets the wrong owner;
* a required prerequisite is missing;
* the task requires a materially different architecture;
* safe implementation depends on unavailable runtime evidence;
* scope must be split;
* a kill line is reached.
Otherwise:
Verify → correct the plan → build → test → verify.

1. REPOSITORY BASELINE
Before making claims, capture:
* current branch;
* current HEAD SHA;
* working-tree status;
* current migration head if schema is relevant.
If unrelated modifications already exist, identify them and do not overwrite them.

Create a concise Verified From Code (VFC) table before implementation.
Use:
ID	Task Claim	Verdict	Verified Reality	Evidence
VFC-01	...	CONFIRMED / PARTIAL / FALSE / OUTDATED	...	file:line
VFC-02	...	...	...	...
Verify at minimum:
Root cause
Does the bug/gap actually exist as described?
Code ownership
Confirm:
* route;
* service;
* function;
* canonical writer;
* queue/worker;
* schema/table;
* frontend owner;
where relevant.
Callers
Find every relevant caller of the code being changed.
Writers
Find all other code paths that can mutate the same important state.
Consumers
Find anything that relies on:
* changed statuses;
* changed response shapes;
* changed columns;
* changed behavior.
Existing protections
Check whether the code already has:
* deduplication;
* idempotency;
* transactions;
* locking;
* validation;
* role gates;
* retries;
* audit logging;
* suppression/contactability gates.
Do not duplicate protections that already exist.

4. VERIFIED ROOT CAUSE
After inspecting the code, state:
Original task assumption
What the task claimed was happening.
Verified root cause
What current code actually does.
False or outdated assumptions
Use a short table:
Original Assumption	Verified Reality	Correction
...	...	...
If there are no material corrections, say so.

5. SOURCE-OF-TRUTH CHECK
Before implementing, identify the canonical owner.
State:
* Canonical data owner
* Canonical mutation owner
* Canonical queue/job owner
* Canonical external integration owner
* Canonical audit/log owner
Only include categories relevant to the task.
Do not create a second competing implementation if one already exists.
Examples:
* contact creation should use the canonical contact writer;
* promotional enrollment should use the durable enrollment service;
* GHL synchronization should use the canonical GHL owner;
* lead scoring should use the canonical scoring path;
* readiness should use the canonical readiness engine.

6. BLAST RADIUS
Identify what can actually be affected.
In scope
List exact behaviors/files.
Out of scope
List behavior that must remain untouched.
Files expected to change
path — reason
Files explicitly not expected to change
path — reason
This is not permission to change every file listed during preflight.
Keep the final diff minimal.

7. DATA / SCHEMA CHECK
If persistent data is involved, verify:
* exact table;
* exact columns;
* types;
* nullability;
* defaults;
* constraints;
* unique indexes;
* foreign keys;
* status values;
* archive behavior;
* all important readers/writers.
If a migration is required:
* verify migration high-water mark;
* create the next valid migration;
* update the proper Drizzle migration metadata/journal;
* do not use db push;
* do not backfill historical records unless explicitly required.
If no migration is needed, say:
Migration required: NO

8. AUTHORIZATION CHECK
If the task involves an operator/API action, verify actual permissions.
Do not assume:
* isAuthenticated
* isDashboardUser
* requireRole(...)
mean what the task claims.
State who may perform the action:
Action	Public	Agent	Manager	Admin
relevant action	...	...	...	...
Admin overrides must be explicitly role-gated where required.

9. CONCURRENCY / IDEMPOTENCY CHECK
Required for tasks involving:
* contact creation;
* prospect conversion;
* imports;
* enrollment;
* sending;
* deduplication;
* merchant matching;
* jobs;
* recovery;
* bulk operations.
Check:
* Can two requests run simultaneously?
* Is there a DB unique constraint?
* Is there an atomic claim?
* Is there a stable idempotency key?
* What happens on retry?
* What happens after partial success?
* Can a crash leave a permanent stuck state?
* Can a retry duplicate external side effects?
Do not rely on:
SELECT
if missing
INSERT
alone when concurrency matters.

10. EXTERNAL SIDE-EFFECT CHECK
If GHL, SendGrid, SMS, enrichment, Redis/BullMQ, payment systems, or another external provider is involved, document ordering.
For example:
DB lookup
→ external call
→ DB update
→ enqueue
→ audit
Then verify:
* external succeeds / DB fails;
* DB succeeds / external fails;
* retry;
* replay;
* duplicate execution.
Do not claim external operations are atomic with PostgreSQL.

11. PREFLIGHT VERDICT
Give one verdict:
BUILD-READY
Task is correct as written.
BUILD-READY WITH CORRECTIONS
Task is valid, but the implementation plan needs corrections.
PREFLIGHT REQUIRED
More investigation is genuinely required before coding.
NOT BUILD-READY
A prerequisite or architecture issue blocks implementation.
NOT NEW TASK
Already solved by existing implementation.
WATCH
No immediate build required.
If verdict is BUILD-READY or BUILD-READY WITH CORRECTIONS, continue directly into the build.
Do not ask for another approval.

Do not include speculative future architecture.

13. KILL LINES
Define task-specific failure conditions.
At minimum include the central behavioral kill line.
Examples:
KILL LINE: If [unsafe behavior] is still possible after this task, the task has FAILED regardless of all other work.
Additional examples where applicable:
* STOP if the canonical writer is bypassed.
* STOP if duplicate sends remain possible.
* STOP if blocked contacts can still enroll.
* STOP if an opted-out channel can be silently re-enabled.
* STOP if concurrent execution can create duplicate records.
* STOP if new statuses break existing consumers.
* STOP if an external write occurs before the required local authority check.
* STOP if a rejected operation still causes downstream side effects.
* STOP if a migration modifies unrelated historical data.
* STOP if a durable queue is replaced by in-memory/fire-and-forget work.
* STOP if only a helper test passes while the production path remains untested.
Only include kill lines relevant to the task.

14. IMPLEMENTATION RULES
Once preflight passes:
* make the smallest safe diff;
* use existing patterns;
* preserve canonical ownership;
* no architecture redesign;
* no unrelated cleanup;
* no broad renames;
* no unrelated formatting;
* no dependency changes unless required;
* do not change behavior outside scope.
If implementation uncovers a materially different root cause, pause coding long enough to update the corrected plan and then continue only if still safe.

15. TEST REQUIREMENTS
Tests must prove the actual behavior, not merely helper internals.
Include applicable categories:
Happy path
Valid operation works.
Negative path
Unsafe/invalid operation is rejected.
Boundary
Threshold/null/status boundary behaves correctly.
Replay
Repeated request/job is safe.
Concurrency
Two simultaneous attempts do not duplicate effects.
Authorization
Allowed role succeeds; denied role fails.
Partial failure
Where DB + external systems or multiple durable steps are involved.
Regression
Existing expected behavior remains intact.
Do not create meaningless assertion-count tests.
Tests should map directly to Done Looks Like and kill lines.

16. SMOKE / INTEGRATION TEST
Where appropriate, create or update a focused script:
scripts/test-[task-name].ts
The smoke test should validate the production path as realistically as the repo allows.
Typical assertions:
1. prior unsafe behavior is now blocked;
2. correct behavior succeeds;
3. rejected path causes no forbidden mutation;
4. persisted state is correct;
5. audit/log state is correct;
6. replay is idempotent;
7. concurrent behavior is safe if relevant;
8. adjacent canonical behavior still works.
If the repository already has a better existing suite, extend that instead of creating a redundant script.

17. POST-BUILD GREP CHECKS
After implementation, rerun targeted searches.
Prove:
* old unsafe code path is gone or no longer reachable;
* all relevant callers use the corrected path;
* no bypass was missed;
* no stale status consumer was forgotten;
* old helper/legacy owner is not still active where it would conflict.
Document the important results.

18. REQUIRED GATES
Run relevant existing gates.
At minimum:
1. targeted new/modified tests;
2. related subsystem tests;
3. TypeScript/typecheck;
4. relevant contract/invariant tests;
5. migration validation if applicable.
Use actual repository commands.
Do not invent gate commands.
Report:
Gate	Command	Result
Targeted	...	PASS
Related	...	PASS
Typecheck	...	PASS
Other	...	PASS
If a gate fails:
* determine whether the task caused it;
* fix task-caused failures;
* clearly identify unrelated pre-existing failures.
Do not claim COMPLETE if a task-owned required gate remains red.

19. DIFF REVIEW
Before completion run:
git status
git diff --stat
git diff
Confirm:
* only intended files changed;
* no secrets;
* no debug junk;
* no accidental generated files;
* no unrelated lockfile modification;
* no unrelated formatting;
* no production config mutation.

LIBERTY-SPECIFIC SAFETY RULES
Apply these only where relevant.
Contacts
Do not create competing contact writers.
Audit direct contact inserts/updates before introducing another path.
Prospects
Conversion must consider:
* duplicate identity;
* concurrent requests;
* replay;
* deal duplication;
* partial failures.
Outreach
Keep these concepts separate:
* data readiness;
* lead score;
* consent;
* contactability;
* promotional eligibility.
Passing one does not imply passing another.
Consent
Email and SMS are channel-specific unless a verified global DNC rule applies.
Never infer consent merely because a contact exists or submitted a form.
GHL
Treat GHL/local behavior as distributed state.
Verify:
* ownership;
* ordering;
* retries;
* duplicate IDs;
* field protection;
* partial failures.
Email / sequences
Never bypass canonical durable enrollment/sending architecture.
Verify suppression/unsubscribe/contactability where relevant.
Jobs
Revenue-critical work should not rely on:
* setImmediate;
* process-memory-only retries;
* swallowed .catch(() => {});
* non-durable recovery.
Imports / enrichment
Preserve:
* provenance;
* idempotency;
* identity safety;
* confidence;
* manual authority.
Database
Do not use db push.
Use proper migrations and constraints.

PRACTICAL REVIEW STANDARD
Do not turn this prompt into an excuse to redesign every task.
A finding should block the task when there is a realistic production path to:
* duplicate sends;
* compliance bypass;
* wrong customer/merchant mutation;
* duplicate records with material impact;
* data loss;
* unauthorized behavior;
* broken revenue flow;
* unrecoverable job state.
Do not block an otherwise safe implementation merely because a cleaner abstraction or theoretical hardening could exist later.
Separate:
BLOCKING CORRECTION Needed for the task to be safe/correct.
from:
FOLLOW-UP HARDENING Useful later but not required to merge this task.

FINAL DIRECTIVE
Do not implement the task exactly as written merely because it was provided.
First verify it.
Then:
Repository baseline → VFC → greps → verified root cause → ownership → blast radius → corrected plan → kill lines → implementation → targeted tests → gates → post-build greps → final VFC → merge verdict.
If the task is build-ready after reasonable corrections, build it in this same run.
Do not create another planning loop unless there is a genuine blocker.
