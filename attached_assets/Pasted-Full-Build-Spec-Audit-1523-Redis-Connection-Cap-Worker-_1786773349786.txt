Full Build-Spec Audit — #1523 Redis Connection Cap / Worker Timeouts

Audit date: 2026-08-15
Audited repository: liberty-buildspec-audit
Repository HEAD: 4819cefac1478ae700c9996427174e822d97c5a5
Build spec: Pasted markdown(3).md
Audit type: static code, architecture, operational-safety, and cross-document review
Verdict: NO-GO AS WRITTEN

Executive conclusion

The spec correctly identifies one important architectural fact: the shared IORedis singleton avoids the former three-connections-per-queue pattern, while each BullMQ Worker still needs a blocking connection. The repository currently defines 23 physical workers by default, or 22 when legacy GHL sync owns that duty.

The proposed eight-to-one consolidation is not build-ready, however. It treats each logical automation and each physical BullMQ worker as the same thing, while the codebase relies on that one-to-one relationship for kill switches, schedules, retry policy, heartbeat freshness, success/failure attribution, automation-registry status, queue metrics, DLQ operations, and startup reconciliation. Replacing eight physical queues with one background-tasks queue without first separating those two models would cause control-plane and observability regressions.

The spec also makes three invalid safety assumptions:

It says old Redis queue and repeatable-job state can be left orphaned and jobs in flight will continue. A new worker on a new queue name cannot consume jobs stored under the old queue names.

It says a single worker with concurrency: 1 preserves behavior. Today the eight workers may run simultaneously; consolidation serializes all eight, creates head-of-line blocking, and changes execution timing and failure-domain boundaries.

It uses an endpoint and pure smoke test that can return a false green. /api/operator/queue-metrics currently counts the two properties of { queues, usingMock }, not the active queues, so it diagnoses three estimated connections regardless of the actual topology.

The immediate operational priority should be to confirm the real Redis account limit and live failure mode. If the service is hitting a provider cap, raising the limit or moving to an appropriate plan is the lowest-risk stabilization step. Worker pooling can follow as a controlled architectural change with logical-job identity preserved.

Evidence

Required correction

B-01

The provider limit and exact runtime failure are not established.

The repo hardcodes UPSTASH_FREE_MAX = 20 in server/services/queue-connection.ts:196-220. Current public Upstash free-tier documentation does not publish a 20-concurrent-connection allowance. The supplied audits report ETIMEDOUT, but the spec asserts rejected 21st connections and stalled BLMOVE without a live error sample.

Record the Redis product/plan, account limit, live connected_clients, process count, and actual error text. Require evidence such as a max-connections rejection, Worker ready/error/closed states, and a time-correlated incident trace before declaring the root cause proven.

B-02

The proposed cutover strands existing Redis jobs and schedule state.

The spec removes workers for eight old queue names and registers new jobs under background-tasks. BullMQ workers only consume their own queue keyspace. Current startup cleanup runs only for active QUEUE_CONFIGS in server/services/queue-manager.ts:1149-1209.

Add a Redis operational migration: quiesce producers/schedulers, inventory waiting/active/delayed/failed/repeatable jobs, remove old repeat configurations by key, drain or explicitly migrate jobs, install the new schedules, verify each logical schedule once, and retain a rollback procedure.

B-03

Per-automation kill switches would stop controlling the consolidated jobs.

buildProcessor() calls isAutomationEnabled(queueName) at queue-manager.ts:696-709. A pooled worker would check background-tasks; a missing registry row defaults enabled in automation-kill-switch.ts:24-52. Existing logical rows such as db-backup and onboarding-reminder would be bypassed.

Dispatch using a logical job definition and evaluate the logical automation key, not the physical pool name. Preserve existing kill-switch behavior and add tests proving every consolidated job can be disabled independently.

B-04

Heartbeats, registry status, success/failure, DLQ, and metrics attribution collapse to one pool.

Heartbeats use worker_heartbeat_${queueName} at queue-manager.ts:711-718; Worker events record config.name at queue-manager.ts:614-687; admin heartbeat expectations are derived from QUEUE_CONFIGS at admin.ts:1755-1786; metrics and DLQ iterate QUEUE_CONFIGS at queue-manager.ts:1332+ and 1416+.

Separate logical job definitions from physical worker pools. Carry logicalJobKey in job data/name and use it for control, history, heartbeat, audit, registry, and DLQ attribution. Report physical pool health separately.

B-05

The acceptance endpoint is already falsely green.

getAllQueueMetrics() returns { queues, usingMock } at queue-manager.ts:1332-1413. The route computes Object.keys(metrics).length at routes/queue-metrics.ts:77-79, which is always 2, producing an estimate of 3 connections.

Count the actual instantiated worker topology, not object keys or logical jobs. Add a regression test for the route response. Do not use safeForUpstashFree as a kill line until the configured limit and counting source are trustworthy.

B-06

concurrency: 1 materially changes behavior and creates head-of-line blocking.

Eight current Workers each have their own concurrency, so up to eight job types can execute concurrently. The proposed single worker allows only one. Tasks include database backup, AI snapshot generation, emails, enrollments, and monitoring.

Measure handler runtimes and schedule SLAs. Either use multiple pools by failure domain or a pooled Worker with safe local concurrency and durable per-job locks/idempotency. Prove no unacceptable delay under worst-case runtimes and retry storms.

High-risk defects and omissions

ID

Finding

Impact / correction

H-01

The connection arithmetic in the spec is imprecise.

Default topology is 23 workers + one shared client = 24. Removing eight and adding one leaves 16 workers + one shared = 17, not 16. It is 16 total only when legacy GHL sync excludes that worker. Acceptance must state both modes.

H-02

The pure smoke test can be hardcoded to pass.

scripts/test-bullmq-resilience.ts:189-228 already calls diagnoseRedisCapacity(11) even though the repo has 23 configs. The new test must derive the physical topology from exported configuration or a pure topology builder and fail if code and the manifest diverge.

H-03

The spec's repeatable-job semantics are incorrect for BullMQ 5.77.

BullMQ schedules the next repeat when the current job begins processing, not when it finishes. A low-capacity worker can reduce effective frequency. Concurrency 1 prevents simultaneous processing by that Worker but does not prove schedule preservation or idempotency.

H-04

Startup behavior is omitted.

setupRepeatableJobs() removes existing repeat entries, adds the repeat, and also enqueues an immediate randomly delayed startup job for each repeatable config. Consolidation must intentionally preserve or change this per-job startup execution.

H-05

Retry and backoff policy are logical-job properties, not pool properties.

The eight queues have different attempts/backoff/schedule settings. A single QueueConfig cannot accurately represent all of them unless job options come from a logical manifest.

H-06

“No external APIs” and “no ordering changes” are false.

The infrastructure refactor changes when externally acting handlers run. These handlers perform pg_dump/storage, AI generation, email, workflow enrollment, and merchant/customer actions. Ordering, delay, retry timing, and duplicate prevention must be reviewed as side-effect safety.

H-07

The handler-extraction scope is understated.

Some cases are inline, notably executive snapshot processing. The instruction that each handler already exists as a named function is not true. Extracting, typing, and testing handlers increases the change surface.

H-08

Actual connection use has more variables than 1 + workerCount.

The estimate omits transient probes, deployment overlap, and additional service instances. Short-lived connections exist in activation, wizard, integration validation, and scripts. During rolling deploys, two worker processes can temporarily double blocking connections. Reserve explicit operational headroom.

Corrected architecture

The durable design should distinguish logical jobs from physical worker pools.

flowchart TD
    A["Logical job manifest"] --> B["Scheduler registration"]
    A --> C["Kill switch and retry policy"]
    A --> D["Logical metrics and heartbeat"]
    B --> E["Physical worker pool"]
    E --> F["Handler dispatch"]
    F --> D

Logical job manifest

Each job definition should include at least:

stable logical key and BullMQ job name;

physical pool name;

schedule (every or pattern);

immediate-on-start policy;

attempts and backoff;

handler function;

expected duration / stale threshold;

concurrency or overlap key;

idempotency key strategy;

kill-switch key;

side-effect classification and owner.

Physical pool manifest

Each pool should define:

queue name;

one Worker instance per application process;

local concurrency;

rate limiter if required;

connection-budget contribution;

graceful shutdown and readiness state.

The connection diagnostic must count instantiated physical Workers. Logical schedules must remain independently controllable and observable.

Safer grouping

Do not put all eight jobs into one concurrency-1 failure domain without runtime measurements. A safer starting point is to separate infrastructure/long-running jobs (database backup and executive snapshot) from customer/partner communications. Monitoring jobs should not wait behind backups or retrying email work. Final grouping should be based on measured p95/p99 duration, schedule collisions, rate limits, side effects, and acceptable lateness.

Corrected execution plan

Phase 0 — prove and stabilize the incident

Record branch, HEAD, deployment/process count, Redis product/plan, configured account limit, and the current Worker roster.

Capture live connected_clients, INFO clients, Worker ready/error/closed events, and provider error text during a failing window.

Fix /api/operator/queue-metrics to derive its physical Worker count from the QueueManager topology.

Make the capacity limit configuration-driven and label provider assumptions explicitly. Do not present the number 20 as authoritative unless verified for the actual account.

If the cap is confirmed, raise the provider limit or plan first to restore headroom. This is the least invasive incident response and supports the roadmap's runtime-stability priority.

Phase 1 — model logical jobs separately

Introduce typed LOGICAL_JOB_DEFINITIONS and WORKER_POOL_DEFINITIONS.

Export a pure buildWorkerTopology(runtimeFlags) function used by QueueManager, diagnostics, and tests.

Route pooled jobs through a handler registry with exhaustive type checking.

Preserve logical keys for kill switches, registry updates, heartbeats, job history, alerts, and DLQ records.

Preserve each job's schedule, attempts, backoff, immediate-start rule, and idempotency behavior.

Phase 2 — migrate Redis state safely

Inventory repeatable/job-scheduler entries and all job states for every old queue.

Quiesce schedule creation and on-demand producers for the migration window.

Drain active work. Decide explicitly whether waiting/delayed/retry jobs are completed on old workers or recreated idempotently in the new pool.

Remove old repeat configurations using their exact keys.

Register each new logical schedule exactly once in the destination pool.

Verify old queues contain no stranded active, waiting, delayed, or retryable jobs; retain failed history only by policy.

Deploy new workers, validate readiness and logical heartbeats, then remove old workers.

Roll back by disabling new schedules before restoring old workers/schedules; never run both schedule owners concurrently.

Phase 3 — canary and prove

Canary one low-risk logical job before moving the full set.

Observe at least one expected execution per schedule class and a full 24-hour runtime window before declaring Redis timeout trends resolved; monthly jobs need an injected schedule test.

Test rolling-deploy overlap and confirm connection headroom remains safe with two application processes plus transient probes.

Confirm every logical kill switch, heartbeat, success/failure status, DLQ action, and admin view remains correct.

Revised acceptance criteria

The task is complete only when all of the following are true:

The actual Redis plan/account limit is recorded and the capacity budget includes all application instances, Worker blocking connections, transient probes, and deployment overlap.

/api/operator/queue-metrics reports the actual physical Worker count and actual connected_clients; it does not derive count from the response object's property count.

No ERR max concurrent connections exceeded, connection-rejection, or recurring ETIMEDOUT trend appears during the observation window.

Every logical job has exactly one schedule owner and executes on its original schedule or an explicitly approved replacement schedule.

Old queue names have no stranded active, waiting, delayed, or retryable jobs, and old repeat configurations are removed or deliberately retained with a documented consumer.

All logical kill switches continue to work independently.

Logical heartbeats, status, success/failure events, audit entries, and DLQ records retain the original automation identity.

Restart creates one Worker per physical pool and one scheduler per logical job; rolling deployment stays within the verified connection budget.

Database backup or another long-running job cannot violate the latency SLA of communications or monitoring jobs.

Rollback has been exercised or demonstrated in a deterministic test environment.

Recommended disposition of the submitted spec

Do not hand the current text to a build agent. Replace its preflight verdict with:

NO-GO pending runtime proof and architecture corrections. The shared-client connection estimate is plausible, but the provider limit and failure mechanism are not yet proven. Queue consolidation requires logical-job/physical-pool separation, a Redis state migration, per-job control and observability preservation, and corrected topology diagnostics before implementation.

If immediate production stability is the goal, permit a plan/limit increase in scope. Treat pooling as a separate follow-up change after live runtime evidence and handler-duration data are available.

Audit limitations

This is a static audit of the available repository and supplied documents.
