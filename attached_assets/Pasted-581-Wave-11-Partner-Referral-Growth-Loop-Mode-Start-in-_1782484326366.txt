What & Why

Partners and live merchants are a second acquisition channel.

Current assets already exist:

* /partners
* /partners/cpa
* /partners/bookkeeper
* /partners/insurance
* ISOPartnerProgram.tsx
* PartnerPortal.tsx
* PartnerOrgDashboard.tsx
* AffiliateProgram.tsx
* cookie-based attribution
* co-branded proposals
* Wave 6 partner/referral sequences

But the growth loop is incomplete:

* Partner portal does not clearly show referred merchants, active merchants, estimated/reconciled residuals, referral code, co-branded proposal link, application status, and commission tier.
* Referral attribution is not guaranteed to persist from public referral link → contact → deal → merchant application → onboarding → residual reconciliation.
* Merchant referral flow is not clearly connected to Wave 6 safety gates.
* Co-branded proposal attribution can be lost or not written onto the resulting contact/deal/application.
* Residual reconciliation does not provide a partner-level breakdown.
* Partner page SEO/CTA copy exists but needs unique intent by partner type and a stronger residual calculator CTA.

Wave 11 closes the referral flywheel:

partner gets referral link → merchant lead converts → attribution persists → proposal/application/deal retains partner → onboarding/live merchant counted → residuals reconciled → partner sees results → partner refers more merchants

After this wave:

1. Partners can log in and see a useful referral performance dashboard.
2. Partners can copy a safe referral link.
3. Public referral links attribute new contacts/deals correctly.
4. Live merchants can refer another business safely.
5. Merchant referral submissions create measurable referral leads without violating consent/contactability.
6. Co-branded proposal views and signups retain partner attribution.

Critical Safety Rules

1. Attribution must have a source-of-truth rule

Before building, define and report attribution precedence.

Possible attribution sources:

?ref=PARTNERCODE
lb_ref cookie
affiliate cookie
co-branded proposal token
merchant referral link
manual CRM assignment

Required:

* do not silently overwrite existing high-confidence attribution.
* preserve first-touch attribution unless the repo already uses last-touch and product confirms that.
* store latest-touch separately only if fields exist.
* partner attribution should persist to contact, deal, merchant application, and residual reconciliation where schema supports it.
* co-branded proposal attribution should attach to the deal/application it generated, not randomly override unrelated merchant records.

2. Merchant referral does not equal consent

A live merchant submitting a referral does not automatically mean the referred business consented to SMS/email marketing.

Merchant referral sequence behavior must use existing Wave 6 sequence eligibility/contactability rules.

If the referred business has not explicitly consented:

* create the referral contact/lead.
* attribute referrer.
* create a manual follow-up task or safe internal notification if needed.
* do not direct-send SMS/email unless existing consent/contactability permits it.

Do not bypass DNC, opted-out, contactability, consentTier, channel gates, or lifecycle rules.

3. Partner commission language must be qualified

Partner portal may show:

estimated residual
reconciled residual
projected payout
pending review
manual payout status

Do not show unsupported guaranteed earnings.

Use wording like:

Estimated residual based on reconciled processing volume.
Final payout subject to review and partner agreement.

4. “Post Residuals” cannot imply payment processing

Direct partner payment processing is out of scope.

Do not build actual partner payment disbursement.

Allowed actions:

* mark residuals as posted internally
* generate payout alert
* create payout review task
* send partner notification if existing safe notification path exists
* export payout summary if existing export pattern exists

Button language should be safer:

Prepare Payout Alert

or:

Mark Residuals Ready

not:

Pay Partner

unless real payment processing exists and is in scope.

5. Partner portal must be org-scoped

A partner must only see data for their own partnerOrgId.

Do not rely on client-side filtering for partner data.

All partner portal KPI endpoints must derive partner org from the authenticated partner session/user membership.

6. Referral code handling must be safe

Referral codes are public, but must still be normalized and validated.

Required:

* trim
* case-insensitive match
* reject unsafe characters
* prevent arbitrary SQL/filter injection
* handle inactive/suspended partner orgs
* handle expired/disabled referral codes if fields exist
* avoid exposing partner internal details from invalid code lookup

2. Referral attribution capture

When a public lead/contact is created from:

?ref=PARTNERCODE

or an existing valid referral cookie, the backend sets:

* contacts.referralSource = "partner" or closest verified enum/value
* contacts.partnerOrgId = matchingPartnerOrg.id
* partner code field if available
* attribution timestamp/source if fields exist

Then persists attribution through:

* contact
* deal
* merchant application
* onboarding merchant profile if schema supports it
* residual reconciliation linkage

GHL upsert syncs:

lb_referral_source
lb_partner_code

through existing safe GHL contact upsert path.

Do not create raw GHL calls from frontend.

⸻

3. Attribution precedence

Implement and document a deterministic attribution precedence.

Preferred rule unless existing product behavior says otherwise:

1. Existing manually assigned partnerOrgId is preserved.
2. Co-branded proposal token attribution applies to proposal/application/deal generated from that token.
3. Explicit URL ?ref= valid partner code sets first-touch partner attribution if none exists.
4. Existing referral cookie applies if no stronger attribution exists.
5. Merchant referral attribution applies for merchant-submitted referrals, not partner attribution.

Do not overwrite an existing partnerOrgId silently.

If a new referral conflicts with existing attribution, write an audit/log if available and preserve the stronger/earlier source.

⸻

4. Merchant referral flow

Live merchants in Merchant Portal see:

Refer a Business

Required:

* shareable merchant referral link if supported
* simple referral form:
    * business name
    * contact name
    * phone
    * email if available
    * optional note
* creates a new contact with:
    * referralSource = "merchant" or closest verified value
    * referrerId = currentMerchantContactId if field exists
    * source detail if field exists
* creates an internal task/notification if sequence enrollment is not allowed
* triggers Wave 6 Merchant Referral sequence only through existing eligibility/enrollment path

Important:

Do not direct-send SMS/email to the referred business unless consent/contactability permits it.

If the sequence is intended to remind the referring merchant, enroll the referrer.
If the sequence is intended to contact the referred merchant, require contactability/consent.

The final report must clarify which contact is enrolled and why.

Do not infer or invent commission rates.

7. Co-branded proposal attribution

When /co-branded-proposal/:token is viewed:

* identify partner org from token
* record safe analytics/audit if existing pattern exists
* do not expose token internals publicly

When merchant starts application/signs up from that proposal:

* preserve partnerOrgId on resulting deal/application/contact if no stronger attribution exists
* set deal.partnerOrgId if field exists
* preserve source token/proposal ID if field exists
* do not overwrite existing manually assigned partner attribution without audit

If token is invalid/expired:

* fail closed
* do not attribute to wrong partner
* show existing safe error state

8. Partner referral sequence trigger

When a partner org is approved:

* enroll partner contact/org owner in Wave 6 Partner Referral sequence through existing sequence eligibility/enrollment path
* do not directly send from the approval handler
* dedupe enrollment by partner org/contact + sequence family
* respect DNC/opt-out/contactability rules
* write audit/log if available

Do not enroll every user in the partner org unless product explicitly wants that.

Default: enroll primary partner contact/owner only.
