# LIBERTY BANCARD — PREFLIGHT + BUILD MODE

## MODE

PREFLIGHT + BUILD. Verify the worker/queue claims against current code and runtime-facing configuration, correct the plan, and implement all safe repository-owned work in the same run. Stop only for a false finding, wrong owner, missing prerequisite, unavailable runtime evidence required for a production capacity decision, necessary scope split, or kill line.

Do not replace durable work with in-memory execution, invent another scheduler/coordinator, use `db push`, weaken recovery tests, alter production capacity blindly, or clean unrelated workers.

Required sequence: baseline → VFC → searches → root cause → ownership → blast radius → schema/auth/concurrency/external checks → verdict → corrected plan → kill lines → build → tests/gates → post-build searches → diff → final VFC → merge verdict.

## 1. REPOSITORY BASELINE

Capture branch, HEAD SHA, working tree, migration head and current queue/scheduler configuration files. Preserve unrelated changes. Record whether runtime capacity/settings evidence is available without mutating it.

## 2. VERIFIED FROM CODE — PREFLIGHT

Create:

| ID | Task Claim | Verdict | Verified Reality | Evidence |
|---|---|---|---|---|
| VFC-01 | ... | CONFIRMED / PARTIAL / FALSE / OUTDATED | ... | `file:line` |

Verify every BullMQ queue/worker, legacy interval/cron, startup registrar, named schedule, lock/fence, claim/lease, retry/max-attempt path, post-enrichment intent writer/worker, coordinator hold/release owner, Redis connection factory, heartbeat/alert, backlog endpoint and measured high-volume query. Trace all callers, writers and consumers.

## 3. REQUIRED SEARCH / GREP CHECKS

Search and inspect:

- `Queue`, `Worker`, BullMQ, repeatable jobs, job schedulers and queue names;
- `cron`, `setInterval`, `setTimeout`, `setImmediate`, startup/boot registration;
- discovery, re-enrichment, post-enrichment and digest/outreach jobs;
- `pending`, `processing`, claim token, lease, heartbeat, attempts, retry and DLQ statuses;
- coordinator desired/observed state, holds, staged release and pause authority;
- Redis/Upstash connection creation, pools, locks, timeouts and alerts;
- schedule interval mutation and named schedule reconciliation;
- backlog preview/list/status APIs and UI consumers;
- `pg_stat_statements`, query plans and existing indexes;
- recovery/concurrency/pre-deploy tests.

Inspect implementations; a registered name is not proof of a live unique owner.

## 4. VERIFIED ROOT CAUSE

State original assumptions and verified reality for crash windows, duplicate ownership, schedule loss, Redis headroom, coordinator convergence, recovery assertions and hot queries. Separate code defects from runtime evidence gaps. Correct outdated findings explicitly.

## 5. SOURCE-OF-TRUTH CHECK

Identify canonical queue/job owner, schedule registry, claim/lease owner, coordinator/hold owner, Redis client owner, post-enrichment eligibility owner, operational audit owner and database performance evidence source. Do not add parallel schedulers, locks or coordinator truth.

## 6. BLAST RADIUS

### In scope

- durable intent creation/claim/recovery;
- production-function retry/max-attempt/idempotency tests;
- schedule ownership and durable fencing;
- coordinator convergence and hold hygiene;
- bounded backlog plus run/lease/oldest-age visibility;
- Redis connection budgeting and heartbeat/alert SLO wiring;
- measured query/index remediation.

### Out of scope

- broad provider behavior (BT-10);
- consent/outbound redesign (BT-03/BT-04);
- speculative queue framework replacement;
- unmeasured index additions;
- production capacity/config mutations without evidence and authority;
- CRM navigation consolidation (BT-11).

List expected/untouched files after preflight.

## 7. DATA / SCHEMA CHECK

Verify intent/job/hold tables, status values, token/lease columns, attempts, timestamps, uniqueness, FKs, archive/GC behavior and all readers/writers. A committed `processing` row must already have a valid claim/lease or be impossible; otherwise commit pending and claim atomically later.

Use the next migration and journal if required; prove clean replay. For indexes, capture the measured query and plan before/after. Do not use `db push`, bulk-reset shared state or rewrite unrelated history.

## 8. AUTHORIZATION CHECK

Produce a matrix for queue visibility, retry/requeue, hold creation/release, staged-release approval, schedule changes, recovery and capacity controls. Admin actions must be server-role-gated and audited. Worker credentials must not inherit operator/admin capabilities unnecessarily.

## 9. CONCURRENCY / IDEMPOTENCY CHECK

Central requirement. Test two workers claiming simultaneously, duplicate scheduler ticks, replica restart, lease expiry, crash after claim, crash after external effect, retry, max attempts, schedule update races and coordinator release races. Require atomic claims, owner/fencing tokens, stable idempotency keys and recoverable terminal states. Never use SELECT-if-missing-INSERT as the sole protection.

## 10. EXTERNAL SIDE-EFFECT CHECK

For jobs that call GHL, email/SMS, enrichment or another provider, document claim → final authority/eligibility check → external call → durable result/audit → ack ordering. Verify external success/DB failure, DB success/external failure, timeout, retry and duplicate execution. External effects are not atomic with PostgreSQL/Redis.

## 11. PREFLIGHT VERDICT

Choose BUILD-READY, BUILD-READY WITH CORRECTIONS, PREFLIGHT REQUIRED, NOT BUILD-READY, NOT NEW TASK or WATCH. Continue immediately for build-ready work. Runtime capacity or query evidence may leave a bounded verification item pending, but must not prevent correction of verified code defects and test gaps.

## 12. CORRECTED BUILD PLAN

State corrected root cause, outcomes and file-specific steps. Separate production correctness, isolated tests and runtime/capacity evidence. Identify how parallel task branches avoid migration or shared scheduler-file conflicts.

## 13. KILL LINES

- KILL LINE: If a crash, retry, replica race or duplicate tick can permanently strand work or duplicate a material external side effect, the task has FAILED.
- STOP if two active owners can execute one logical job without durable fencing.
- STOP if a `processing` intent can exist without a valid claim/lease.
- STOP if changing a base interval deletes or renames unrelated schedules.
- STOP if tests create persistent holds, epochs, records or provider calls.
- STOP if capacity/index claims lack measured evidence.
- STOP if recovery tests avoid the production claim/retry functions.

## 14. IMPLEMENTATION RULES

Use current durable queue/coordinator patterns and the smallest safe diff. No architecture replacement, unrelated job cleanup, broad rename, formatting sweep or dependency/config mutation. Preserve named schedules and fail-closed behavior.

## 15. TEST REQUIREMENTS

Cover happy execution, invalid eligibility, simultaneous claims, duplicate schedule ticks, replay, lease expiry, crashes at each durable boundary, max attempts/DLQ, hold/release convergence, named schedule preservation, isolated teardown, authorization, provider partial failure and measured query regression. Tests must invoke production functions.

## 16. SMOKE / INTEGRATION TEST

Extend the strongest queue/recovery suite or add `scripts/test-bt09-queue-recovery-ownership.ts`. Prove:

1. only one worker owns a logical job;
2. intent creation cannot strand `processing` work;
3. retry/replay does not duplicate effects;
4. max-attempt state is correct;
5. named schedules survive interval changes;
6. coordinator/holds converge and teardown restores baseline;
7. backlog/run/lease/age output is bounded and correct;
8. fake transports receive no forbidden call.

## 17. POST-BUILD GREP CHECKS

Prove duplicate legacy/BullMQ owners are removed/fenced, no unclaimed-processing path remains, production retry functions are used, named schedule mutation is safe, Redis clients use the canonical factory, test cleanup is scoped and measured hot paths have justified indexes only.

## 18. REQUIRED GATES

Run targeted queue/recovery/coordinator tests, outbound/contactability/provider-adjacent suites, typecheck, build, migration replay, schedule/invariant/pre-deploy gates, test-isolation checks and `git diff --check`. Report actual commands and distinguish unavailable runtime SLO proof.

## 19. DIFF REVIEW

Run `git status`, `git diff --stat` and `git diff`. Confirm intended files only, no real provider configuration, secrets, debug artifacts, unbounded logs, unrelated formatting/lockfile changes or test-created persistent state.

## 20. FINAL VFC TABLE

Produce:

| ID | Requirement | Evidence | Test / Gate | Status |
|---|---|---|---|---|
| VFC-F01 | ... | `file:line` | test | PASS |

Map every requirement and kill line; include measured query evidence for any index change.

## 21. FINAL RESPONSE FORMAT

Return: VERDICT (COMPLETE / VERIFIED, PARTIALLY COMPLETE or DO NOT MERGE); Repository State (starting SHA, ending SHA/working tree, migration head); Verified Root Cause; Preflight Corrections; Implementation (`file:line`); Tests/Gates; Grep Verification; Kill-Line Verification; Runtime Verification; Remaining Risks; and Final Status (SAFE TO MERGE, SAFE TO MERGE — RUNTIME VERIFICATION PENDING or DO NOT MERGE). Never call local fake-worker evidence proof of production singleton/capacity.

## LIBERTY-SPECIFIC SAFETY RULES

- Revenue-critical jobs must be durable, fenced and replay-safe.
- Final outbound/eligibility authority remains mandatory before external I/O.
- Do not use swallowed `.catch(() => {})` as recovery.
- Redis, PostgreSQL and providers are separate failure domains.
- Proper migrations only; no `db push`.

## PRACTICAL REVIEW STANDARD

Block duplicate provider effects, permanent stuck state, lost schedules, unfenced replicas, authorization bypass, persistent test pollution or unmeasured dangerous DB changes. Do not require a queue-framework rewrite when existing durable primitives can be corrected.

# TASK TO PREFLIGHT + BUILD

## BT-09 — Queue Ownership, Recovery, Capacity & Database Performance

**Primary findings:** `QUE-01`, `QUE-02`, `QUE-03`, `QUE-05`, `QUE-07`, `QUE-08`, `QUE-09`, `QUE-10`, `QUE-12`, `DAT-07`, `ENR-06`

**Dependencies:** BT-03/BT-04 eligibility contracts; BT-05 isolated tests

### What & Why

Discovery, re-enrichment and post-enrichment work have incomplete or competing schedule ownership; intent claiming/recovery can be inconclusive; coordinator state and holds need cross-process convergence; Redis headroom is unproven; and high-volume queries lack evidence-driven performance closure.

### Done Looks Like

- Every logical job has one durably fenced owner.
- No `processing` intent lacks a valid claim token/lease.
- Claim/retry/max-attempt/idempotency use production functions.
- Named schedules survive interval changes.
- Coordinator desired/observed state, staged release and holds converge.
- Backlog/run/lease/oldest-age visibility is bounded.
- Redis connection and heartbeat/alert SLOs are evidenced.
- Only measured hot paths receive verified indexes.
- Tests leave no persistent state or provider effects.

### Out of Scope

- Provider yield/backfills, broad queue replacement, speculative indexes and production configuration changes without authority.

### Proposed Implementation Steps

1. Inventory owners, schedules, claims, Redis clients and hot queries.
2. Correct intent creation/atomic claim/lease semantics.
3. Fence or remove duplicate job owners.
4. Preserve/reconcile named schedules.
5. Close coordinator/hold convergence and test isolation.
6. Add bounded operational state and SLO evidence.
7. Profile and remediate measured database paths.
8. Add production-function crash/concurrency tests.

### Relevant Files and Areas to Verify

- queue manager, worker/bootstrap and scheduler registry
- post-enrichment intent/service/worker
- outbound queue coordinator and pause authority
- Redis/Upstash factories, heartbeat and alerts
- queue/backlog admin routes and UI consumers
- `shared/schema.ts`, migrations/journal and measured queries/indexes
- recovery, sequence, pre-deploy and isolation suites

### Existing Kill Line

KILL LINE: No logical job may have duplicate unfenced owners, unrecoverable intent state or replayable duplicate external effects.

## FINAL DIRECTIVE

Verify first, then build all safe repository-owned corrections in this run. Preserve durability and fail-closed authority; clearly reserve only genuine runtime capacity/singleton proof for exact-release verification.
