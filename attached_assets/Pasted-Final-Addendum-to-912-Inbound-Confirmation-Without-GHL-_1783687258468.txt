Final Addendum to #912 — Inbound Confirmation Without GHL Workflow Dependency

Verdict

BUILD-READY WITH CORRECTIONS.

The preflight findings are accepted as the implementation source of truth.

Confirmed Build Direction

Implement:

public form submission
→ preserve successful GHL workflow early-return path
→ otherwise attempt GHL direct email when available
→ fall back to SMTP using the recipient email address
→ record actual provider result
→ schedule a durable 24-hour follow-up

A GHL workflow ID must not be required for immediate confirmation delivery.

Correction 1 — Verify the BullMQ Consumer, Not Only the Producer

Before using the sequences queue, confirm:

the queue has a running worker
the worker dispatches by job.name
the new inbound follow-up job name will be handled
failed jobs are visible/retryable
the worker starts in production

Add a concrete job type, for example:

inbound-confirmation-followup

Required flow:

await queue.add(
  "inbound-confirmation-followup",
  {
    contactId,
    dealId,
    formType,
    submissionId,
  },
  {
    delay: 24 * 60 * 60 * 1000,
    jobId: followupJobId,
    attempts: existingSafeRetryCount,
    backoff: existingSafeBackoff,
    removeOnComplete: existingPolicy,
  },
);

Do not put it on a queue whose worker does not recognize the job name.

Kill line

STOP if queue.add() is implemented without proving that a production worker consumes inbound-confirmation-followup jobs.

Correction 2 — Use a Submission-Scoped Idempotency Key

Do not use only:

inbound_followup:<contactId>:<formType>

That can prevent a legitimate future follow-up when the same contact submits the same form again.

Preferred key:

inbound_followup:<submissionId>

Acceptable fallback:

inbound_followup:<contactId>:<dealId>:<submittedAtEpoch>

Use a stable identifier created once for that specific submission.

If the public routes do not currently expose a submission ID, generate one inside the canonical helper and include it in:

audit metadata
BullMQ payload
BullMQ jobId

Kill line

STOP if one prior form submission can permanently suppress follow-up scheduling for all later submissions by the same contact.

Correction 3 — Separate Immediate Delivery From Follow-Up Scheduling Outcome

Immediate confirmation and delayed follow-up scheduling are separate operations.

Required behavior:

immediate email succeeds
follow-up scheduling succeeds
→ inbound_confirmation_sent
→ inbound_confirmation_followup_scheduled
immediate email succeeds
follow-up scheduling fails
→ keep inbound_confirmation_sent
→ write inbound_confirmation_followup_schedule_failed
→ do not falsely mark immediate confirmation failed
immediate email fails through all providers
→ inbound_confirmation_failed
→ do not schedule the follow-up unless there is an explicitly approved reason to do so

Add audit action:

inbound_confirmation_followup_schedule_failed

Include:

contactId
dealId
formType
submissionId
failureReason

Canonical Email Helper

The private GHL-only unifiedSendEmail() must be reworked or replaced with a provider-independent helper.

Suggested result:

type ConfirmationEmailResult =
  | {
      sent: true;
      provider: "ghl_direct" | "smtp";
      providerMessageId?: string | null;
    }
  | {
      sent: false;
      providerAttempts: Array<{
        provider: "ghl_direct" | "smtp";
        error: string;
      }>;
      reason: string;
    };

Required provider order:

GHL direct email, only when the required GHL client/contact data exists
→ SMTP fallback using contact.email

SMTP must not require:

ghlContactId
GHL configuration
GHL workflow ID

A best-effort GHL contact upsert may still occur, but failure to upsert must not block SMTP confirmation delivery.

SMTP Result

Inspect sendSmtpEmail() return value.

If Nodemailer returns a message ID, capture it.

Do not hardcode:

providerMessageId = null for SMTP

unless the SMTP helper genuinely exposes no provider ID.

GHL Workflow Early Return

Preserve the existing successful workflow behavior:

configured workflow triggers successfully
→ audit ghl_inbound_confirmation_enrolled
→ return
→ no direct email duplicate

If workflow enrollment fails or is unavailable:

continue to direct email path

Do not remove or weaken the successful early return.

SMS

Keep SMS optional and non-blocking.

If GHL/SMS is unavailable:

skip SMS
email result remains authoritative

SMS must continue to require existing consent and enablement gates.

Do not add SMTP-like fallback semantics for SMS.

Durable Follow-Up Handler

The BullMQ handler must reload current state at execution time.

Required checks:

contact still exists
contact has not opted out
contact is not DNC
email remains usable/contactable
deal has not progressed beyond the eligible state
follow-up has not already been sent

Use evaluateContactability() at execution time.

Do not rely solely on state captured 24 hours earlier.

Write:

inbound_confirmation_followup_sent
inbound_confirmation_followup_skipped
inbound_confirmation_followup_failed

For skips, include a stable reason such as:

deal_progressed
opted_out
dnc
no_contact
no_email
contactability_blocked
duplicate_already_processed

Dev Redis Limitation

Do not claim durable persistence when using an in-memory/mock Redis implementation.

Final report must state separately:

Production Redis durability: verified / not verified
Local mock durability across process restart: no

A mock Redis job disappearing after a development process restart is expected; a production Redis-backed delayed job disappearing is a blocker.
