582 — Wave 12: Release QA + Go-Live Safety

Mode

Start in PLAN / PREFLIGHT MODE, then build the release validation suite and go-live safety layer.

This is the final release-readiness wave after Waves 1–11.

Do not add product features. Do not redesign pages. Do not change public copy except for operator-facing activation/checklist language. This wave proves that the platform can safely go live and that operators have a repeatable checklist before enabling acquisition/automation flags.

What & Why

Before scaling acquisition, every release kill line must be proven with tests, scripts, screenshots, and an operator checklist.

The platform must prove:

* no cold scraped lead can receive automated SMS, voice AI, or ringless voicemail
* no DNC contact can be enrolled in a sequence
* no opted-out contact can be enrolled in any automated sequence
* no PEWC checkbox exists without storing disclosure evidence
* no statement upload succeeds without CRM contact/deal creation
* no appointment booking is unattributed
* no sensitive document route lacks role protection
* no GHL workflow enrollment bypasses contactability
* no queue failure is invisible to operators
* no feature flag can be enabled without visible prerequisites and release checks

Wave 12 builds and runs the release validation suite, extends the existing smoke-role-guards.ts pattern to compliance gates, and creates a go/no-go checklist operators can run before enabling each feature flag.

Non-Negotiable Release Safety Rules

1. No real outbound sends during tests

Tests must not send real SMS, voice AI calls, ringless voicemail, live GHL workflow enrollments, or customer emails.

Use existing dry-run/test/mocked paths where available.

If no dry-run exists, the script must verify blocking logic without firing the send.

Kill line:

Stop if a validation test would trigger a real outbound SMS, voice call, ringless voicemail, GHL workflow, or customer email.

2. Test data must be isolated

All scripts must use clearly marked test contacts/leads.

Required prefix/pattern:

QA_RELEASE_TEST

or equivalent existing repo test naming convention.

Scripts must either:

* clean up created test records, or
* mark them clearly as test data and exclude them from automation.

Do not run tests against real customer/merchant data.

3. Feature flag enabling must be guarded

The Activation Panel may show enable/disable controls, but enabling high-risk automation flags must be operator-safe.

For high-risk flags:

SMS_ENABLED
VOICE_AI_ENABLED
RINGLESS_VM_ENABLED
ORCHESTRATOR_ENABLED
NIGHTLY_DISCOVERY_ENABLED
SDR_ENABLED

The UI must show:

* current state
* what it enables
* prerequisites
* last pass/fail status
* verification command
* kill lines satisfied
* operator confirmation
* admin/manager role guard

Preferred:

Enable button is disabled until prerequisites are marked passed or an admin override reason is provided.

Do not make feature flag enabling a casual one-click action.

4. Static compliance scanning must be precise

A brittle grep like “sendSms preceded by evaluateContactability” is not enough by itself.

The scanner should:

* find direct send call sites
* classify them by channel
* allow low-level sender implementations only if they are explicitly listed
* fail business-logic call sites that send without calling contactability/sequence eligibility
* report file + line + reason
* use an allowlist file/comment only for known safe infrastructure wrappers

If AST parsing is too heavy, use structured grep plus explicit allowlist and require final manual review of findings.

2. Contactability unit tests

scripts/test-contactability.ts

It imports evaluateContactability() and runs at least 10 test cases.

Required cases:

1. cold scraped lead — SMS blocked
2. cold scraped lead — voice AI blocked
3. PEWC lead — SMS allowed only if SMS feature flag enabled
4. PEWC lead — SMS blocked if SMS feature flag disabled
5. DNC contact — all automated channels blocked
6. opted-out contact — all automated channels blocked
7. quiet hours — call/voice blocked
8. Florida contact without express written consent — SMS blocked
9. doNotAutoContact — all automated channels blocked
10. ringless VM — blocked unless contactability + mobile phone-type requirements pass
11. email-only consent — SMS blocked
12. manual call task — allowed only if current rules permit

Script exits:

* 0 on all pass
* 1 with detailed failures

3. Sequence enrollment compliance tests

scripts/test-sequence-compliance.ts

Required tests:

* enroll cold lead in PEWC-required sequence → blocked

Kill Lines

Stop and report if:

* any test would trigger a real outbound SMS, voice call, ringless VM, GHL workflow, or customer email.
* test data cannot be isolated from real contacts/leads.
* contactability service cannot be imported/tested directly.
* sequence enrollment API cannot run in dry-run/test mode or equivalent safe path.
* static compliance scanner cannot distinguish wrappers from business send sites.
* feature flag mutation API does not exist and would require inventing a risky new control path.
* enabling a high-risk feature flag would not be admin/manager guarded.
* queue failure visibility would expose secrets or sensitive payloads.
* document route tests would expose real private documents.
* PEWC evidence storage fields cannot be identified.
* booking attribution flow cannot be tested without live external booking provider calls.
* SEO script would require broad route rewrites.
* mobile screenshot route list includes nonexistent pages and no fallback is defined.
* any compliance gate is skipped because “manual review later.”
