Verdict: NOT BUILD-READY

The redesign fixes several real issues, but the proposed stale-heartbeat takeover is still unsafe. A new run can take ownership while the old run remains alive, and nothing prevents the old run from continuing to score contacts or overwrite the new run’s progress.

Corrections to send back

Resolve these blockers before implementation:
1. Add runId fencing to every job mutation.
A DB-level start guard is insufficient by itself.
Every progress/heartbeat/completion/failure update must include the active runId condition:
UPDATE system_settings
SET value = ...
WHERE key = 'contact_scoring_job_progress'
  AND value->>'runId' = :runId
  AND value->>'status' = 'running'
If 0 rows are updated, the worker has lost ownership and must stop immediately.
2. Fence batch execution before and after database writes.
Before beginning each batch, verify the current persisted runId still matches.
After committing the batch, update the cursor and heartbeat conditionally on runId.
STOP processing if ownership changed. An old worker must never mark a replacement run complete or overwrite its cursor.
3. Do not permit stale-heartbeat takeover based only on age while the original process may still be alive.
Startup reconciliation may mark a running job interrupted because a process restart proves the old in-memory execution is gone.
For an ordinary POST:
- reject status === running with 409;
- do not automatically steal it merely because heartbeat is older than five minutes.
A separate operator recovery action may mark it interrupted after confirming the worker is no longer executing.
4. Make initial acquisition atomic when the progress row does not exist.
A conditional UPDATE does nothing when the system_settings row is absent.
Use the project’s canonical transaction/upsert/advisory-lock pattern so two first-ever requests cannot both create a running row.
Provide the exact SQL and affected-row semantics in the implementation plan.
5. Persist the complete run contract at start:
{
  runId,
  actorId,
  mode,
  eligibilityCutoff,
  status,
  totalEligible,
  processed,
  updated,
  skipped,
  errors,
  lastProcessedContactId,
  startedAt,
  lastHeartbeatAt
}
Resume must reuse the original mode and eligibility definition. It must not accept a different mode or recalculate a moving target population.
6. Correct re-score mode.
“archivedAt IS NULL” means every active contact, including contacts scored seconds ago.
That is an extremely broad full re-score, not merely a second mode.
Require:
- explicit preview,
- exact eligible count,
- typed confirmation,
- a separate action label such as “Re-score All Active Contacts,”
- stronger admin-only authorization unless manager access is explicitly approved.
7. Define cursor and eligibility semantics together.
The page query must use a stable predicate such as:
id > lastProcessedContactId
AND archivedAt IS NULL
AND lastScoredAt IS NULL
for backfill mode.
Persist any cutoff used by re-score mode at run creation so records do not enter or leave the population unpredictably during execution.
8. Prove the proposed bulk data access exists.
Provide file:line evidence or exact new storage methods for:
- contacts by IDs,
- deals grouped by contact IDs,
- email logs grouped by contact IDs,
- call logs grouped by contact IDs,
- enrollments grouped by contact IDs.
Each query must be bounded to the current page and must avoid SQL parameter limits.
9. Use a transaction per committed page.
The score writes and cursor/progress advance must have defined atomicity:
- Either all score rows for the page commit and the cursor advances;
- or neither commits.
Do not advance lastProcessedContactId when the batch update partially fails.
10. Do not use Promise.all of individual upserts.
That is still hundreds of writes per page.
Use a genuine set-based write:
- INSERT ... VALUES ... ON CONFLICT DO UPDATE,
- temporary/staging values joined into one UPDATE,
- or another repository-supported bulk operation.
11. Preserve scoring behavior exactly.
scoreContactPageBulk must reuse the same canonical score-input construction and calculateLeadScore logic as scoreContactBatchSafe.
Do not independently reconstruct scoring inputs in a way that can drift between single-contact scoring and mass scoring.
12. Define skipped and errors precisely.
“Contact not found” should normally be skipped.
A failed query or failed score write is an error.
Require:
processed = updated + skipped + errors
only if each eligible contact reaches exactly one terminal result. Otherwise adjust the accounting model and tests.
13. Sanitize audit errors.
Do not write raw database/provider error messages into audit details. Persist a bounded operator-safe error category; send full diagnostics only to canonical logging/Sentry.
14. Startup reconciliation belongs in the canonical startup reconciliation service.
Do not add another isolated startup mutation if Task 919 already establishes a startup reconciliation owner. Extend that owner with a separately scoped scoring reconciliation function.

Kill lines

STOP if an old run can write scores or progress after a replacement runId becomes active.
STOP if a five-minute heartbeat age alone permits automatic ownership takeover.
STOP if first-run acquisition is not atomic when the progress row is absent.
STOP if resume can change mode, eligibility criteria, or cutoff.
STOP if “Re-score mode” silently targets every active contact without an exact preview and typed confirmation.
STOP if progress advances outside the same committed batch boundary as score writes.
STOP if Promise.all performs one INSERT/UPDATE per contact.
STOP if bulk scoring duplicates or reimplements the canonical scoring algorithm.
STOP if startup reconciliation is added in a second unrelated startup location.
STOP if raw internal error details are written to audit logs or returned to the UI.

Validation

pnpm typecheck
pnpm lint

Required targeted tests:

- Two simultaneous first-ever POST requests create exactly one run.
- A second request during an active run returns 409.
- An old runId cannot update heartbeat, cursor, failure, or completion state.
- Worker stops when a conditional progress update reports lost ownership.
- Restart marks the old run interrupted and resume retains the original mode/cursor.
- Batch failure does not advance the cursor.
- Crash after score commit but before progress write is safely repeatable and does not corrupt counts.
- Bulk page scoring produces identical results to canonical single-contact scoring fixtures.
- Query count remains constant per 500-contact page, not proportional to contacts.
- No prospects, enrollment, GHL, email, or SMS mutations occur.
- Backfill reaches zero remaining lastScoredAt-null active contacts or reports explicit skips/errors.

Final status: NOT BUILD-READY

The key missing architecture is run ownership fencing. runId cannot be informational only—it must prevent an old or overlapping worker from mutating scores and job state after ownership changes.
