Part A — Document Vault bulk ZIP download CSRF

Required behavior

Authenticated bulk ZIP download must include the same CSRF header expected by other authenticated POST requests:

x-csrf-token

Preferred fix:

Use the existing shared authenticated request/helper pattern if one exists.

Do not hand-roll a second inconsistent CSRF system unless there is no shared helper.

Kill lines

STOP if the backend CSRF requirement is weakened, bypassed, or disabled.
STOP if the ZIP endpoint is changed from protected/authenticated to public.
STOP if the fix only works for one button but another bulk-download POST still omits x-csrf-token.
STOP if document ownership/role checks are changed or loosened.

⸻

Part B — Pipeline detail proposal retry

Required behavior

If proposal details fail to load inside the deal detail panel, the user must see:

Details unavailable
Retry

Retry must re-fire the failed proposal fetch, not just dismiss the warning.

The detail panel must not silently show stale/blank proposal data as if it loaded successfully.

Kill lines

STOP if a proposal-detail fetch failure has no retry affordance.
STOP if retry does not actually refetch proposal details.
STOP if stale proposal data is presented as current after a failed fetch.
STOP if this task changes proposal status/business rules.

⸻

Part C — Calendar bad-date warning actions

Required behavior

Each bad-date warning row must let an admin resolve the underlying bad event from the same card.

Allowed actions:

Edit event date/time
Delete event

The action must call the real calendar mutation route and clear the warning after success.

Do not make this a client-only dismiss.

Kill lines

STOP if bad-date rows can be dismissed without fixing/deleting the underlying event.
STOP if edit/delete bypasses existing auth/role checks.
STOP if the Calendar page still requires navigating elsewhere to fix a flagged bad-date event.
STOP if valid calendar events regress or disappear from normal date grouping.
