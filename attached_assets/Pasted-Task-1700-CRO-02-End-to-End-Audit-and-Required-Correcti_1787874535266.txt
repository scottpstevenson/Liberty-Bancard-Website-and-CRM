Executive verdict

NOT BUILD-READY AS WRITTEN.

The attached plan correctly identifies the repository's major CRO-02 defects. All 15 P0 findings, all 10 P1 findings, and all five P2 ownership boundaries remain materially supported by the current source, subject to the qualifications recorded below.

The proposed remedy, however, introduces or leaves unresolved eight cutover-level P0 risks:

It changes transactional_response from an intentional unknown-contact allowance to a production-graph requirement, which would block legitimate inbound confirmations for newly created contacts.

It requires new business-root graph enforcement while prohibiting reconstruction/backfill, so existing records would be quarantined immediately.

It has no compatibility rule for pre-CRO-02 historical events that possess only immutable record_class_at_event truth.

It overlooks BT-10's existing eligibility_snapshots authority and would create competing purpose-decision snapshots.

Its graph-generation requirement is not executable as specified for cross-subject dependencies, redirects, mappings, and merges.

Its typed-evidence requirement does not freeze a concrete schema and its blanket source-event immutability conflicts with canonical intake replay.

It does not choose one canonical organization/link/relationship writer or define the disposition of existing heuristic relationship rows.

It declares an agent object-scope rule that is not consistently authoritative in the repository and is incomplete for unowned businesses.

Task #1700 may safely proceed only after the implementation contract is replaced with the corrected phased contract in this report. The safe code-side tranche can build additive schema, shadow resolution, command/import fencing, authority consolidation, tests, and a runbook. Enforcement cutover, historical reconstruction, production classification, and live operations remain separate authorizations.

New P0 corrections required before build

P0-A — Preserve legitimate inbound transactional responses

The plan's matrix requires a production commercial graph for every transactional response. That contradicts BT-06 and would deny newly created unknown contacts before they can receive the confirmation that acknowledges their inbound form, statement, application, booking, callback, support, or equipment request.

The repository has many trusted transactional call sites, including public forms, GHL workflow enrollment, SMTP/GHL transports, statement/proposal flows, booking reminders, merchant status messages, and chat replies. One coarse purpose is no longer sufficient.

P0-B — Separate shadow build from enforcement cutover

Adding businesses.record_class DEFAULT 'unknown', new reviewed link/mapping facts, and graph snapshots while forbidding reconstruction means existing production records will lack the new dependencies. Migrating all safety-critical consumers to enforce the new resolver in the same release would zero reports, block payouts/pre-spend, and quarantine current workflows by construction.

Required phased rollout:

Additive/shadow: add schema, authorities, resolvers, indexes, and tests. Existing consumers remain authoritative. New resolver runs read-only in shadow and records aggregate comparisons only.

Dual-read comparison: compare legacy and CRO-02 decisions by purpose at a frozen data high-water mark. No changed business behavior.

Separately authorized reconstruction: owner-approved, bounded, restart-safe dry run and reconstruction; no inference or promotion without evidence.

Purpose-by-purpose enforcement: enable only after exact-SHA deployment, coverage thresholds, discrepancy review, rollback proof, and explicit authorization.

The build must default to shadow mode. Startup must refuse enforcement when required policy version, schema version, coverage high-water mark, or rollback marker is absent.

P0-C — Define pre-CRO-02 historical compatibility

Pre-CRO-02 events cannot reference a snapshot that did not exist. The task cannot both require every historical reader to have a new snapshot and prohibit historical reconstruction.

Required contract:

Freeze a cutover timestamp, release SHA, and policy version.

For pre-cutover outbound_send_log and statement_upload_commands, preserve immutable record_class_at_event as legacy_class_snapshot_v1.

Missing CRO-02 snapshot on a pre-cutover row is a known legacy state, not a dangling-runtime defect.

Never convert legacy unknown to production or synthesize evidence.

New post-cutover events must atomically reference a CRO-02 resolution snapshot and must agree with record_class_at_event while that compatibility column remains.

Historical aggregate output must expose legacy/unknown coverage separately.

P0-E — Freeze an executable graph-generation algorithm

A single per-subject integer cannot prove freshness when a decision depends on multiple roots and edges. A contact decision can become stale when a business, company mapping, redirect, identity observation, link review, or relationship review changes.

Required algorithm:

Give every typed root and every authority edge a monotonic revision.

Bump both endpoints for two-ended link/mapping/relationship changes in the same transaction.

Redirect/merge mutations bump requested, deprecated, and survivor dependency revisions as applicable.

A snapshot stores a sorted dependency vector of {typed object, object ID, revision, authority version} and its canonical SHA-256 fingerprint.

Revalidation locks and rereads every dependency in one documented order.

The current fingerprint must exactly equal the preview fingerprint before approval/execution.

New dependency phantoms must be prevented by advisory/key-range locks or detected by a deterministic membership revision.

Missing rows, zero required edges, cycles, depth overflow, or dependency drift quarantine.

The schema, lock order, membership rule, and canonical serialization must be frozen before implementation begins.

P0-F — Freeze typed evidence and preserve intake replay

The plan requests “exactly one typed FK” without enumerating legal evidence kinds or columns. It also says referenced source events cannot be updated, while writeContact legitimately updates only last_seen_at during idempotent replay.

Required contract:

Define one checked evidence-kind enum and one nullable FK per supported authority row.

Enforce num_nonnulls(...) = 1 at the database layer.

Initially support only explicitly required kinds: classification event, contact source event, import row disposition, identity observation, merge operation/redirect, business-link decision, legacy-company mapping decision, and relationship review.

Validate same-subject/effective-subject compatibility in the authority transaction.

Reference immutable authority facts; do not copy source payloads.

For contact_source_events, freeze authority-bearing fields but continue to allow last_seen_at replay updates, or reference a separate immutable evidence assertion/hash.

Use ON DELETE RESTRICT or an approved tombstone/retention mechanism for referenced evidence.

Do not place raw emails, phones, names, source payloads, identity tokens, or protected values in snapshots or logs.

P0-G — Choose one organization/link/relationship authority

“Existing organization resolver/business-ingest authority” is ambiguous because the resolver and SDR ingest path own different writes today.

Required ownership:

organization-resolver.ts owns organization identity match/create and strong identity fields.

A single organization service wraps it and owns allowed descriptive projections with a checked field-ownership matrix.

sdr/dedupe.ts, CSV, orchestration, storage, and routes become callers/adapters; they may not update organization identity or contacts.business_id directly.

Append-only contact_business_link_decisions owns link truth; contacts.business_id is a projection updated in the same transaction.

Existing entity_relationships rows are heuristic candidates only. They never authorize decision-maker state or commercial eligibility.

A new reviewed business-scoped relationship history owns decision-maker truth; compatibility fields are projections.

Legacy company-to-business mapping is reviewed and append-only; no name/domain/phone-only automatic mapping.

The field-ownership matrix and exact adapter list must be part of the build contract.

P0-H — Freeze one object-scope policy

Single tenancy does not imply that every agent can inspect every graph object. Conversely, revenue-specific ownership code is not automatically the global CRM policy.

Required policy:

Admin/manager: global read; sensitive authority mutations remain role- and dual-control-gated.

Agent contact/deal access: reuse the shared CRM object-access predicate, including the chosen unassigned behavior.

Agent business access: only if an authorized contact or deal links to that business. Unlinked businesses are admin/manager-only.

Classification, mapping, business-link review, and relationship review: admin/manager or stricter task-specific role; an agent may submit a candidate only if explicitly allowed.

Lists, counts, detail, child resources, and errors apply scope before fetching/aggregating and use the same non-enumerating 404 convention.

Raw authority graph/evidence remains unavailable to general dashboard roles; expose only safe aggregate/review projections.

Update the shared object-access authority rather than duplicating SQL ownership rules across routes.
