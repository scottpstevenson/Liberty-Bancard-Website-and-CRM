Verdict: NOT BUILD-READY

The missing downstream trigger is plausible, but this plan reintroduces two problems already rejected elsewhere: unmanaged fire-and-forget work and trusting inbound GHL compliance fields that the sync contract intentionally does not own.

Critical corrections

1. Do not fire scoreContact() as an unmanaged promise

This:

scoreContact(contact.id).catch(() => {});

can be lost on restart and hides failures completely.

Also verify the correct owner: scoreContact() belongs to the behavioral lead-scoring service, not contact-readiness.ts. Readiness recalculation and behavioral scoring are separate systems.

Use the existing durable scoring job if one exists. If none exists, this task needs a preflight identifying the canonical scoring execution path before adding another detached promise.

2. Do not fire enqueuePromotionalEnrollment() as fire-and-forget

The enqueue function itself may be durable, but the act of calling it can still fail before it writes the durable DB row.

At minimum:

* await enqueuePromotionalEnrollment(...) after the contact transaction has committed;
* catch and record the canonical deferred/queue-unavailable outcome;
* do not block or roll back valid contact creation because enrollment enqueue fails.

The sync operation can still complete successfully while reporting the downstream enqueue outcome separately.

3. Do not trust inbound GHL compliance fields for the skip guard

The plan says to skip based on:

doNotContact
doNotAutoContact
emailStatus

from the GHL payload.

Those fields are explicitly Replit-owned and stripped from inbound GHL updates. They must not become authoritative merely because they appear in the provider payload.

The durable promotional-enrollment worker already re-reads current persisted contact state and runs the canonical eligibility/contactability gate. That is the correct authority.

Therefore:

* do not add a payload-based pre-enqueue compliance guard;
* optionally avoid enqueue only when the persisted contact is conclusively ineligible, but this is mostly redundant;
* the worker must remain authoritative.

4. Clarify that campaign eligibility is not controlled by enrollment

This statement is inaccurate:

Bypasses the durable promotional enrollment gate — is immediately campaign-eligible with zero verification.

Campaign audience eligibility is controlled by readiness targeting plus evaluateContactability() in the campaign preview/queue/send path. Promotional sequence enrollment is a separate workflow.

The actual gap is:

New GHL contacts do not receive the expected behavioral-scoring trigger or promotional-enrollment evaluation event.

Do not conflate those systems.

5. Use a stable source-event identity

The enrollment request needs the durable provenance/source event created by Task #973, not merely:

sourceEvent: "ghl_sync"

That value is shared by every GHL contact and cannot support idempotency.

Use something like:

sourceEventId: contactSourceEvent.id

or the canonical event key associated with the exact inbound GHL event.

The enrollment job’s idempotency must distinguish:

* replay of the same GHL event;
* a genuinely new GHL event for the same contact;
* existing sequence enrollment.

6. Trigger only on genuine creation

The race-recovery path may return an existing contact after another concurrent request wins. It must not blindly emit another “contact created” event.

writeContact() or syncContactFromGhl() should return an explicit result:

{
  contact,
  created: boolean,
  sourceEventId
}

Only created: true should trigger new-contact scoring and promotional enrollment.

If the race loser resolves an already-created contact, it should not create a second scoring/enrollment job for the same creation event.

Corrected implementation scope

1. Verify the canonical behavioral-scoring execution mechanism.
   - If a durable scoring queue/job exists, enqueue it.
   - Do not add scoreContact(...).catch(() => {}).
   - Do not confuse lead scoring with readiness recalculation.
2. Make the GHL writer/sync return:
   { contact, created, sourceEventId/eventKey }.
3. After a successfully committed new-contact creation:
   - enqueue behavioral scoring through the canonical durable path;
   - await enqueuePromotionalEnrollment() so the durable DB job row is confirmed;
   - pass the exact GHL provenance/source-event identity.
4. If enrollment enqueue reports queue unavailable:
   - preserve the deferred durable row;
   - allow GHL sync to succeed;
   - record the outcome through existing job/audit observability.
5. Do not inspect inbound GHL doNotContact, consent, or email-status fields as
   authoritative enrollment gates.
   The worker re-reads persisted state and evaluates current eligibility.
6. Existing-contact updates and 23505 race recovery must not emit duplicate
   contact-created downstream events.

Smoke-test corrections

The proposed test also needs adjustment:

* Do not require leadScore to become non-null within five seconds unless the verified canonical scoring worker has a deterministic test harness. Wall-clock polling against a shared worker is flaky.
* Do not use a GHL payload’s doNotContact: true as the reason no job is created. The canonical behavior should generally be: job created, worker evaluates persisted state, result becomes blocked.
* Do not assert updateSyncStatusRecord() through audit_logs unless that function is proven to write there. Assert the actual sync-status table or mock the function directly.
* “No immediate sequence enrollment” should be checked before the durable worker executes, or with worker processing paused; otherwise it races the test.

Required tests

- Genuine new GHL contact returns created=true and a durable source event.
- Exactly one promotional_enrollment_jobs row is written for that source event.
- Same GHL event replay does not create another logical enrollment job.
- Concurrent creation race produces one contact and one new-contact downstream event.
- Existing-contact GHL update does not trigger contact_created enrollment.
- Queue unavailable produces a durable deferred job, not lost in-memory work.
- Persisted DNC/opt-out contact is evaluated as blocked by the worker.
- Spoofed inbound GHL compliance fields do not override persisted contact state.
- No immediate direct autoEnrollFromTrigger call occurs in ghl-sync.ts.
- Behavioral scoring uses the verified canonical execution owner.

Kill lines

* STOP if either scoring or enrollment is launched with .catch(() => {}).
* STOP if inbound GHL compliance fields are treated as canonical eligibility state.
* STOP if sourceEvent: "ghl_sync" is used as a global idempotency identity.
* STOP if a race-recovered existing contact emits another contact_created event.
* STOP if campaign eligibility and promotional sequence enrollment are treated as the same gate.
* STOP if the test relies on arbitrary five-second worker timing.
* STOP if a valid contact creation is rolled back because downstream enrollment or scoring is unavailable.

Final status: NOT BUILD-READY. The task should be rewritten as durable post-create triggers for genuinely new GHL contacts, using the exact source-event identity and canonical scoring/enrollment owners.
