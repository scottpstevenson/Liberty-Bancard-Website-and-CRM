# LIBERTY BANCARD — PREFLIGHT + BUILD MODE

## MODE

PREFLIGHT + BUILD. Verify current code and data ownership, correct the task, and implement in the same run when safe. Stop only for a false finding, wrong owner, missing prerequisite, unavailable evidence needed for safe merge behavior, necessary scope split, or kill line. Do not use `db push`, weaken tests, auto-merge production duplicates, redesign unrelated systems or create a second identity authority.

Required sequence: baseline → VFC → searches → root cause → ownership → blast radius → schema/auth/concurrency/external checks → verdict → corrected plan → kill lines → implementation → tests/gates → post-build searches → diff → final VFC → merge verdict.

## 1. REPOSITORY BASELINE

Capture branch, HEAD SHA, working tree and migration head. Identify unrelated modifications and preserve them. Record the exact starting state.

## 2. VERIFIED FROM CODE — PREFLIGHT

Create:

| ID | Task Claim | Verdict | Verified Reality | Evidence |

Trace every merge/dedupe caller and all relationship consumers.

## 3. REQUIRED SEARCH / GREP CHECKS

Search and inspect:

- email/phone normalization utilities and versions;
- duplicate email/phone reports, candidates and constraints;
- `mergeContact`, dedupe, redirect, alias, canonical-contact and survivor logic;
- every `contact_id`, contact FK, polymorphic entity reference and denormalized contact field;
- consent, suppression, DNC, email/SMS status and GHL identifiers;
- `writeContact`, direct contact inserts/updates and import/enrichment writers;
- shared/business phone classification and phone types;
- merge audit/history/undo and operator routes/UI;
- relevant migrations and tests.

Grep is inventory, not proof. Inspect transaction boundaries and FK behavior.

## 4. VERIFIED ROOT CAUSE

Compare original assumption with current implementation. State whether identity normalization is absent, partial or inconsistent; whether shared business phones are being treated as people; and whether an existing merge path is complete/reversible. Document outdated assumptions in a correction table.

## 5. SOURCE-OF-TRUTH CHECK

Identify canonical contact identity owner, normalization owner, merge mutation owner, consent owner, organization authority and audit owner. BT-04 owns consent semantics; BT-06 owns classification; BT-08 owns canonical intake/provenance. This task must integrate those owners rather than duplicate them.

- complete contact relationship inventory;
- merge proposals and dry runs;
- operator decision, field arbitration, redirects and undo ledger;

### Out of scope

- general import/provenance writer migration (BT-08);
- organization consolidation beyond identity references (BT-08);

- unrelated CRM UI redesign (BT-11).

List exact expected/untouched files after preflight.

## 7. DATA / SCHEMA CHECK

Verify columns/types/nullability/defaults/constraints/indexes/FKs/archive behavior for contacts and every dependent table. Determine whether observations, candidates, decisions, redirects and undo operations need new tables. Any uniqueness rule must account for normalization version, nulls, phone ownership and shared business endpoints.

Use the next valid Drizzle migration and journal entry; prove clean replay. Do not add a unique constraint until collision inventory and compatibility behavior are proven. Do not backfill or merge production records unless explicitly required and evidence-approved.

## 8. AUTHORIZATION CHECK

Produce a role matrix for viewing candidates, previewing a merge, approving/rejecting, executing, undoing and exporting evidence. Merge/undo must be admin or specifically verified data-steward authority, role-gated server-side and audited. UI hiding is not authorization.

## 9. CONCURRENCY / IDEMPOTENCY CHECK

Required. Check concurrent proposals, simultaneous merges of overlapping contact sets, retries, stale previews, contact mutations during execution, crash recovery and undo. Require locking/version checks, stable operation IDs, one canonical survivor, deterministic replay and transactional local relationship transfer. A retry must not re-transfer or duplicate side effects.

## 10. EXTERNAL SIDE-EFFECT CHECK

Treat GHL/local identity as distributed. Inventory whether merging updates GHL or any external provider. Prefer no external mutation in the local merge transaction unless an existing durable reconciliation owner requires it. Document DB transaction → durable reconciliation intent → provider call → result/audit ordering and partial failure behavior.

## 11. PREFLIGHT VERDICT

Choose BUILD-READY, BUILD-READY WITH CORRECTIONS, PREFLIGHT REQUIRED, NOT BUILD-READY, NOT NEW TASK or WATCH. Continue immediately if build-ready. If full production merge execution is unsafe without data evidence, build the proposal/dry-run/ledger/guardrails and mark only the operational execution as runtime pending rather than stopping everything.

## 12. CORRECTED BUILD PLAN

State corrected root cause, exact outcomes and file-specific steps. Separate normalization, candidate generation, reviewed merge execution and undo. Identify any prerequisite from BT-04/BT-06 that is not actually present.

## 13. KILL LINES

- KILL LINE: If two concurrent or replayed merge operations can produce data loss, split authority, duplicated relationships or an irreversible wrong survivor, the task has FAILED.
- STOP if shared business phone numbers are treated as unique person identity.
- STOP if consent/suppression becomes less restrictive or loses evidence.
- STOP if any FK/side table is silently orphaned or discarded.
- STOP if production contacts are automatically merged without review.
- STOP if undo is advertised but cannot deterministically restore local state.
- STOP if the canonical contact writer/identity owner is bypassed.

## 14. IMPLEMENTATION RULES

Smallest safe diff, existing patterns, transactions and constraints. No unrelated cleanup or bulk dedupe. Preserve records and evidence. Prefer proposals and compatibility redirects over destructive rewrites. Update the plan if current architecture differs.

## 15. TEST REQUIREMENTS

Cover normalization versions, null/invalid identities, shared phones, duplicate candidates, false positives, all-FK transfer, consent preservation, GHL-ID conflicts, replay, concurrency, stale preview rejection, authorization, rollback/crash behavior and undo. Tests must exercise the production merge service and real schema relations with isolated fixtures.

## 16. SMOKE / INTEGRATION TEST

Extend the canonical identity suite or create `scripts/test-bt07-canonical-identity-merge.ts`. Prove:

1. normalized duplicates form a proposal without auto-merging;
2. shared business phones do not merge people;
3. authorized reviewed merge transfers every inventoried relationship once;
4. blocked/unauthorized/stale execution causes no mutation;
5. consent remains safe;
6. retry is idempotent;
7. undo restores deterministic local state;
8. dry-run counts reconcile.

## 17. POST-BUILD GREP CHECKS

Prove no legacy automatic merge bypass remains, every relationship is handled or explicitly retained, normalization callers use one versioned owner, no unsafe unique-person assumption remains for phone, and all API/UI consumers understand redirects and operation status.

## 18. REQUIRED GATES

Run targeted identity/merge tests, contact/import/consent/GHL-adjacent tests, typecheck, build, migration replay, RBAC/contract tests, invariant/pre-deploy suites and `git diff --check`. Report actual commands.

## 19. DIFF REVIEW

Run `git status`, `git diff --stat` and `git diff`. Confirm intended files only, no data dumps, debug output, unrelated formatting, lockfile or config mutation, and no production merge execution artifact.

## 20. FINAL VFC TABLE

Produce:

|---|---|---|---|---|

Map every Done Looks Like requirement and kill line.

## 21. FINAL RESPONSE FORMAT

Return: VERDICT (COMPLETE / VERIFIED, PARTIALLY COMPLETE or DO NOT MERGE); Repository State (starting SHA, ending SHA/working tree, migration head); Verified Root Cause; Preflight Corrections; Implementation (`file:line`); Tests/Gates; Grep Verification; Kill-Line Verification; Runtime Verification; Remaining Risks; and Final Status (SAFE TO MERGE, SAFE TO MERGE — RUNTIME VERIFICATION PENDING or DO NOT MERGE). Never label a dry run as a completed production merge.

## LIBERTY-SPECIFIC SAFETY RULES

- Contact identity is evidence-based and versioned.
- Consent is channel-specific and cannot be inferred from identity.
- Classification, readiness and lead score are distinct from identity.
- GHL/local changes are distributed state.
- No `db push`; proper migrations only.

## PRACTICAL REVIEW STANDARD

Block realistic wrong-person merges, consent loss, relationship loss, concurrency duplication, unauthorized decisions or irreversible state. Do not block safe proposal/dry-run infrastructure because future probabilistic matching could be more sophisticated.

# TASK TO PREFLIGHT + BUILD

## BT-07 — Canonical Identity & Reversible Merge System

**Primary findings:** `DAT-02`, `DAT-03`, `DAT-11`

**Dependencies:** BT-06 classification; BT-04 consent model

### What & Why

Email and phone identity are not consistently normalized or evidence-versioned, duplicate/shared-phone groups are ambiguous, and merge behavior lacks proven all-relationship transfer and deterministic undo. Unsafe dedupe can combine different people or discard consent, activity and commercial history.

### Done Looks Like

- Normalized email/phone observations retain normalization version and source.
- Phone type, ownership and shared business endpoints are modeled before uniqueness.
- Every contact FK and side table has an explicit merge disposition.
- Candidate generation is separate from human decision and execution.
- Field arbitration and consent preservation are explainable.
- Merges are transactional, replay-safe and reversible through redirects/undo ledger.
- No production automatic merge occurs.

### Out of Scope

- Unreviewed bulk production merges.
- Canonical import/provenance migration.
- Provider enrichment or CRM navigation redesign.

### Proposed Implementation Steps

1. Inventory normalization and all contact relationships.
2. Define/extend canonical observation and merge-operation schema.
3. Add collision-safe migrations and indexes.
4. Implement candidate/dry-run generation.
5. Implement authorized reviewed transaction with locking/idempotency.
6. Add redirects and deterministic undo.
7. Add operator/API contracts and production-path tests.

### Relevant Files and Areas to Verify

- `shared/schema.ts`, migrations and journal
- contact storage/writers/normalizers/dedupe services
- consent/suppression and GHL identity services
- all tables referencing contacts or contact identity
- merge/review/audit routes and UI
- import/enrichment callers and tests

### Existing Kill Line

KILL LINE: No merge may lose relationships, weaken consent, conflate shared-business-phone contacts or become irreversible.

## FINAL DIRECTIVE

Verify the complete relationship graph before implementation. Build the safe identity, proposal, transaction and undo path in this run; never convert uncertainty into an automatic production merge.
