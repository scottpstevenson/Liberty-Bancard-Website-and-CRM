BUILD-READY WITH REQUIRED CORRECTIONS — Task #1022 / 991B-0

Proceed with the schema-only prerequisite, with these changes:

1. Do not expose provenance fields through public insert/update schemas

These fields represent classification authority and must be server-owned:

* verticalSource
* verticalConfidence
* manualVerticalOverride

Do not automatically expose them through insertContactSchema or any public contact create/update schema.

Specifically audit and omit them from:

* insertContactSchema
* contact PUT/PATCH schemas
* bulk contact update schemas
* any generic client-facing Drizzle/Zod schema

A dashboard or public client must not be able to claim:

{
  "verticalSource": "operator",
  "verticalConfidence": 100,
  "manualVerticalOverride": true
}

Create internal server-only types later for 991B-1.

Apply the same protection to any client-facing SDR merchant or lead-state schemas.

2. Fix the nullable/default contradiction

The brief says:

* all fields are nullable;
* existing rows should remain NULL;
* manualVerticalOverride has default false.

A default of false means future inserts that omit the field receive false, while historical rows remain null after ADD COLUMN ... DEFAULT false behavior depends on the exact migration and PostgreSQL version.

Use one explicit contract:

Recommended:

vertical_source           NULL
vertical_confidence       NULL
manual_vertical_override  NULL

Meaning:

* NULL = provenance not established;
* false = explicitly evaluated and not manually overridden;
* true = confirmed manual override.

Do not default to false in this schema-only phase. Let 991B-1 assign explicit values when a writer actually establishes provenance.

3. Add a database range constraint for confidence

verticalConfidence must not accept arbitrary values such as -5 or 900.

Add a check constraint to each table:

CHECK (
  vertical_confidence IS NULL
  OR vertical_confidence BETWEEN 0 AND 100
)

Reflect the same rule in server-internal validation when 991B-1 is implemented.

4. Define source vocabulary now, even though no writer uses it yet

Add a shared server-safe constant/type for the planned source values, for example:

export const VERTICAL_SOURCES = [
  "operator_override",
  "discovery_enrichment",
  "import_classification",
  "website_form",
  "ghl_sync",
  "legacy_unknown",
] as const;

The exact vocabulary must match the upcoming resolver contract.

Do not add a DB CHECK on verticalSource yet unless the list is fully approved and migration-safe. However, do not leave the intended values undocumented.

5. Keep coarse and fine-grained provenance distinct

sdrMerchants has both:

* vertical
* subvertical

A single verticalSource and verticalConfidence pair may be ambiguous if the coarse vertical and fine-grained subvertical came from different sources.

Before finalizing the schema, choose one of these contracts:

Preferred:

vertical_source
vertical_confidence
subvertical_source
subvertical_confidence
manual_vertical_override

Or explicitly document that verticalSource and verticalConfidence describe the complete resolved classification pair and that vertical and subvertical must always be written together by 991B-1.

Do not leave the meaning ambiguous.

6. Confirm whether sdrLeadState needs manualVerticalOverride

Manual authority may belong canonically to the contact or merchant record, while sdrLeadState stores the resolved projection.

A safer lead-state schema may be:

vertical_source
vertical_confidence
vertical_resolution_reason

rather than allowing a second independent manual-override flag that could drift from the contact.

If the same three columns remain on all tables, document which table owns the override and which tables merely copy its resolved metadata.

7. Use a versioned migration only

The migration must:

* use the next valid migration number;
* be added to the Drizzle journal;
* use a when value above the current high-water mark;
* add columns and confidence constraints only;
* contain no backfill or resolver behavior;
* avoid db push.

After applying, verify the exact definitions through information_schema and pg_constraint.
