SECTION 1: EXECUTIVE SUMMARY
================================================================================

What the App Does:
Liberty Bancard is an AI-powered merchant payment processing acquisition
platform. It combines a public marketing website (SEO-optimized for merchant
services), a full CRM for sales pipeline management, and an autonomous AI SDR
(Sales Development Representative) engine designed to find, score, contact, and
convert merchants into payment processing customers — targeting zero manual
intervention.

Main User Types:
  - Admin:      1 (scott@libertybancard.com) — Full system access
  - Manager:    0 — Dashboard access, agent management
  - Agent:      0 — Own pipeline, contacts, tasks
  - Affiliate:  0 — Referral program, commission tracking
  - Merchant:  18 — Merchant portal, self-service, statement uploads

Core Flows:
  1. Lead Acquisition: Sunbiz scraping -> Outscraper/Apify/Serper discovery ->
     CSV import -> enrichment -> scoring -> SDR pipeline
  2. Autonomous Outreach: SDR orchestrator sweep (5 min) -> email -> SMS ->
     Voice AI (Rachel) -> channel escalation
  3. Conversion Pipeline: Reply classification -> meeting booking -> statement
     collection -> AI proposal generation -> human handoff -> close
  4. Merchant Onboarding: Application wizard -> e-signature -> equipment order
     -> go-live tracking
  5. Public Conversion: Marketing pages -> cost quiz -> savings calculator ->
     statement upload -> contact creation

Current Maturity Level:
INFRASTRUCTURE: 95% BUILT. ACTIVATION: 0%. The entire autonomous SDR pipeline,
CRM, website, analytics, compliance, and AI intelligence layers are coded and
deployed. However, no leads have been bridged into the SDR pipeline (0 SDR
merchants, 0 businesses records), GHL credentials are not configured, and the
orchestrator has never run a live sweep. The system is a fully assembled machine
that has not been turned on.

5.6  TECHNICAL DEBT

1. storage.ts (2,801 lines) — Single file handles all CRUD for 79 tables.
   Should be split into domain-specific storage modules.

2. schema.ts (2,597 lines) — All 79 table definitions in one file.
   Could be organized into domain modules.

3. Dual lead systems — Old prospect/contact system and new SDR
   merchant/business system coexist with overlapping data models.
   No clear migration/deprecation path.

4. Legacy Sunbiz services — sunbiz-scraper.ts (1,014 lines),
   sunbiz-enrichment.ts (1,496 lines), sunbiz-cron.ts, daily-outreach.ts
   (792 lines) feed the OLD prospect system, not the new SDR pipeline.

5. Multiple outreach engines — Old campaign-engine.ts + sequence-worker.ts
   + daily-outreach.ts coexist alongside the new SDR orchestrator.ts.
   Risk of conflicting sends when both systems are active.

6. No Redis/caching — All state in PostgreSQL, including sessions.
   May need caching for large dataset queries at scale.
