Verdict: NOT BUILD-READY

The intent is correct, but this task conflates primary source labeling, append-only provenance, batch rollback, and operator UI. Adding two mutable columns does not make records traceable or reversible.

Corrections to send back

1. Do not make contacts.sourceCategory the complete provenance system.
A contact can arrive through multiple sources over time:
- CSV import
- later GHL sync
- later website form
- manual update
- discovery bridge
A single mutable sourceCategory can only represent one value and will erase history.
Use:
A. contacts.primarySourceCategory
   - immutable first-known origin, or explicitly governed canonical origin
B. append-only contact_source_events table
   - contactId
   - sourceCategory
   - sourceExternalId
   - importBatchId
   - sourceRecordId / sourceRowNumber
   - firstSeenAt
   - lastSeenAt
   - actorType / actorId
   - metadata
   - createdAt
Every intake event appends or idempotently upserts provenance without overwriting the
contact’s historical origin.
2. Do not require importBatchId on single-record create paths.
website_form, manual_crm, and individual GHL sync events do not naturally belong to an
import batch.
Required rule:
- importBatchId required for bulk/import executions
- nullable for genuine single-record events
- sourceEventId or sourceExternalId required where no batch exists
Do not fabricate meaningless batch UUIDs for manual or form creation.
3. Verify ProspectList identity type.
The plan says:
prospects.importBatchId = ProspectList UUID
Confirm whether ProspectList.id is actually a UUID. If it is an integer FK, do not
mislabel it as a UUID.
Prefer a dedicated import_executions UUID referenced by:
- prospect list
- prospect rows
- Sunbiz rows
- rollback manifest
Do not overload listId and importBatchId with unclear duplicate meanings.
4. Define source categories from actual ownership, not a closed incomplete enum.
The proposed values omit or blur sources such as:
- direct GHL inbound
- statement upload
- callback form
- support form
- registry import
- Apollo
- Outscraper
- Apify
- Sunbiz / COREVT
- partner/referral intake
- API integration
Use a stable canonical taxonomy with:
- broad sourceCategory
- specific sourceType
Example:
sourceCategory = "website_form"
sourceType = "statement_upload"
sourceCategory = "discovery"
sourceType = "apollo"
Do not force unrelated sources into discovery_bridge or csv_import.
5. Do not expose provenance columns through unrestricted public Zod schemas.
The server must assign provenance from the authenticated route/intake owner.
Clients must not be allowed to submit:
{
  sourceCategory: "website_form",
  importBatchId: "..."
}
and forge origin history.
Public create/update schemas must omit protected provenance fields.
Use server-internal input types only.
6. Define immutability and update ownership.
Once primarySourceCategory is set:
- ordinary updates must not change it;
- GHL inbound must not overwrite it;
- manual operators need a dedicated audited correction action if correction is allowed.
importBatchId on an existing record must not be reassigned by later sources.
Later source arrivals create provenance events instead.
7. Batch rollback requires a manifest, not only importBatchId.
A batch detail panel must distinguish:
- inserted records
- updated existing records
- skipped duplicates
- conflicts
- invalid rows
- rows later modified by another source
- rows already promoted or enrolled
Rollback must never blindly delete every row with importBatchId.
The import execution must persist per-row action and prior state where updates are
reversible.
8. Split schema/provenance from UI.
This task is too broad as written.
Recommended split:

973B — Intake-Path Adoption
973C — Batch Detail and Safe Rollback UI

Do not build dashboard/document-index UI before the provenance model is correct and

9. Define historical backfill policy.
Existing 154K+ contacts will have missing origin data.
Before enforcing NOT NULL:

- assign only evidence-backed categories;
- use "legacy_unknown" for unresolved rows;
- record inference method and confidence;
- do not guess based only on tags when ambiguous.
Use expand → backfill → verify → constrain deployment order.
10. Add DB-level provenance idempotency.
Repeated ingestion of the same source event must not append duplicate provenance rows.
Define a unique identity such as:
(contact_id, source_category, source_type, source_external_id)
or:
(import_batch_id, source_row_fingerprint)
Use a targeted unique index and conflict-safe insert.
11. Preserve compliance audit meaning.
Provenance explains where data came from; it does not itself prove consent.
Do not treat sourceCategory as evidence that:

Consent and contactability remain separate canonical records.
