CONFIRMED CODE — Apollo: executeSfpApolloDiscovery calls performApolloSearch. That searches organizations and /mixed_people/api_search, returning people and personIds. The SFP waterfall then looks for person.ownerEmail/person.email. It never calls the existing people-reveal function in this path. Apollo documents that People API Search returns no email addresses or phone numbers; actual enrichment must follow the search. Consequently, this SFP path cannot normally obtain named emails from search, even when it obtains organization data and reports provider success.

CONFIRMED CODE — Apollo contract: apolloCreditReceipt recognizes selected integer-only headers and credits_used/credit_cost aliases; absent recognized fields produce unknown certainty. performApolloSearch converts a successful HTTP response with unknown certainty into outcome ambiguous before accepting search results. Current Apollo bulk-enrichment documentation describes credits_consumed and permits fractional values; the existing parser does not handle that contract. Search-result acceptance and business identity must not depend on invented billing fields. Verify the live contract, record known/unknown usage truthfully, and keep unknown cost separate from ambiguous identity. This is a concrete adapter risk; its production incidence is unmeasured.

CONFIRMED CODE — Apollo targeting: the people search submits organization_ids, page 1 and per_page. It does not submit owner/manager title or seniority filters; ranking occurs after retrieval. A large company can return less relevant people while the best decision makers remain beyond the first page. The organization lookup also adds city/state filters; validate their meaning and avoid excluding an in-scope operating branch solely because its headquarters is elsewhere.

Adding an enrichment flag alone is insufficient: parse the actual returned email objects, person names, titles and source evidence.
