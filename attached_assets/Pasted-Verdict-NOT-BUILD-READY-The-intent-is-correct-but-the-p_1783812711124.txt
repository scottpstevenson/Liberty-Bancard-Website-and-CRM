Verdict: NOT BUILD-READY

The intent is correct, but the proposed dedupe rules are too weak and still race-prone.

“Check existing rows, then bulk insert” does not make either importer idempotent under concurrent uploads. Email/phone also cannot safely act as universal prospect identity without normalization and collision rules.

Corrections to send back

1. Add file-level import identity first.
Before parsing or inserting, compute a deterministic fingerprint from the original
uploaded file bytes, for example SHA-256.
Persist an import execution record containing:
- importType: prospect_csv | sunbiz_corevt
- fileHash
- originalFileName
- fileSize
- status: pending | running | complete | failed
- totalRows
- insertedRows
- skippedWithinFile
- skippedExisting
- conflictRows
- startedAt
- completedAt
- actor
Enforce one completed/running import per importType + fileHash at the database level.
A repeated identical upload should return the existing import result rather than
creating another ProspectList and reparsing/reinserting everything.
2. Separate file replay protection from row deduplication.
These are different guarantees:
- Same file uploaded again:
  detect by fileHash and return the prior result.
- Different file containing previously seen records:
  apply row-level identity and conflict rules.
Both are required.
3. Normalize identifiers centrally.
Prospect email:
- trim
- lowercase
- blank → null
- use the same normalization as the canonical contact/prospect lookup
Phone:
- normalize to canonical E.164 when possible
- invalid/ambiguous phone → not a safe dedupe key
Do not implement new normalization logic directly in the route.
4. Do not silently deduplicate all prospects by phone.
Shared office numbers, call centers, franchises, and household numbers can represent
multiple legitimate people or companies.
Required prospect outcomes should be:
- exact_duplicate
- inserted
- possible_match_review
- invalid_identity
- duplicate_within_file
Recommended identity:
A. normalized email exact match → duplicate candidate
B. no email + normalized phone plus compatible company/name evidence → duplicate
C. phone-only match without corroboration → possible_match_review, not silent skip
5. Deduplicate inside the incoming file before querying the database.
For every upload:
- normalize rows
- group by canonical row identity
- retain deterministic winner or mark conflicts
- report duplicateWithinFile separately
Do not send thousands of repeated identifiers into database lookups.
6. Use batch queries, not per-row existence checks.
For each chunk:
- collect normalized emails
- collect normalized phones
- query existing records in bulk
- build Maps/Sets for matching
- insert only approved rows in bounded batches
No N+1 SELECT loop across 10K–100K rows.
7. Make row insertion conflict-safe at the database boundary.
Application pre-checks alone are race-prone.
For any identity treated as authoritative, enforce it with:
- an applicable unique index, and
- INSERT ... ON CONFLICT behavior or targeted 23505 recovery.
Do not add a global prospect-email or phone constraint without first auditing whether
duplicates are currently valid across prospect lists.
If global uniqueness is not safe, persist a source-row fingerprint or import-row
identity and enforce uniqueness on that instead.
8. Verify Sunbiz filing-number scope.
Do not assume filingNumber is globally unique.
Audit whether uniqueness requires:
- filingNumber only
- registry/state + filingNumber
- source/list type + filingNumber
- entity type + filingNumber
The DB constraint and lookup must use the proven natural-key scope.
9. Add a DB-level Sunbiz uniqueness backstop.
Once the natural key is confirmed:
- audit existing duplicates
- resolve conflicts before migration
- add a versioned unique index
- use conflict-safe bulk insert
A SELECT-before-insert check alone will still duplicate under concurrent uploads.
10. Define ProspectList behavior for replayed and partially duplicated files.
For an identical replay:
- do not create a second ProspectList;
- return the prior import/list ID and result.
For a new file with some duplicate rows:
- create one new import/list record;
- store inserted/skipped/conflict counts;
- preserve row-level import provenance.
Do not create empty lists without an explicit operator-visible result.
11. Preserve row-level provenance.
Every inserted row should remain attributable to:
- import execution ID
- source file/list
- source row number or row fingerprint
Skipped/conflict rows should be available in a downloadable or inspectable report.
12. Define failure and retry semantics.
If a 100K-row import fails after 40K rows:
- rerun must resume or safely replay without duplicates;
- progress must be persisted;
- completed chunks must not be inserted again;
- failed import cannot be treated as a completed file replay.
Use keyset/chunk progress or conflict-safe replay—not only in-memory counters.

Kill lines

STOP if identical-file detection relies only on filename.
STOP if email/phone normalization is implemented differently from canonical lookup logic.
STOP if phone alone silently merges or skips prospect records.
STOP if either importer performs one DB lookup per row.
STOP if row dedupe is only read-before-write with no concurrency backstop.
STOP if filingNumber uniqueness is implemented before its registry/state scope is proven.
STOP if a repeated identical file creates another ProspectList.
STOP if partial failure cannot be retried safely.
STOP if skipped/conflicting rows lose file and source-row provenance.
STOP if db push or manual production edits are used instead of migrations.

Validation

- Same exact CSV uploaded twice → second request returns original import result;
  zero new list and prospect rows.
- Same CSV bytes under a different filename → still recognized as a replay.
- Same filename with different contents → treated as a new import.
- Duplicate emails with case/whitespace differences are normalized consistently.
- Duplicate rows within one CSV are counted separately from existing-DB duplicates.
- Phone-only ambiguous matches are reported for review, not silently skipped.
- Two concurrent uploads of the same file produce one import execution.
- Two different files containing the same canonical row do not race into duplicates.
- COREVT re-upload produces zero new entities.
- Two concurrent COREVT uploads produce one row per confirmed natural key.
- Partial failure followed by retry reaches the same final database state as one
  successful run.
- Returned totals reconcile exactly:
  total = inserted + duplicateWithinFile + skippedExisting + conflicts + invalid.

Final status: NOT BUILD-READY

The correct design is file-fingerprint replay protection plus conflict-safe row-level idempotency. Email/phone checks and filing-number lookups alone are insufficient for large, concurrent, retryable imports.
