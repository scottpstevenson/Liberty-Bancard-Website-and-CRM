What & Why

Replit is the system of record for channel permissions, consent tier, suppression state, lifecycle state, and compliance rules.

GHL is the communication execution layer.

The current risk is that GHL-native workflows can be triggered by GHL-side events, such as:

* GHL form fill
* tag applied inside GHL
* manual workflow enrollment
* GHL automation rule
* pipeline stage movement
* missed appointment automation

These GHL-native triggers can bypass Replit’s Wave 1A evaluateContactability() gate unless the workflow is configured to call Replit or branch on Replit-synced permission fields.

Wave 7 hardens the boundary:

* Replit computes channel permission truth.
* Replit syncs explicit permission fields to GHL.
* GHL workflows must branch on those fields or call the permission-check endpoint.
* GHL webhook opt-outs flow back into Replit.
* GHL sync errors and circuit breaker status are visible to operators.
* Replit compliance fields always win in conflicts.

⸻

Core Authority Rule

Replit owns compliance truth.
GHL executes only what Replit explicitly permits.

Replit-owned fields

GHL must not override these fields:

* doNotContact
* doNotAutoContact
* consentTier
* lifecycleStage
* phoneType
* channel opt-out flags
* PEWC evidence
* suppression state
* permission payload / channel permissions

GHL-owned or GHL-sourced engagement fields

GHL may provide these if the repo already stores them:

* last message timestamp
* last reply timestamp
* reply content/snippet
* GHL conversation ID
* GHL pipeline/stage label
* appointment metadata
* workflow event metadata

Even then, GHL data must not loosen Replit compliance restrictions.

⸻

Critical Boundary

This task cannot magically enforce external GHL-native workflow internals.

It can enforce:

* Replit-triggered GHL workflow enrollment
* Replit contact upsert field sync
* Replit-side permission-check endpoint
* Replit webhook processing
* Replit dashboard visibility

For GHL-native workflows, this task can provide:

* synced permission fields
* permission-check endpoint
* workflow guard documentation
* dashboard warnings

But GHL-native workflows are only safe after they are configured in GHL to consume those fields or call the endpoint.

The final report must clearly list any remaining external GHL configuration required.

Channel Semantics

Use Wave 1A channel names consistently:

type Channel =
  | "email"
  | "manual_call"
  | "sms"
  | "voice_ai"
  | "ringless_vm";

Meanings:

* email = email send
* manual_call = human task only, never AI voice/autodial/RVM
* sms = automated text message
* voice_ai = AI/prerecorded/artificial/autodialed voice
* ringless_vm = ringless voicemail / prerecorded voicemail drop

Unknown channel values must be rejected.

Done Looks Like

1. Permission-check endpoint

Create:

POST /api/ghl/permission-check

Auth:

* authenticated with GHL_WEBHOOK_SECRET
* use existing webhook secret/header pattern if present
* otherwise use Authorization: Bearer <GHL_WEBHOOK_SECRET> or x-ghl-webhook-secret
* no unauthenticated access
* apply existing webhook/public rate limit if available

Request:

{
  ghlContactId: string;
  channel: "email" | "manual_call" | "sms" | "voice_ai" | "ringless_vm";
  sequenceName?: string;
  workflowId?: string;
  workflowName?: string;
  stepName?: string;
  reason?: string;
}

Behavior:

* validates input with zod
* maps ghlContactId to a Replit contact
* if no contact found: return allowed false, reason contact_not_found
* calls Wave 1A evaluateContactability() in permission-check/dry-run mode
* does not write a consent enforcement audit log
* may write a lightweight GHL activity log entry for permission-check observability if existing ghlActivityLog supports it
* returns fail-closed result
* does not send messages
* does not enroll workflows
* does not mutate contact consent state

Response:

{
  allowed: boolean;
  reason: string;
  channel: string;
  consentTier?: string;
  lifecycleStage?: string;
  contactId?: number;
  ghlContactId: string;
  permissionCheckedAt: string;
}

Important:

If GHL cannot parse non-2xx responses reliably in workflow branches, return HTTP 200 with allowed: false for business-rule denials. Use 401/403 only for auth failure and 400 only for malformed input.

2. Channel permission custom field sync

On every GHL contact upsert, write Replit-computed permission state.

Use the existing GHL custom field mapping pattern.

Do not duplicate Wave 1A logic.

Preferred source:

* existing Wave 1A ghlPermissionPayload, if available
* otherwise compute a per-contact dry-run matrix using evaluateContactability() for the five canonical channels

Required synced fields:

* lb_consent_tier
* lb_do_not_contact
* lb_do_not_autocontact
* lb_lifecycle_stage
* lb_channel_permissions
* lb_channel_permissions_updated_at

lb_channel_permissions should be a JSON string:

{
  "email": true,
  "manualCall": true,
  "sms": false,
  "aiVoice": false,
  "ringlessVm": false,
  "lastUpdated": "2026-06-25T00:00:00.000Z"
}

Also add flat fields if the existing GHL field mapping supports them, because GHL workflow conditions may not parse JSON reliably:

* lb_can_email
* lb_can_manual_call
* lb_can_sms
* lb_can_ai_voice
* lb_can_ringless_vm

Field value format must match verified GHL custom field behavior:

* if GHL expects text, write "true" / "false"
* if GHL supports booleans, write booleans
* if field IDs are required, use existing mapping; do not invent field IDs

If fields are missing from external GHL settings, log/report the write error clearly. Do not silently drop it.

3. GHL workflow guard contract

Update the internal GHL workflow guidance UI/documentation, likely:

* client/src/pages/dashboard/GhlWorkflows.tsx
* GhlSequenceGuide.tsx
* existing integration guide component

Add a clear operator-facing contract:

Every GHL-native workflow that can send email, SMS, AI voice, or ringless voicemail must do one of the following before sending:

1. Call POST /api/ghl/permission-check, or
2. Branch on Replit-synced permission fields:
    * lb_can_email
    * lb_can_sms
    * lb_can_ai_voice
    * lb_can_ringless_vm
    * lb_do_not_contact
    * lb_do_not_autocontact
    * lb_consent_tier

Hard warnings:

* GHL-native workflows are unsafe until configured to consume Replit permission fields or endpoint.
* SMS requires lb_can_sms === true.
* AI voice requires lb_can_ai_voice === true.
* Ringless voicemail requires lb_can_ringless_vm === true.
* Manual call task is not AI voice or autodialing.
* Replit remains the source of truth.

Do not claim this task automatically changes external GHL workflow internals unless the repo has an API-managed workflow editor that actually updates those workflows.

4. Opt-out webhook hardening

Audit and update existing:

POST /api/ghl/webhook

Handle verified GHL opt-out events only after inspecting current payload shapes.

Potential events to support if verified:

* contact opt-out / DND event
* SMS STOP / SMS opt-out
* email unsubscribe
* tag applied with opt-out/DNC/unsubscribe tag
* contact deleted/disabled if existing logic treats it as suppression

Rules:

Global opt-out / DNC

Set:

* doNotContact = true
* doNotAutoContact = true
* consentTier = "opted_out"

Write consent audit log:

* action = "opt_out"
* source = "ghl_webhook"
* GHL contact ID
* event type
* raw payload summary in details JSONB, without excessive PII

Channel-specific SMS opt-out

Set channel-specific SMS opt-out field if it exists.

Also set:

* doNotAutoContact = true if Wave 1A expects it for automated channel block

Do not necessarily set global doNotContact unless the event clearly means global DNC.

Write consent audit log.

Email unsubscribe

Set email opt-out/suppression field if it exists.

Do not automatically convert to global DNC unless the event clearly means global DND.

Write consent audit log.

Ambiguous opt-out event

Fail conservative:

* set doNotAutoContact = true
* do not loosen any permission
* write audit log
* surface warning in GHL sync dashboard

Do not downgrade or change PEWC except through explicit opt-out/revocation semantics.

See above.

Admin/manager only.

Returns:

{
  generatedAt: string;
  lastSuccessfulSyncAt: string | null;
  failedSyncs24h: number;
  contactsMissingGhlContactId: number;

  };

GET /api/ghl/sync-errors

Admin/manager only.

Supports pagination or limited recent results.

Returns recent sync errors from ghlActivityLog or equivalent.

POST /api/ghl/force-sync-contact

Admin/manager only.

Request:

{
  contactId: number;
}

Behavior:

* loads contact
* recomputes permission fields
* upserts/syncs GHL contact fields
* logs success/failure
* no communication send
* no workflow enrollment

If an equivalent endpoint exists, reuse it instead of creating a duplicate.

Kill Lines

Stop and report before build if:

* evaluateContactability() is not importable.
* ghlContactId cannot be mapped to a Replit contact.
* GHL webhook auth pattern cannot be identified.
* Adding permission-check would create an unauthenticated public endpoint.
* GHL custom field mapping requires external field IDs that are unavailable.
* Existing GHL upsert uses a field format that cannot safely carry permission values.
* ghlActivityLog cannot support error/dashboard data and schema migration pattern is unclear.
* Circuit breaker state cannot be read and creating a new breaker would be required.
* Opt-out webhook payload shapes cannot be verified.
* A webhook event would loosen restrictions or clear suppression state.
* Force Sync Contact would send communication or enroll workflow.
* Dashboard action would bypass compliance.
* The task would enable SMS, AI voice, ringless voicemail, or GHL workflows.
* The task would claim external GHL-native workflows are automatically safe without GHL-side configuration.
