## Two implementation clarifications

### 1. Move native delivery feasibility to the first executable gate

The task’s “Supported schema delivery and release gates” section already acknowledges that managed Publish may not deliver native functions/triggers. However, its implementation sequence can still permit substantial construction before that feasibility is proved.

`replit.md:21` explicitly requires production deployment feasibility to be verified **before building around required database objects**, and prohibits manual production migrations, startup/deployment-build DDL and custom production migration runners.

Insert this at the start of Steps:

> Before implementing changes that depend on native functions, triggers or constraints, establish and record the supported production delivery route for those exact object types. Use project/platform evidence and isolated certification; do not execute production DDL during planning. If the supported route cannot deliver them, identify the platform owner and resolution, mark that dependency blocked, and do not claim the consolidation is ready to publish or run production imports. Continue only independent work that does not assume the unavailable contract.

This is a dependency-order correction, not a request to bypass the database guard. The source audit cannot prove this platform capability. The task’s reported installed=false result makes it consequential.

### 2. Name every business-scoped receipt dependency in the global-reuse migration

The task already requires fresh same-address reuse across inputs/businesses. Make its implementation explicit:

> Migrate the address-level claim/receipt lookup together with SFP freshness checks, commercial link authority and the native typed-source trigger. Preserve immutable original provider-operation/observation identity and original validation time/expiry. Reference the shared receipt from each independently supported business/contact affiliation; never rewrite an observation’s original subject to simulate reuse. Address validity does not establish business affiliation.

At minimum include:
- `server/services/cro03/sfp-outreach-policy.ts` — `findFreshProviderObservation`;
- `server/services/cro03/sfp-validation.ts` — existing observation joins, reuse and final receipt checks;
- `server/services/commercial-link-authority.ts` — typed-source receipt validation;
- the native trigger defined by `0314_sfp_verified_recipient_link_commitments.sql`, through a new forward migration.

Add one real-database acceptance case: the same selected normalized address arrives through an existing contact and an import, with two independently supported business associations. Concurrent processing produces one validation dispatch/receipt while both associations can consume it without a cohort and without extending expiry. A third unsupported association remains held. Test current evidence/hash versions and stale-receipt handling.

Without coordinated migration, a new global queue could avoid duplicate vendor calls while the downstream native trigger still rejects the reused receipt.
