P0 — EFFECT-CONSUMER IDEMPOTENCY

The dispatcher being durable and lease-fenced does not by itself prevent duplicated effects. Complete idempotency at each consumer.

Inventory every stage-effect type emitted by the new intent authority and produce a matrix containing:

- effect type;
- consumer;
- local or external effect;
- immutable logical operation key;
- existing idempotency support;
- durable receipt location;
- ambiguous-outcome behavior;
- retry behavior;
- terminal behavior;
- test proving replay safety.

For every consumer:

A. Local database effects

- Use an immutable effect-intent ID plus effect type/target as the logical operation key.
- Enforce uniqueness at the database boundary.
- Apply the local mutation and durable completion receipt in one transaction.
- Replaying an already completed intent must return the existing result without repeating the mutation.
- Never use an in-memory processed set as authority.

B. External provider effects

- Pass a stable provider idempotency key derived from the immutable intent/command identity when supported.
- Persist provider request identity, provider reference, response classification, and final disposition.
- If the provider times out after request transmission, record UNKNOWN or RECONCILE_REQUIRED.
- Do not blindly retry an ambiguous effect.
- Reconcile using provider lookup/reference capabilities before another mutation attempt.
- If a provider lacks both idempotency and lookup/reconciliation capability, fail closed into manual reconciliation. Do not claim exactly-once delivery.
- A stale lease owner must never overwrite the result recorded by a newer owner.

C. Existing canonical authorities

- Reuse current GHL projection, onboarding, lifecycle, task, analytics, and command authorities where they already provide durability.
- Do not create parallel workers or duplicate outboxes.
- Remove any direct competing material effect after durable intent creation.
- Explicitly classify nonmaterial analytics/notification effects if they remain best-effort.

Required idempotency tests:

1. Same intent dispatched twice serially.
2. Same intent claimed by two competing owners.
3. Lease expires during execution.
4. Stale owner completes after lease loss.
5. Process dies after local mutation but before worker acknowledgement.
6. Provider accepts request but response is lost.
7. Provider returns the same idempotency result on retry.
8. Provider lacks idempotency but supports reconciliation.
9. Provider lacks both capabilities and is sent to manual reconciliation without automatic replay.
10. Terminal effect failure remains visible and does not falsely complete the parent stage transition.
