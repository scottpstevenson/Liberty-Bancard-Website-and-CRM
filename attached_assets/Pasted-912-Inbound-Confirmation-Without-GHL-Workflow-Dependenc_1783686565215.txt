912 — Inbound Confirmation Without GHL Workflow Dependency

Verdict

Build-ready only with the corrections below.

What & Why

All public lead forms must send an immediate confirmation even when no GHL workflow is configured.

The current implementation incorrectly gates the direct confirmation path behind:

isGhlConfigured() || isSdrGhlConfigured()

This allows a valid form submission to complete without any confirmation when GHL is unavailable or incompletely configured.

This task makes immediate inbound confirmation provider-independent:

GHL workflow is optional
GHL direct-send API is optional
SMTP is the final delivery fallback

Critical Corrections

1. Never send both workflow confirmation and direct confirmation

The flow must choose exactly one immediate-confirmation path.

Required precedence:

1. If a configured GHL workflow is intentionally used and trigger succeeds:
   record workflow enrollment
   do not direct-send a duplicate confirmation
2. If workflow ID is missing, workflow enrollment is disabled, or workflow trigger fails:
   send confirmation through unifiedSendEmail()
3. unifiedSendEmail():
   use GHL direct-send if available
   otherwise use SMTP

Kill line:

STOP if one form submission can trigger both a GHL workflow confirmation and a direct confirmation email.

2. Do not use a 24-hour in-memory setTimeout

A 24-hour setTimeout is not reliable for production scheduling.

It is lost on:

server restart
deployment
process crash
autoscaling
worker replacement

The follow-up nudge must be scheduled through the project’s existing durable queue, delayed-job, task, cron, or persisted follow-up mechanism.

Preflight these existing systems before implementation:

BullMQ or delayed jobs
follow-up task table
scheduled communications table
sequence worker delayed steps
existing inbound confirmation follow-up scheduler

Preferred behavior:

persist follow-up dueAt = submittedAt + 24 hours
worker evaluates whether deal has progressed
send only if still eligible
mark job completed/skipped/failed

Do not create a second scheduling system if an existing durable mechanism already exists.

Kill line:

STOP if the 24-hour follow-up remains dependent on an in-memory setTimeout.

3. Audit successful provider acceptance, not merely intent

Add distinct audit actions:

inbound_confirmation_send_attempted
inbound_confirmation_sent
inbound_confirmation_failed
inbound_confirmation_followup_scheduled
inbound_confirmation_followup_sent
inbound_confirmation_followup_skipped
inbound_confirmation_followup_failed

inbound_confirmation_sent should only be written after the selected provider accepts the send request successfully.

Include:

contactId
dealId if available
formType
provider = ghl_direct | smtp | ghl_workflow
recipient
providerMessageId if available
workflowId if applicable
failureReason if failed

Do not treat an attempted send or a “sending direct” skip reason as confirmed success.

Required Immediate Confirmation Flow

Refactor or add a helper such as:

sendInboundConfirmation({
  contact,
  deal,
  formType,
  bookingLink,
})

Expected result:

type InboundConfirmationResult =
  | {
      sent: true;
      method: "ghl_workflow" | "ghl_direct" | "smtp";
      providerMessageId?: string;
    }
  | {
      sent: false;
      method?: "ghl_workflow" | "ghl_direct" | "smtp";
      reason: string;
    };

The public routes should call one canonical helper instead of duplicating delivery decisions.

Workflow Behavior

The GHL workflow ID must no longer be required for confirmation delivery.

Allowed:

workflow configured and successfully triggered
→ workflow owns immediate confirmation

Fallback:

workflow missing
workflow disabled
workflow trigger fails
→ unified direct-send path

Do not classify a missing workflow ID as an error when direct delivery succeeds.

SMTP Fallback

Verify unifiedSendEmail() has real provider fallback semantics:

attempt GHL direct send only when properly configured
if unavailable or provider call fails in a fallback-eligible way, use SMTP
return actual provider used
return success/failure explicitly

Do not swallow a GHL error and falsely report success.

Do not call real providers in tests.

SMS

The request says “email + optional SMS,” but SMS must remain governed by existing consent and feature flags.

Only send SMS if:

the contact has the required consent
SMS is enabled
the existing SMS contactability gate passes

Email confirmation must still work if SMS is unavailable.

Do not make SMS delivery a condition for overall confirmation success.

Durable 24-Hour Follow-Up

The follow-up must:

be persisted durably
be idempotent
check deal progression at execution time
check current opt-out/DNC/contactability state
use unifiedSendEmail()
skip if the lead has progressed
skip if the contact opted out
avoid duplicate follow-up scheduling for the same submission/contact

Recommended idempotency key:

inbound_confirmation_followup:<formSubmissionId>

or an equivalent stable submission/contact identifier.

Go-Live Check Stage 5

Update Stage 5 to pass when there is evidence of a valid confirmation path.

Passing states:

OR recent ghl_inbound_confirmation_enrolled

Conditional/degraded state:

Failure states:

recent inbound confirmation failed
no usable GHL direct-send or SMTP provider
workflow missing and no direct provider available

Do not treat this as a success:

inbound_confirmation_skipped with text containing "sending direct"

That only proves routing intent, not successful delivery.
