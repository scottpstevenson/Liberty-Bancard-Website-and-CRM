# P0 corrections

These are merge blockers.

### P0-1 — Replace GHL-first semantics everywhere covered by the kill line

`server/services/contact-writer.ts:171-217` calls `upsertGhlContact()` before the local transaction. The compatibility wrapper at `:366-386` adds nondeterministic `legacy_unknown` provenance. `updateContactGhlFirst()` at `:397+` also projects before committing locally.

Exact fix:

1. Replace `ghl_upsert_first` with a local-first mode.
2. In one local transaction:

   * resolve or create the contact;
   * insert/upsert its deterministic source event;
   * record BT‑07 identity observations;
   * write audit data;
   * create a durable provider-projection intent.
3. Commit.
4. Only then enqueue or attempt GHL projection.
5. Preserve `ghl_inbound_no_echo` for provider-originated changes.
6. Remove production use of `createContactGhlFirst()` and correct `updateContactGhlFirst()` ordering.

The task’s file list misses these live call sites:

* `server/routes/public.ts:383,593,733,859,1064,1135,1262,1433,1541`
* `server/routes/partners.ts:294,1124`
* `server/routes/partner-orgs.ts:90`

* Add a static scanner that fails on unapproved `insert(contacts)`, `storage.createContact()`, `createContactGhlFirst()`, and `ghl_upsert_first`.

### P0-3 — Add a processor lease, not merely a unique execution key

Current `import_executions` uniqueness at `shared/schema.ts:29-32` applies only after completion. Two requests can create two running executions or both process the same execution.

Add to migration `0155`:

* Permanent `execution_key` uniqueness.
* `claim_token`
* `lease_expires_at`
* `heartbeat_at`
* `attempt_count`
* Durable row outcome table keyed by `(execution_id, source_row_number)`.
* Durable provider projection intent/state if no existing suitable outbox is reused.

Execution flow must use an atomic compare-and-set claim. A concurrent loser returns the existing execution and does not process rows. Expired claims can be reclaimed using token comparison.

Treat `import_executions` as lifecycle authority. `csv_imports` may remain a UI projection, but must not independently own status or counters.

### P0-4 — Make every row atomic and durably reconciled

Current problems include:

* In-memory global dedupe sets at `imports.ts:1501-1513`.
* Invalid/duplicate rows only increment counters at `:1682-1696`.
* Original row identity is discarded when `contactInserts` is built.
* Source events are written later, fire-and-forget, at `:1977+`.
* `sourceRowNumber` is the successful-result index, not the original input row.
* All-invalid/all-duplicate runs may leave `import_executions` running.
* Reconciliation logs a mismatch but still returns success.
* The catch path marks an arbitrary processing import failed.

Exact per-row transaction:

1. Claim `(execution_id, logical_row_number)`.
2. Normalize and validate.
3. Resolve existing identity without weak automatic merging.
4. Create or match the contact.
5. Record source event and identity observations.
6. Apply restrictive consent only through `ConsentAuthority`.
7. Link the organization safely or record a deferred reason.
8. Write the immutable row disposition.
9. Write provider intent if applicable.
10. Commit.

Counters must be derived from the row ledger. Completion must fail if:

```text
total_rows != created + matched_noop + updated + rejected + deferred + failed
```

### P0-5 — Correct authorization and actor attribution

Currently:

* Import create: `isAuthenticated` only at `imports.ts:1427`.
* Import list: `isAuthenticated` at `:1233`.
* Stats: `isAuthenticated` at `:1294`.
* Detail: `isAuthenticated` at `:1421`.
* `importedBy` trusts request input at `:1481`.
* Business create/ingest accepts any authenticated user at `sdr.ts:2217,2228`.

Use one explicit matrix:

| Operation                      | Agent |         Manager | Admin |
| ------------------------------ | ----: | --------------: | ----: |
| Import create/list/detail      |  Deny |           Allow | Allow |
| Row-disposition read           |  Deny | Allow, redacted | Allow |
| Retry/repair/force-fail        |  Deny |            Deny | Allow |
| Generic business create/ingest |  Deny |           Allow | Allow |

Derive actor ID, role and email exclusively from `req.user`. Never accept `importedBy`, provenance, authority fields, or audit identity from request bodies.

### P0-6 — Serialize organization resolution

`ingestBusiness()` reads at `server/services/sdr/dedupe.ts:283` and creates at `:360` without serialization. `findOrCreateBusinessForMerchant()` repeats the race at `server/storage/businesses.ts:137-148`, and lead-finder calls it at `:747,1067`.

Exact fix:

* Create one organization resolver.
* Acquire a transaction-scoped PostgreSQL advisory lock over the strongest normalized evidence: Google Place ID, domain, phone, or normalized name/location.
* Re-read candidates under the lock.
* Create only when still unmatched.
* Route `ingestBusiness`, `findOrCreateBusinessForMerchant`, lead-finder and manual business creation through it.
* When two candidates tie or evidence conflicts, return `deferred` with `AMBIGUOUS_ORGANIZATION_MATCH`; never choose the first candidate arbitrarily.
* Do not merge the contact, company and business models.
