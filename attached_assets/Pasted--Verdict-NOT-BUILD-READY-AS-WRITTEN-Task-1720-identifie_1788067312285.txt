## P0 corrections

### 1. Define whether the task proves process truth or fleet truth

`QueueManager.getTopologySnapshot()` reports only the local PID, nullable identity, and local release SHA. It cannot prove that all autoscaled replicas run the same release.

Use one of these explicit contracts:

* Recommended: add a TTL-based fleet-presence registry under the existing QueueManager authority, using Redis. Each process publishes an immutable lifetime identity, role, release SHA, startup time, last-seen timestamp, and sanitized topology.
* Narrower alternative: remove mixed-SHA and fleet-completeness claims and clearly label the route `local_process_snapshot`.

If fleet proof is retained, readiness must aggregate all nonexpired members and report mixed SHA, duplicate identity, stale heartbeat, and incomplete registry states.

Do not construct identity solely from PID. Use release SHA + role + host/container identifier + generated process-lifetime UUID.

Keep platform liveness separate from operator readiness so a telemetry configuration mistake does not unexpectedly restart every autoscaled instance.

### 2. Replace the declarative manifest check with an actual owner census

Current validation does not find real callers. At minimum, the census must include:

* Every BullMQ `Queue` and `Worker` construction
* Base and named repeatables
* Process-lifetime `setInterval` and cron schedulers
* Startup recovery loops
* Detached request-triggered work requiring recovery
* Job-lock and heartbeat owners
* Manual/operator starters
* Dormant legacy implementations

Confirmed unrepresented or incompletely represented paths include:

* Merchant-application outbox worker
* Deal-boarding outbox worker
* Wizard flag-cache refresh
* Daily SDR maintenance scheduler
* Content scheduler
* CRO-03A detached execution and GET-triggered recovery

The manifest needs explicit fields for mechanism, activation state, owner symbol, starter, durability, schedule identity, lease/fence, and effect class. CI must fail on an unknown active starter, not merely an unknown queue name.

Current `main` contains no merged correction for the CRO-03A ownership violation. If #1730 merges first, rebase and register that owner. Otherwise #1720 must report it as a known blocking violation and must not create a competing CRO worker.

### 3. Eliminate false-green queue telemetry

Correct these behaviors:

* Include every expected queue even when it was not instantiated; report `not_initialized`.
* Propagate `getAllQueueMetrics().status` instead of hardcoding operator status to `ok`.
* Never convert backlog-query failure to backlog `0`.
* Never silently convert Redis information failure to `null` without a probe status.
* Report effective schedule values, not only static configuration.
* Label five-job duration samples with sample size and observation range.
* Label throughput as process-local and polling-dependent until replaced.
* Distinguish logical jobs, physical queues, physical workers, schedules, and processes.

Observed repeatables must report expected and unexpected schedules with:

* Queue and job names
* Repeatable identifier/key
* `every` or cron expression
* Next execution
* Declared owner
* Captured time
* `matched`, `missing`, `unexpected`, `duplicate`, or `probe_error`

### 4. Treat DLQ privacy as a persistence problem

The current dead-letter path writes raw `job.data`, stack traces, and error messages into durable review-queue records. Fixing only the response projection leaves the stored exposure intact.

Create one canonical failure sanitizer used before:

* Review-queue persistence
* Background-job failure persistence
* Audit logging
* Alert construction
* Structured console logging
* API projection

Allowed fields should be limited to opaque job identity, queue/job type, attempt counts, timestamps, stable error class/code, and a sanitized message or digest.

Also:

* Stop writing new raw payloads and stack traces.
* Apply defense-in-depth projections so historical records cannot leak through review-queue list/detail routes.
* Provide an idempotent, non-printing production scrub for existing `dead_letter_job` metadata.
* If the task requires historical raw values to be removed, record this as data remediation and coordinate it with migration ownership. “No migration” cannot remain an unconditional assertion.

Pagination needs a bounded opaque cursor with a snapshot boundary or keyset ordering. Offset pagination will skip or duplicate records while the failed set changes.

### 5. Remove all provider calls from generic health

Editing only `/api/admin/live-health` is insufficient. [`health-monitor.ts`](https://github.com/scottpstevenson/Liberty-Bancard-Website-and-CRM/blob/dfa10220c4736027fefa0a47981a48350e853b22/server/services/health-monitor.ts) also:

* Runs an OpenAI completion
* Records AI spend
* Checks email and SMS transports
* Can reach GHL through transport health checks

Generic health should read configuration and last-observed provider evidence only. Live probes belong behind explicit provider-health authority and must never run as part of ordinary infrastructure health.

The same health monitor incorrectly treats a missing outbound-pause setting as healthy and “defaults to unpaused.” It must consume the canonical fail-closed outbound-control snapshot.

### 6. Define one truthful queue-alert authority

The repository currently contains multiple independent cooldown paths, including at least one apparently unused threshold function.

For queue/DLQ alerts:

* Normalize an incident fingerprint.
* Claim it atomically in Redis with a lease/cooldown.
* Return a structured outcome: durable-feed result, transport configuration, attempted, delivered, failed, or suppressed.
* Check Slack HTTP status.
* Never retain or return provider response bodies.
* Do not stamp the full successful cooldown before confirmed delivery.
* Use a short retry lease/backoff after failure.
* Ensure a distinct incident is not suppressed by another incident’s cooldown.
* Remove or integrate the dead threshold-alert implementation.

Keep this task scoped to queue/DLQ alerts unless it explicitly expands to the separate health-email cooldown system.

### 7. Use durable, truthful history semantics

The present in-memory history must not be called a fixed 24-hour window.

A no-schema option is BullMQ’s built-in Redis metrics, enabled consistently on every worker. BullMQ stores completed and failed aggregates per minute; every worker for a queue must use the same retention setting. See the [official BullMQ metrics documentation](https://docs.bullmq.io/guide/metrics/).

The API must still disclose:

* `observedFrom`
* Requested and available window
* Expected and available points
* Release/process boundaries
* Partial or complete status
* Whether failures represent attempts or terminal exhaustion

After first deployment, the series remains partial until a genuine 24-hour window matures. Do not backfill missing minutes as zero.

### 8. Make the tests exercise production code

Current tests contain material gaps:

* `test-build-identity.ts` duplicates logic rather than importing the production identity contract.
* It permits all-zero placeholder SHAs.
* Its live endpoint checks can skip with exit zero.
* It is not registered in the main CI/pre-deploy manifest.
* `test-bullmq-resilience.ts` contains placeholder assertions and outdated expected queue counts.
* Existing topology tests prove presence and counts, not complete roster ownership.
* `test-live-health.ts` can pass when the server is unavailable and has a different critical-check definition from production.

Every new suite must be added to both `scripts/pre-deploy.ts` and `scripts/ci-suite-manifest.ts`, and to the current GitHub workflow.
