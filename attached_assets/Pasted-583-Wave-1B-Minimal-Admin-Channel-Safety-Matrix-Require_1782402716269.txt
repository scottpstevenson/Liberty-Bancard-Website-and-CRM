⸻

What & Why

Wave 1A created the backend contactability engine: the canonical source of truth for whether a contact can receive email, manual call tasks, SMS, AI voice, or ringless voicemail.

Operators now need minimum viable visibility into that engine before Liberty scales outreach.

This task builds a lean Channel Safety Matrix inside the existing admin/dashboard area. It shows what the backend contactability engine is allowing, blocking, and why — without waiting for the full Operator Command Center in Wave 9.

This is a visibility layer only.

It must read from the Wave 1A contactability logic and enforcement audit logs. It must not define channel permission rules itself.

⸻

Core Principle

The UI displays backend truth. It does not create backend truth.

Replit’s evaluateContactability() / Wave 1A contactability service remains the only authority for channel permission logic.

The Channel Safety Matrix must not duplicate, fork, override, or reinterpret contactability rules.

Backend Implementation Rules

Rule 1 — Do not duplicate contactability logic

The summary endpoint must not create its own version of channel rules.

Allowed approaches:

1. Use a Wave 1A batch/dry-run helper if one exists.
2. Add a small summarizeChannelSafety() helper in server/services/contactability.ts that reuses the same internal evaluator as evaluateContactability().
3. Query contacts in batches and run dry-run evaluations through the same contactability service.

Blocked approach:

* Writing separate SQL conditions like “SMS eligible = consentTier = PEWC AND SMS_ENABLED = true” as the final authority.

SQL grouping may be used for coarse counts, but final channel eligibility must come from the contactability engine.

Rule 2 — Dry-run only

The summary endpoint must not write outreach audit logs.

If it needs to evaluate eligibility, it must use dry-run mode.

Opening or refreshing the dashboard must never create compliance/audit noise.

Rule 3 — Performance guard

Do not load unbounded full contact records into memory if the contacts table can be large.

Use one of:

* aggregate SQL for simple source/consent counts
* paginated/batched contactability dry-run evaluation
* an existing summary/cache pattern if the repo has one

If exact per-contact dry-run counts are too expensive for the current repo, implement a safe bounded approach and return a warning explaining the limitation.

Do not build a new queue/caching system in this task.

Rule 4 — Audit log schema verification

Before aggregating blocked attempts, inspect the actual Wave 1A audit log structure.

Use whatever table/event fields Wave 1A created.

Do not assume:

* table name is audit_logs
* event type is exactly channel_blocked
* reason field name is exactly reason

If the audit log schema differs, adapt to the actual implementation and document the mapping.
