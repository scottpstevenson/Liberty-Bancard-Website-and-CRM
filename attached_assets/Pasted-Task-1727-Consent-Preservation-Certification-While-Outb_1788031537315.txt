1. Verdict

VALID NARROW TASK, BUT NOT BUILD-READY AS WRITTEN.

The immediate crash is correctly identified: scripts/test-csv-import-opt-out-preservation.ts calls the production upsertGhlContact() mutation while the canonical pause is active, so the pause authority correctly rejects the call before the test can inspect the GHL payload.

However, merely unpausing a test fixture or loosening the assertion would produce a misleading green result. Four controlling corrections are required:

The GHL assertions must consume a pure production payload builder, not call a provider mutation and not alter pause state.

The suite must stop replacing the certification wrapper's provider-deny fetch; the current mock removes the boundary the suite claims to prove.

The local consent cases must use the current canonical CSV/consent path instead of a copied pre-BT-04/raw-SQL simulation whose result differs from production.

The suite must be registered in both mandatory-suite registries as disposable deterministic integration; at the audited SHA it is in neither registry and therefore cannot currently unblock a full capability run.

No migration is required. No production feature should be disabled. The production admin launch control remains available. The only thing this certification task must not do is toggle that control or call a live provider.

2. Direct production and launch-gate clarification

This task does apply to production code, in the following safe sense:

production CSV imports and the certification suite must consume the same consent-intent authority;

production upsertGhlContact() and the certification suite must consume the same GHL permission-payload builder;

the production GHL mutation remains protected by the existing pause/epoch/transport boundary;

the admin UI/API retains its existing authority to pause or unpause the launch gate.

This task does not authorize a deployment-time unpause, live GHL mutation, paid enrichment call, sequence send, or production-data cleanup. That is an execution authorization boundary, not an instruction to leave product features permanently disabled.

Do not add any new production feature flag, route-level 503, provider disablement, admin restriction, or test-only production bypass. Cold-outreach preparation, sequence construction, enrichment, readiness, and operator workflows remain available under their existing controls. Actual external sends remain governed by the launch/pause authority.

Whether non-message GHL CRM projections should continue while the message-send gate is paused is a separate effect-classification decision. #1727 must not silently redefine it. GHL contact upserts can trigger provider-side workflows, and the current code writes the base contact before its separate permission-field update; changing that production boundary requires explicit proof that no provider workflow can send during the interval.

4. P0 corrections

P0-01 — Use a pure production GHL permission-payload seam

Create a side-effect-free production module, preferably server/services/ghl-contact-payload.ts, and move the permission-field construction into it.

The builder contract must:

accept only contact consent/lifecycle values, an already-resolved optional channel-permission payload, and an injected timestamp/clock;

return the exact customFields array used by the production GHL PUT;

perform no environment access, token/config lookup, database/storage access, pause access, logging, dynamic import, timers, fetch, HTTP, queue work, or provider construction;

deterministically emit lb_do_not_contact, lb_do_not_autocontact, lb_lifecycle_stage, lb_channel_permissions_updated_at, lb_consent_tier when present, and all resolved channel-permission fields;

preserve field names and wire values exactly.

server/services/ghl.ts must resolve any asynchronous contactability evidence, call this builder, and use its returned fields for the real provider request. The certification suite must call the same builder directly.

Do not expose skipPause, testMode, bypassAuthorization, an exception key, an environment-based shortcut, or an injectable production pause decision. Do not make doUpsertGhlContactInner() public merely so the test can bypass the boundary.

P0-02 — Keep the denied-provider boundary installed

Remove all of the following from scripts/test-csv-import-opt-out-preservation.ts:

assignment to global.fetch/globalThis.fetch;

fake GHL_PRIVATE_INTEGRATION_TOKEN, GHL_API_KEY, or GHL_LOCATION_ID values;

direct import or invocation of upsertGhlContact() for payload-only assertions;

assertions that captured fake HTTP requests prove no real request occurred.

The provider-denied wrapper must remain the owner of network denial. The corrected suite must complete with:

zero attempted provider transports;

zero blocked provider attempts;

no provider credentials introduced after the wrapper scrub;

no GHL URL construction required by the payload tests.

Add a source/behavior regression that fails if this suite assigns fetch, sets GHL credentials, or imports the provider mutation again.

P0-03 — Replace stale consent replicas with the current canonical path

Cases 1-14 currently certify duplicated test logic, not the production import path. Extract a small pure CSV consent-intent module, preferably server/services/csv-consent-intent.ts, and make server/routes/imports.ts consume it.

The shared module must normalize and classify:

existing restrictive state that must be preserved;

no restriction/no-op;

channel-specific email opt-out;

explicit global DNC.

Freeze scope explicitly:

doNotContact=true and an explicit do_not_contact tier are global DNC;

email unsubscribed/opted_out and optedOutEmail=true are email restrictions;

consentTier=opted_out must not be silently widened into global DNC unless a separately documented canonical rule proves that exact scope;

a permissive CSV value never generates an opt-in and never clears an existing restriction.

For newly applied restrictions, the disposable integration portion must invoke the actual applyConsentCommand() result selected by the shared intent module, then read both canonical consent projections and compatibility contact fields. Raw SQL may be used only for fixture creation/teardown, never to simulate the behavior being certified.

Test global DNC and email-only opt-out as separate fixtures. Expected GHL fields must be derived from the actual post-command contact record, not hard-coded to the stale combined state.
