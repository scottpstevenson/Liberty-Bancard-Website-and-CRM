What & Why

The Operator Dashboard is becoming the command plane for Liberty Bancard.

Previous waves built the underlying systems:

* Wave 1A — contactability gate
* Wave 1B — Channel Safety Matrix
* Wave 5 — Offer Router
* Wave 6 — Compliant SDR Sequence Architecture
* Wave 7 — GHL/Replit sync authority hardening
* Wave 8 — Analytics + Attribution APIs

Wave 9 should not rebuild those systems.

Wave 9 should unify them into a single operator control plane with:

* Lifecycle Command Center
* SDR Command Center
* Conversion view powered by Wave 8
* GHL Sync view powered by Wave 7
* Channel Safety extension powered by Wave 1B/Wave 7 logs
* Launch Readiness Checklist powered by existing readiness signals

The goal is to help admins answer:

* Where are contacts in the lifecycle?
* Which stages are stuck?
* Are SDR sequences safe and healthy?
* Are channels being blocked correctly?
* Is GHL sync healthy?
* Are analytics/conversions flowing?
* Are we ready to scale?

⸻

Core Rule

Wave 9 is a read-only command center unless an existing safe operator action already exists.

Allowed actions:

* navigate to filtered lists
* refresh data
* force sync contact only if Wave 7 already shipped a safe force-sync endpoint
* toggle feature flags only if the repo already has a safe feature flag mutation pattern

Forbidden actions:

* sending SMS
* sending email
* placing AI voice calls
* triggering ringless voicemail
* enrolling GHL workflows
* creating new sequences
* changing contactability rules
* changing consent state
* changing offer routing
* activating sequences without the Wave 6 activation checklist guard
* inventing readiness signals with fake pass states

1. Lifecycle Command Center tab

Add a Lifecycle tab to /dashboard/operator.

Shows cards for canonical lifecycle stages:

prospect
lead
analysis_requested
statement_uploaded
call_booked
proposal_sent
verbal_commit
live_merchant
retained
referred
closed_lost

Each stage card shows:

* stage label
* count
* stuck count
* percentage of total active pipeline
* link to contacts list filtered by lifecycle stage
* clear empty state if count is zero

Stuck logic:

* default stuck threshold: > 7 days in same stage
* only compute if a reliable timestamp exists, such as lifecycleStageUpdatedAt, updatedAt, or a verified stage progression event
* if no reliable timestamp exists, show Stuck tracking unavailable rather than faking the value

Required backend:

Create only if no equivalent exists:

GET /api/operator/lifecycle-stage-counts

Admin/manager only.

Response:

{
  generatedAt: string;
  stages: Array<{
    lifecycleStage: string;
    count: number;
    stuckCount: number | null;
    stuckThresholdDays: number;
    filterUrl: string;
  }>;
  totalActivePipeline: number;
  warning?: string;
}

6. Launch Readiness Checklist

Add a Launch Checklist section to /dashboard/activation or a Launch tab if that is the existing Activation Panel pattern.

Preferred:

/dashboard/activation because activation already owns readiness/go-live context.

Required endpoint:

Create only if no equivalent exists:

GET /api/activation/readiness

Admin/manager only.

Returns readiness items with:

{
  generatedAt: string;
  overallStatus: "green" | "yellow" | "red";
  items: Array<{
    key: string;
    label: string;
    status: "green" | "yellow" | "red";
    value?: string | number | boolean | null;
    description: string;
    remediation?: string;
    source: string;
  }>;
  warnings?: string[];
}

Checklist items:

Required launch gates

* GHL connection configured
* PEWC disclosure version set
* Wave 1A evaluateContactability() available
* consent tier migration applied
* Wave 6 sequence families seeded, expected 10/10
* Wave 7 permission fields sync status healthy
* Wave 8 analytics events present / recent
* feature flags visible:
    * SDR_ENABLED
    * SMS_ENABLED
    * VOICE_AI_ENABLED
    * NIGHTLY_DISCOVERY_ENABLED
* inbox health for active senders
* queue health / dead-letter jobs
* sitemap coverage if an existing sitemap audit exists

Readiness honesty rule

If a signal cannot be verified from the repo/database, status must be yellow with remediation.

Never show green for an unverified signal.

Examples:

* no sitemap audit source → yellow, “Sitemap coverage check unavailable”
* no queue health source → yellow, “Queue health source unavailable”
* no inbox health source → yellow, “Sender health source unavailable”
* Wave 8 not yet populated → yellow, “Analytics data still accumulating”

Overall status:

* red if any required hard gate is red
* yellow if no red but any unknown/yellow
* green only if all required signals are verified green

Source-of-Truth Rules

Lifecycle

Source:

* contacts.lifecycleStage
* stage timestamp if verified

Do not infer stage from tags if lifecycleStage exists.

Stuck

Source priority:

1. dedicated lifecycle stage timestamp
2. stage progression event
3. updatedAt only if it accurately reflects stage movement
4. unavailable

Do not calculate stuck from createdAt unless that is explicitly the only stage timestamp and documented as approximate.

SDR

Source:

* follow-up sequence enrollments
* sequence worker logs/outbound messages
* sender health table/service
* sequence metadata from Wave 6

Do not infer sends from template presence.

Conversion

Source:

* Wave 8 analytics APIs / analytics_events

Do not mix in audit logs unless Wave 8 explicitly uses them.

GHL

Source:

* Wave 7 GHL sync APIs
* ghlActivityLog
* circuit breaker state

Do not create another circuit breaker.

Compliance

Source:

* Wave 1B/Wave 7 contactability/channel safety summaries

Do not duplicate enforcement logic.

Launch readiness

Source:

* direct config/database/service checks only

No mocked green statuses.

Kill Lines

Stop and report before build if:

* OperatorDashboard tab architecture cannot be identified.
* Wave 8 analytics APIs are missing and the task would need to recreate Wave 8.
* Wave 7 GHL sync APIs are missing and the task would need to recreate Wave 7.
* Channel Safety data source cannot distinguish blocked reasons and the implementation would guess.
* lifecycle stuck timestamp cannot be verified and the implementation would fake stuck counts.
* SDR send counts would be inferred from templates instead of actual send/log records.
* launch readiness signal cannot be verified but would be shown green.
* Force Sync action would send a communication or enroll a workflow.
* feature flag toggles do not already have a safe mutation pattern.
* adding the dashboard requires a broad refactor of OperatorDashboard.
* dashboard tables would expose raw phone, email, names, message bodies, notes, or statement details.
* any route would be exposed without admin/manager guard.
* any endpoint would mutate state except verified safe force-sync or existing safe feature-flag toggle.
* implementation would change contactability, consent, offer routing, sequence enrollment, GHL sync behavior, or analytics collection.
