# 2. CORE AUDIT RULES

## Evidence over assumptions

Every material technical claim in the knowledge brief must be backed by evidence where practical:

- file path
- function/class/table name
- approximate line range
- schema/migration
- route
- worker/job name
- environment variable
- test
- DB query result
- integration configuration

Use:

**CONFIRMED** — proven directly from code/schema/runtime evidence.

**PARTIALLY CONFIRMED** — some evidence exists but ownership/behavior remains incomplete.

**UNVERIFIED** — documentation/task language claims it, but code/runtime evidence is insufficient.

**CONTRADICTED** — repository/runtime evidence conflicts with the presumed architecture.

Do not convert assumptions into facts.

# KILL LINES

STOP and report rather than proceeding if:

- the audit would require mutating production data;
- a command could send email/SMS;
- a command could enroll contacts;
- an enrichment/crawler command would incur external requests or costs;
- an import script could write records;
- a migration or `db:push` is required;
- production environment cannot be distinguished from development;
- secrets would need to be printed;
- a destructive cleanup is proposed;
- you discover an active mass-send path that appears unsafe;
- you discover evidence of consent/opt-out bypass;
- you discover a migration/schema mismatch that makes further DB assumptions unsafe.

Document the blocker and continue auditing other read-only areas.
