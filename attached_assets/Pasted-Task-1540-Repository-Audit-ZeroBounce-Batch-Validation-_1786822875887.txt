Task #1540 Repository Audit — ZeroBounce Batch Validation

Audit target: origin/main at d9bf0b783a1fd8a154c5e19a48167365087cb53b
Audit mode: Read-only static inspection
Verdict: NEEDS REVISION BEFORE BUILD

Executive verdict

Task #1540 identifies a real filter regression, but it is not build-ready as written. The five server-side predicates and the DataQuality row-action guard do omit the new unvalidated status. However, the task overstates the affected current population: migration 0135_contacts_email_status_unvalidated_default.sql explicitly changes only the default for newly inserted contacts and intentionally leaves existing rows unchanged. The current live distribution cannot be inferred from the repository.

More importantly, adding campaign totals to the existing setImmediate loop would create an unreliable tracker. The current implementation can convert provider/configuration failures into terminal unknown contact statuses, lose work on restart, run overlapping batches against the same contacts, spend duplicate credits, and double-count or lose campaign totals. Those issues must be corrected before the UI may describe the process as a campaign or report completion.

Findings by priority

P0 — false validation completion on provider failure

Files:

server/services/sdr/zerobounce.ts

server/routes/contacts.ts:2119–2151

server/routes/contacts.ts:2184–2219

No key, a non-2xx response, timeout, or network exception returns an ordinary ZeroBounceResult with status: "unknown". Both the batch and manual endpoints persist that result and present the operation as completed. Because #1540's proposed selector includes only NULL, active, and unvalidated, the contact will not be retried.

Required correction: Introduce a discriminated provider outcome. A completed provider decision may update the contact (valid, unsafe, unverified, or an explicitly supported provider result). Configuration absence and transport/provider faults must be retryable failures and must not change the prior contact status. They must be counted separately from validation results.

P0 — duplicate calls and corrupt campaign accounting

Files:

server/routes/contacts.ts:2057–2161

server/services/zerobounce-daily-limiter.ts

server/storage/misc.ts:247–263

The limiter atomically reserves a daily unit, but nothing atomically claims a contact for a specific run. Overlapping requests can select the same rows before either updates them. A singleton JSON campaign object updated with read-modify-write would also lose increments when two completions race; setSystemSetting() atomically replaces a value but does not atomically merge counters.

Required correction: Use a durable queue job and a database-backed unique contact claim. At minimum, enforce one active campaign/run and atomically claim each contact. Do not implement campaign totals as an unversioned singleton JSON accumulator.

P1 — real unvalidated filter regression

Files:

server/routes/contacts.ts:254, 308, 344, 2088, 2093

client/src/pages/dashboard/DataQuality.tsx

Use one shared canonical definition, not five hand-maintained SQL fragments:

archived_at IS NULL
AND email_status IN (NULL/legacy-active/unvalidated semantics)
AND email is a real, syntactically eligible address
AND email is not an internal/synthetic placeholder

SQL should express the status portion as email_status IS NULL OR email_status IN ('active', 'unvalidated'). The summary, scan, batch selection, campaign denominator, and live remaining count must all use the same full eligibility definition.

P1 — synthetic and ineligible addresses consume credits

Files:

server/routes/imports.ts:1829–1835

server/routes/contacts.ts:2084–2105

The import path deliberately stores unique .internal placeholder addresses. Nonblank-email filtering admits them. The explicit contactIds path bypasses even the archived/status/nonblank predicates and does not deduplicate IDs.

Required correction: Add a canonical email-validation eligibility function/predicate that rejects placeholders, internal/test domains, malformed syntax, archived contacts, and terminal statuses. Apply it to normal selection, explicit IDs, quality counts, and campaign remaining. Deduplicate explicit IDs and require an explicit revalidation mode for already-final contacts.

P1 — campaign tracker design is not durable

The proposed zerobounce_campaign_progress JSON key has no campaign ID, immutable starting cohort, reset/restart semantics, per-contact idempotency, failure recovery, or concurrency control. Completion-only updates cannot represent a crashed or interrupted run.

Required correction: A migration is warranted. Recommended minimum model:

zerobounce_validation_campaigns: campaign ID, status, normalized filter/cohort definition, initial eligible total, created/started/completed timestamps, actor, daily limit snapshot.

zerobounce_validation_runs: run ID, campaign ID, durable job ID, state, counters, heartbeat, stop reason, timestamps.

zerobounce_validation_attempts: campaign/run/contact IDs, unique claim, provider outcome, credit reservation state, retryability, error code, timestamps.

If schema work remains out of scope, #1540 must be narrowed to the filter/provider hotfix and must not claim campaign-level reliability.

P2 — progress and UI semantics are incomplete

Incremental writes every ten contacts are useful, but the record needs status, attempted, providerCompleted, retryableErrors, skipped, creditsReserved, lastHeartbeatAt, and stopReason. The final invariants must reconcile exactly with the queued cohort. A process crash must be visible as stale/interrupted rather than “in progress” forever.

The UI should:

Treat null, active, and unvalidated consistently in the badge and Validate action.

Show live numeric progress, stale/interrupted state, retryable errors, and budget stop.

Use the server's canonical initial cohort and remaining counts.

Calculate estimated days with ceiling division and label it as a minimum at the configured daily limit.

At 155,660 contacts and 500 validations/day, the theoretical minimum is 312 days, before retries or non-working days. For launch readiness, a prioritized outbound cohort should be validated first instead of blocking on the entire database.

Corrected build scope

Build 1540A — correctness hotfix (must land first)

Centralize the eligible-unvalidated predicate and use it in the five server locations, batch candidates, explicit-ID candidates, campaign totals, and remaining counts.

Add unvalidated to the DataQuality button and badge behavior.

Exclude synthetic/internal/test/malformed emails.

Change ZeroBounce outcomes so missing configuration and provider/transport errors remain retryable and never overwrite contact status.

Preflight the correctly cased ZEROBOUNCE_API_KEY before claiming a local credit or starting a run.

Add route/service tests with a fake provider. No real provider traffic.

Build 1540B — durable batch campaign

Replace setImmediate with a durable BullMQ job.

Add campaign/run/attempt persistence and unique contact claims.

Enforce one active run per campaign and idempotent retries.

Track reserved attempts separately from confirmed provider responses; do not call local reservations “credits consumed” unless provider billing semantics prove that equivalence.

Add heartbeat, restart recovery, budget-stop, cancellation, and terminal reconciliation.

Add the campaign read endpoint backed by persisted campaign/run state.

Build 1540C — tracker UI

Add the campaign card only after 1540B's API contract is stable.

Show cohort total, completed provider decisions, retryable failures, remaining eligible, daily budget, minimum days, last heartbeat, and run state.

Disable duplicate starts while a run is active and expose a safe resume action for interrupted work.

Gate checks and tests

Gate

Required proof

G-01 Filter parity

Summary, scan, batch, explicit IDs, campaign total, and remaining all return the same eligible set for the same filter.

G-02 Status matrix

NULL, active, and unvalidated are eligible; final blocked/valid statuses are not, absent explicit revalidation.

G-03 Placeholder exclusion

.internal, no-email-*, blank, malformed, and configured test domains consume zero provider calls and zero credits.

G-04 Failure safety

Missing key, 401/403/429/5xx, timeout, invalid JSON, and network exception leave the original contact status unchanged and remain retryable.

G-05 Provider result mapping

Valid, invalid/abuse/spamtrap/do-not-mail, catch-all, and provider-unknown map to the documented internal statuses.

G-06 Concurrency

Simultaneous batch starts cannot claim the same campaign/contact twice or exceed the daily limiter.

G-07 Restart recovery

Kill the worker mid-run; the durable job resumes or terminates visibly without losing/doubling attempts.

G-08 Accounting invariant

Every claimed contact is exactly one of provider-completed, retryable-failed, skipped, or pending; totals reconcile after success, budget exhaustion, cancellation, and crash.

G-09 Incremental progress

Polling observes monotonic counters and heartbeats; stale jobs are explicitly marked.

G-10 UI

Button/badge support explicit unvalidated; card renders not-started/running/budget-stopped/interrupted/completed states.

G-11 No live I/O

All automated tests use fake transports and cannot reach ZeroBounce.

G-12 Regression scan

CI fails if a new unvalidated-email predicate diverges from the canonical helper/query builder.

Kill lines

STOP if unvalidated is omitted from any eligible count, scan, batch, explicit-ID path, campaign denominator, or remaining query.

STOP if missing credentials or provider/transport failure changes contacts.email_status to unknown or any terminal result.

STOP if a retryable failure disappears from the next eligible batch.

STOP if two batches can validate the same campaign/contact concurrently.

STOP if a restart can strand a job as permanently “in progress” or silently lose claimed work.

STOP if campaign totals use a non-atomic JSON read-modify-write accumulator.

STOP if placeholder/internal/test/malformed addresses can reserve credits or reach the provider.

STOP if explicit IDs bypass eligibility, deduplication, archived-state, or status rules.

STOP if creditsConsumed actually means only locally reserved attempts without that distinction being explicit.

STOP if counts shown by summary, scan, campaign total, and remaining use different predicates.

STOP if a real ZeroBounce request is made during tests or static verification.

STOP if completion is claimed without runtime proof that migration 0135 is applied and the live cohort has been measured.

Runtime verification — separate from static findings

The following cannot be confirmed from repository code and must be verified against the deployed environment using read-only checks before starting a real campaign:

Deployed SHA equals the intended green commit and migrations 0133–0135 are applied.

Actual counts grouped by email_status, including NULL, active, unvalidated, unknown, unverified, valid, and unsafe/bad statuses.

Exact count of real eligible addresses after excluding synthetic/internal/test/malformed emails.

Correctly cased ZEROBOUNCE_API_KEY is visible to the running worker process; report only configured/not configured, never the value.

Current daily limit and today's locally reserved count.

Whether any batch job is already active or stale in any process.

Worker/BullMQ connectivity and restart recovery behavior.

Provider account balance/quota and a deliberately authorized sandbox verification, if the provider supports one. Do not use a real customer address for this check.

The actual live launch cohort and projected time/cost; do not infer it from the old 155K estimate.

Final recommendation

Do not ship #1540 exactly as pasted. Land 1540A as the immediate correctness fix, then build 1540B before representing the process as a durable multi-day campaign, and add 1540C last. The existing global outbound pause should remain active throughout validation work. Repository source was not modified during this audit.
