## Lifecycle and concurrency proof required

| Scenario                                         | Required behavior                                          |
| ------------------------------------------------ | ---------------------------------------------------------- |
| Two workers apply conflicting events             | Row lock or fencing permits one ordered projection result  |
| Duplicate event key                              | One logical event and one projection transition            |
| Older positive event arrives late                | Persist as history without re-enabling a newer restriction |
| Equal-time opt-in and opt-out                    | Restrictive event wins deterministically                   |
| Future-dated public event                        | Rejected or bounded by server policy                       |
| Event insert succeeds but projection fails       | Entire transaction rolls back                              |
| Projection write succeeds but event insert fails | Entire transaction rolls back                              |
| Phone changes after PEWC consent                 | Old phone evidence cannot authorize the new phone          |
| Runtime attempts audit UPDATE/DELETE             | Database rejects it                                        |
| Maintenance procedure executes                   | Explicitly authorized, bounded and auditable               |
| Email opt-out                                    | Does not suppress otherwise eligible SMS                   |
| SMS STOP                                         | Blocks SMS/automated phone without inventing email opt-out |
| Global DNC                                       | Blocks every automated channel                             |
| Deliverability bounce                            | Changes reachability, not historical consent               |
| Legacy contradictory state                       | Fails closed and enters inventory/manual-review state      |

## Scope closure

The two existing follow-on tranches remain correctly separate:

* Universal provider/sink enforcement, manual-route authorization and contactability dominance.
* Durable workflow occurrences, retries, reconciliation and truthful provider outcomes.

They are still release-blocking for outbound unpause, but they are **not reasons this core tranche failed**.

This core tranche failed because consent authority itself still excludes wizard/SDR writers and leaves subject cardinality, purpose projections, event precedence, PEWC phone binding, consent-versus-deliverability separation and database-role enforcement unresolved. Those corrections belong in the already-existing first tranche.
