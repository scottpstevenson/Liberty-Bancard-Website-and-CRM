# #1599 — Prevent repeated zero-yield Serper merchant searches

## Data model

Add to `sdr_merchants`:

- `last_serper_checked_at TIMESTAMPTZ`
- `serper_no_result_attempts INT NOT NULL DEFAULT 0`
- `serper_next_eligible_at TIMESTAMPTZ`
- `serper_last_outcome TEXT`
- `serper_last_reason_code TEXT`
- Optional claim/lease fields if atomic claiming cannot be implemented without them

Use `serper_no_result_attempts`, not generic `serper_attempts`, because provider failures must not make a merchant appear permanently unfindable.

Add an index supporting the eligibility query.

## Outcome rules

### Completed 200 response with no usable merchant match

- Increment `serper_no_result_attempts`
- Set `last_serper_checked_at`
- Set `serper_last_outcome='no_result'`
- Apply progressive cooldown:
  - first no-result: 24 hours
  - second: 7 days
  - third and later: 30 days

### Useful result found

- Reset `serper_no_result_attempts=0`
- Set `last_serper_checked_at`
- Set `serper_last_outcome='matched'`
- Apply a cooldown even when the result is partial, so missing fields do not cause immediate reselection
- Clear or advance `serper_next_eligible_at` according to policy

### Provider/control failure

Examples: global Serper disabled, circuit open, 401/403, 429, timeout, network error, or 5xx.

- Do not increment merchant no-result attempts
- Do not classify the merchant as unfindable
- Record the normalized provider/control outcome
- Defer retry according to the global #1597 circuit/budget policy

## Atomic candidate selection

Candidate claiming must prevent two workers from selecting the same merchants concurrently.

Use an atomic claim mechanism such as a transaction with `FOR UPDATE SKIP LOCKED`, or an equivalent lease/token design.

Eligibility requires all of:

- Merchant is missing at least one target field
- `do_not_contact_flag IS NOT TRUE`
- `serper_next_eligible_at IS NULL OR <= NOW()`
- No active claim/lease
- Canonical #1597 Serper authority permits the operation

The global Serper decision must be rechecked immediately before provider I/O.

## Deployment/backfill

Because the existing 251 merchants have documented repeated zero-yield attempts:

- Do not allow all 251 to become immediately eligible after migration.
- Seed them into a temporary cooldown or explicitly excluded cohort.
- Record the affected count.
- Release only a small capped canary after #1597 confirms provider readiness.

Do not fabricate historical attempt counts that were never stored.

## Manual requeue

If included:

- Admin/manager authorization required
- Non-empty reason
- Actor, merchant ID, correlation ID, and timestamp audited
- Clear merchant cooldown/no-result state only
- Must not bypass the global Serper control, circuit, or quota budget
