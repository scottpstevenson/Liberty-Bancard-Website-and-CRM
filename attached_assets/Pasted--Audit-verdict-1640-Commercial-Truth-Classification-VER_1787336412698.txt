## Verified root cause

The repository has grown several independent data axes:

* provenance and acquisition source;
* consent and reachability;
* lifecycle/readiness/status;
* test/demo conventions embedded in names and emails;
* event and KPI aggregations;
* direct writers for commercial entities.

There is no reviewed commercial-truth authority joining those axes. Consequently, test or unproven data is included by default in metrics and candidate selection, while cleanup relies on destructive filename/email heuristics.

The task correctly identifies the need for commercial truth, but it incorrectly models `import` and `system` as commercial classes and does not distinguish root subjects, immutable events, and derived aggregates.

# P0 corrections

## P0-1 — Restore enforceable GitHub CI first

**Evidence**

* `.github/workflows/` is empty.
* Current commit explicitly deletes the only workflow.
* Current SHA has no workflow runs.

**Exact fix**

1. Restore `.github/workflows/wave12-ci.yml`.
2. Do not merely restore the deleted workflow verbatim—it ran only a subset of the 40-suite manifest and lacked a Redis service.
3. Add:

   * static job: typecheck, migration integrity, tracked-file scan, compliance scan, classification static tests;
   * integration job: disposable PostgreSQL and Redis, provider-denial environment, classification integration tests;
   * execution driven from the capability manifest or a manifest-owned runner.
4. Obtain a GitHub credential/app permission capable of updating workflow files instead of deleting the workflow to unblock pushes.
5. After a successful run, configure a `main` ruleset requiring the exact static and integration check names.

## P0-2 — Correct the classification vocabulary

The proposed values contradict the task’s own requirement not to conflate provenance with commercial truth:

* `import` is provenance. Imported contacts can be legitimate production leads.
* `system` describes the writer/origin. System-generated snapshots may represent production revenue.

**Exact fix**

Use:

```text
production | test | demo | synthetic | unknown
```

Keep these separate:

```text
origin/source: csv_import | public_form | ghl_sync | system_derived | ...
commercial class: production | test | demo | synthetic | unknown
```

An unreviewed import receives `record_class=unknown` with import provenance. It may transition to production only through evidence-backed approval. System-generated facts inherit or summarize the class of their source records; they are not automatically non-production.

## P0-3 — Define subject, event, and aggregate semantics

The task’s listed entities are incomplete. The live schema contains 170 `pgTable` definitions.

Missing material entities include:

* `companies`, `businesses`, `master_leads`;
* `sdr_lead_state`, `sdr_channel_attempts`, `communication_events`;
* documents, statement proposals/reviews, rate-review requests;
* residual imports and import rows;
* MID daily stats, health scores, chargebacks;
* equipment orders/shipments and other merchant facts.

A single class on `daily_funnel_metrics`, `residual_reports`, `agent_payouts`, or executive snapshots is insufficient because these rows can aggregate mixed source classes.

**Exact fix**

* Root subjects carry current commercial class and classification version.
* Operational events carry immutable `record_class_at_event`, authority version, and source subject.
* Aggregates are built from filtered production inputs and store:

  * policy version;
  * source-row count;
  * excluded non-production count;
  * unknown count;
  * source high-water/lineage.
* Mixed or unresolved inputs must fail closed or appear in reconciliation—not be labelled production after aggregation.

## P0-4 — Enforce class at the canonical outbound boundary

Filtering cohort queries alone is bypassable. Direct-by-ID, worker, toolkit, manual-send, and future paths can still reach providers.

At the same time, blanket production-only enforcement would break legitimate transactional confirmations: live routes call `evaluateContactability()` with `campaignType: "confirmation"` for newly submitted, potentially still-unknown contacts.

**Exact fix**

Create a separate `CommercialClassificationAuthority.authorizeUse()` decision with a required purpose:

```text
marketing_outreach
commercial_reporting
financial_payout
transactional_response
internal_test
```

For marketing/outreach, only `production` is allowed. Invoke this authority at the unavoidable contactability/dispatch boundary before existing consent checks. Return a stable denial such as `COMMERCIAL_CLASS_NOT_PRODUCTION`.

Transactional responses may use a separately verified inbound/application context, but must not enter production KPIs. Production classification must never override a consent or reachability denial.

## P0-5 — Disable heuristic and broad destructive cleanup

Current code violates the task kill lines:

* `server/routes/admin.ts:5000-5207` hard-deletes contacts and related rows based on email/name patterns.
* `server/storage/prospects.ts:119-136` archives lists whose names contain `demo`, `test`, `sample`, `fake`, or `internal`.
* `scripts/purge-test-contacts.ts:21-116` deletes by test email domains.
* `scripts/cleanup-test-data.ts` and `scripts/cleanup-smoke-contacts.ts` use similar patterns.
* `scripts/cleanup-demo-data.ts:18-75` deletes **all enrollments, all tasks, and all deals**.
* Current roadmap/checklist documentation instructs operators to run these utilities.

**Exact fix**

* Immediately return `410 Gone` from production cleanup endpoints and remove their UI actions.
* Make destructive test cleanup scripts refuse execution unless:

  * `NODE_ENV=test`;
  * `TEST_DATABASE_URL` is supplied;
  * it resolves to a different database from `DATABASE_URL`.
* After the authority exists, production cleanup may target only an approved classification-command manifest containing explicit IDs and event evidence.
* Replace existing production cleanup scripts with read-only reconciliation reports.
* Update conflicting documentation.

## P0-6 — Repair migration replay before adding #1640 schema

Static integrity currently passes, but its conclusion is false:

* `0000_faulty_gwen_stacy.sql` creates `contacts` and `deals`.
* Journal index 109, `0109_fearless_starhawk.sql`, later creates those tables again using bare `CREATE TABLE`.
* `server/db-migrate.ts` only baselines entries through `when=1777739833710`.
* The checker nevertheless reports `0109` safe through that baseline.

A fresh replay would reach both definitions. A legacy database detected merely by the existence of `contacts` can also reach `0109` without it being baselined.

**Exact fix**

Without editing applied SQL history:

1. Treat `0109` as an explicit bootstrap snapshot.
2. For a genuinely empty database, apply the snapshot once, record its hash/HWM, then apply only later migrations.
3. For an existing database with no reliable migration ledger, refuse startup unless a schema fingerprint or explicitly authorized baseline is supplied; `contacts` existing is not sufficient proof.
4. Update `check-migration-integrity.ts` so:

   * Rule 8 verifies actual runner behavior rather than asserting safety;
   * new duplicate timestamps are failures;
   * every new entry must be strictly greater than the dynamic current maximum, not only the frozen `1793200000000` baseline.
5. Add clean-bootstrap and upgraded-database replay tests against disposable Postgres.
