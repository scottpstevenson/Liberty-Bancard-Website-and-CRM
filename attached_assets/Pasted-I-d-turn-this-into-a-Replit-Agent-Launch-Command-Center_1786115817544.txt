I’d turn this into a Replit Agent “Launch Command Center” prompt that forces it to audit first, consolidate the backlog, rank by launch impact, and then execute in controlled sprints rather than creating more overlapping tasks.

PRODUCTION LAUNCH COMMAND CENTER — AUDIT, CONSOLIDATE, PRIORITIZE & EXECUTE

We are preparing this application for production launch within the coming days.

Before creating additional tasks or making unnecessary changes, perform a complete audit of the existing application, codebase, database, queued tasks, suggested tasks, known issues, features, UI, dashboards, integrations, and deployment requirements.

The primary objective is:

Consolidate everything → eliminate overlap → identify launch blockers → organize the remaining work into prioritized sprints → execute toward a stable production release.

Do not create another large list of disconnected recommendations.

We need one authoritative launch plan and one consolidated backlog.

⸻

PHASE 1 — DISCOVER EVERYTHING

First, inspect the entire project.

Review:

* Existing queued tasks
* Suggested tasks
* TODOs
* Known bugs
* Replit Agent tasks/recommendations
* Development notes
* Code comments/TODO markers
* Incomplete features
* Partially implemented features
* Database/schema
* APIs
* Backend services
* Frontend
* Dashboards
* Forms
* Tables
* Filters
* Search
* Buttons/actions
* Navigation
* Tabs
* Notifications
* Authentication
* Authorization
* Integrations
* Automations
* Scheduled/background jobs
* Environment/configuration
* Deployment configuration
* Logging/error handling
* Existing tests

Also identify anything that appears to have been implemented multiple times.

Do NOT begin by creating new features.

First determine exactly what already exists.

⸻

PHASE 2 — CONSOLIDATE THE ENTIRE BACKLOG

Create a single master inventory of all:

* Queued tasks
* Suggested tasks
* Bugs
* Improvements
* Technical debt
* Security issues
* UX issues
* Data issues
* Missing functionality
* Deployment requirements

Then aggressively deduplicate it.

If multiple tasks describe substantially the same problem, combine them into ONE authoritative task.

Example:

Instead of:

* Fix dashboard metrics
* Check dashboard data
* Validate dashboard numbers
* Repair dashboard API
* Make dashboard accurate

Create:

Validate & Harden Dashboard Data Pipeline

With the individual requirements underneath it.

⸻

PHASE 3 — FIND OVERLAP

Look specifically for overlapping implementation across the application.

Identify:

* Duplicate components
* Duplicate pages
* Duplicate forms
* Duplicate APIs
* Duplicate services
* Duplicate database queries
* Duplicate business logic
* Duplicate utilities
* Duplicate hooks
* Duplicate notifications
* Duplicate modals
* Duplicate tables
* Duplicate dashboards
* Duplicate workflows
* Multiple implementations of the same feature
* Repetitive UI patterns that should share components

Determine whether each duplicate should be:

KEEP
Best/current implementation.

MERGE
Combine functionality.

REFACTOR
Move shared behavior into reusable architecture.

REMOVE
Obsolete/redundant implementation.

Do not refactor merely for stylistic perfection.

Prioritize refactoring when duplication creates:

* Bugs
* Conflicting behavior
* Maintenance risk
* Data inconsistencies
* User confusion
* Security issues
* Launch risk

⸻

PHASE 4 — FULL CODE AUDIT

Audit the complete codebase for production readiness.

Look for:

* Bugs
* Runtime errors
* Build errors
* Type errors
* Broken imports
* Dead code
* Unused components
* Corrupted or malformed code
* Conflicting implementations
* Race conditions
* Missing validation
* Weak error handling
* Silent failures
* Broken async behavior
* API failures
* Incorrect state handling
* Authentication vulnerabilities
* Authorization problems
* Exposed secrets
* Unsafe database operations
* Missing database constraints
* Broken relationships
* N+1 queries
* Excessive requests
* Performance bottlenecks
* Memory/resource issues
* Hard-coded demo values
* Mock responses
* Development bypasses
* Debug code
* Console errors

Do not rewrite stable code simply because another architecture might be cleaner.

We are optimizing for:

Reliability + Security + Accuracy + Maintainability + Launch Speed.

⸻

PHASE 5 — DATA INTEGRITY AUDIT

Validate that every dashboard and UI surface displays data from the correct authoritative source.

Trace:

Database → Backend/API → Business Logic → Frontend → Dashboard/UI

Verify:

* Correct calculations
* Correct aggregation
* Correct filters
* Correct date ranges
* Correct account/user scoping
* Correct permissions
* Correct statuses
* Correct totals
* Correct empty states
* No fake/demo metrics
* No stale hard-coded values
* No duplicate counting
* No missing records

For every major dashboard metric, identify its source of truth.

If two parts of the application calculate the same metric differently, consolidate them around ONE authoritative calculation.

⸻

PHASE 6 — COMPLETE UI / UX FUNCTIONAL AUDIT

Systematically test every major application surface.

Audit every:

* Page
* Dashboard
* Tab
* Navigation item
* Sidebar item
* Button
* Dropdown
* Menu
* Modal
* Form
* Input
* Search field
* Filter
* Sort control
* Pagination control
* Table
* Chart
* Link
* Notification
* Toast
* Upload
* Download/export
* Create action
* Edit action
* Delete action
* Bulk action
* Settings control

For each interactive element verify:

1. It renders correctly.
2. It performs the expected action.
3. It talks to the correct backend functionality.
4. Success states work.
5. Failure states work.
6. Loading states work.
7. Permissions work.
8. Data updates correctly afterward.
9. The UI does not require unnecessary refreshes.
10. It does not duplicate another interface unnecessarily.

No dead buttons.

No placeholder buttons.

No controls that appear functional but do nothing.

⸻

PHASE 7 — CONSOLIDATE THE USER EXPERIENCE

Audit the app for repetitive or conflicting interfaces.

Examples:

If there are multiple interfaces for essentially the same:

* Contact management
* Company management
* Tasks
* Tickets
* Notifications
* Account management
* Settings
* Search
* Filters
* Reporting

Determine whether they should be consolidated.

Prefer:

One obvious workflow for each major user objective.

Do NOT remove intentionally different interfaces simply because they look similar.

Consolidate only when doing so improves:

* Clarity
* Consistency
* Reliability
* Maintainability
* User experience

⸻

PHASE 8 — CREATE THE MASTER LAUNCH BACKLOG

After completing discovery, create ONE consolidated backlog.

Every item must contain:

Task

Clear description.

Problem

What is wrong or incomplete?

Evidence

What did you find that proves this work is required?

Why It Matters

Why should we care?

Launch Impact

What happens if we launch without fixing it?

Improvement

What will completing it improve?

Proof

How will we objectively verify that it works?

Dependencies

What must happen before this?

Effort

Estimate:

* XS: <1 hour
* S: 1–3 hours
* M: 3–8 hours
* L: 1–2 days
* XL: 2+ days

Priority

Assign:

P0 — LAUNCH BLOCKER
Cannot safely launch without fixing.

P1 — LAUNCH CRITICAL
Should be completed before production launch.

P2 — IMPORTANT
Important for a polished/stable product but can follow immediately after launch if necessary.

P3 — POST-LAUNCH
Optimization, cleanup, enhancement, or technical debt that should not delay launch.

⸻

PHASE 9 — ORGANIZE INTO SPRINTS

Organize the consolidated backlog into execution sprints.

SPRINT 0 — BLOCKERS

Only P0 issues.

Examples:

* Security vulnerabilities
* Authentication failures
* Data corruption risk
* Broken deployment
* Critical workflows failing
* Incorrect production data
* Destructive bugs

Goal:

Make production launch technically safe.

⸻

SPRINT 1 — CORE PRODUCT HARDENING

Focus on:

* Bugs
* Data integrity
* Dashboard accuracy
* Broken workflows
* Forms
* Buttons
* CRUD
* Navigation
* Tabs
* Authentication
* Permissions
* Notifications
* Critical integrations

Goal:

Every core workflow works end-to-end.

⸻

SPRINT 2 — CONSOLIDATION & UX

Focus on:

* Duplicate UI
* Conflicting interfaces
* Duplicate logic
* Reusable components
* Navigation consistency
* Empty states
* Loading states
* Error states
* UX consistency

Goal:

Make the product feel like one cohesive application rather than accumulated features.

⸻

SPRINT 3 — PRODUCTION HARDENING

Focus on:

* Security
* Error handling
* Logging
* Performance
* Database integrity
* API reliability
* Environment configuration
* Background jobs
* Webhooks
* Integration resilience
* Production configuration

Goal:

Make the system resilient enough for real production usage.

⸻

SPRINT 4 — FINAL QA & DEPLOYMENT

Perform:

* Full regression testing
* Production build
* End-to-end testing
* Permission testing
* Responsive testing
* Database verification
* Integration testing
* Deployment verification
* Post-deployment smoke testing

Goal:

Prove the application is ready.

⸻

SPRINT 5 — IMMEDIATE POST-LAUNCH

Move non-blocking work here.

Include:

* Nice-to-have UX improvements
* Deeper refactoring
* Performance optimizations
* Additional reporting
* Minor UI improvements
* Technical debt
* Future enhancements

Do NOT allow P2/P3 work to unnecessarily delay production.

⸻

PHASE 10 — ESTIMATE THE LAUNCH

Before executing major changes, report:

Total Remaining Tasks

After deduplication.

Tasks Removed Through Deduplication

Show what was merged/eliminated.

P0 Count

P1 Count

P2 Count

P3 Count

Estimated Engineering Effort

Provide realistic estimates by sprint.

Critical Path

Identify the smallest sequence of tasks required to launch.

Parallelizable Work

Identify tasks that can safely happen simultaneously.

Launch Confidence

Give:

RED
Not currently launchable.

YELLOW
Launchable after identified blockers.

GREEN
Production-ready.

Explain the rating with evidence.

⸻

PHASE 11 — EXECUTION RULES

Once the audit and plan are established, execute systematically.

Follow this order:

P0 → P1 → P2 → P3

Within each priority:

1. Data integrity
2. Security
3. Broken functionality
4. Core workflows
5. Integration reliability
6. UX
7. Performance
8. Cleanup/refactoring

After completing each task:

* Test it.
* Verify the expected behavior.
* Confirm nothing else broke.
* Mark it complete.
* Record what changed.
* Update remaining effort.

Do NOT continuously generate new tasks without consolidating them into the master backlog.

⸻

PHASE 12 — PREVENT SCOPE CREEP

We need to launch.

Therefore:

Do not turn production preparation into an endless rewrite.

For every proposed change ask:

Does this materially improve launch safety, functionality, data accuracy, security, reliability, or user experience?

If NO:

Move it to post-launch.

Do not delay production for architectural perfection.

⸻

DEFINITION OF DONE

The application is considered launch-ready when:

* P0 backlog = ZERO
* P1 backlog = ZERO or explicitly accepted
* Production build succeeds
* Deployment succeeds
* Authentication works
* Permissions work
* Database integrity is verified
* Dashboards show correct production data
* Core workflows work end-to-end
* All important tabs work
* All important buttons work
* Forms work
* CRUD works
* Notifications work
* Integrations required for launch work
* No obvious duplicate/conflicting interfaces remain
* No demo/test data remains
* No fake dashboard data remains
* No critical console/runtime errors remain
* No known critical security vulnerabilities remain
* Error/loading/empty states work
* Post-deployment smoke tests pass

⸻

REQUIRED FIRST RESPONSE

Do NOT immediately start rewriting large portions of the application.

First return a Launch Readiness Audit containing:

1. Executive Summary
2. Current Launch Confidence — RED / YELLOW / GREEN
3. What Already Works
4. What Is Broken
5. What Is Incomplete
6. Duplicate / Overlapping Work Found
7. Tasks Consolidated
8. Tasks That Can Be Deleted
9. P0 Launch Blockers
10. P1 Launch-Critical Tasks
11. P2 Important Tasks
12. P3 Post-Launch Tasks
13. Sprint Plan
14. Estimated Hours / Days Per Sprint
15. Critical Path to Production
16. What Each Sprint Will Prove or Improve
17. Risks
18. Recommended Launch Sequence

For every recommendation, explain WHY it is necessary and WHAT measurable result will prove it is complete.

Then begin execution with the highest-priority launch blockers.

The goal is not to create more work.

The goal is to determine the minimum complete, secure, reliable, polished version of the application that we can confidently put into production within the coming days, while creating a clear post-launch path for everything that does not need to block deployment.

This structure is especially useful because it tells Replit to stop treating every suggestion as a new task. It has to first prove there is a problem, merge duplicates, estimate the work, and distinguish “must launch” from “would be nice.”
