## Replacement acceptance criteria

- Exactly one active source-to-canonical writer owns each Sunbiz source namespace during the controlled run. Existing claims/links reconcile or are classified for review; no automatic business-ID reassignment.
- Every **claimed** occurrence reaches a durable current state (terminal, retry due, or review); every immutable attempt remains auditable. Counts reconcile to the frozen **enumerated scope**, and unprocessed rows remain visible as unprocessed.
- Replaying the same occurrence/hash does not create a second business, link, or terminal decision. Changed source evidence produces a versioned decision; lease loss/crash is recoverable without an orphaned canonical row.
- Matching requires corroborated operating identity. Shared domain/phone, ambiguous legal entity/location, and fuzzy name cases go to review. DBPR/test/synthetic sources cannot become outreach-eligible through new lineage.
- A newly created `canonical` business with supported location/vertical evidence can enter a **new** ROI selection; it does not mutate an immutable cohort. An unresolved source never receives invented geography or vertical certainty.
- The run's causality ledger shows zero materialization-origin contact, deal, GHL, campaign enrollment, or outreach writes. The protected legacy Sunbiz writer is verified disabled for the controlled cohort.
- Existing Sunbiz bootstrap UI/route/tests and #1998–#2001 regressions pass. Fresh and upgrade migration paths work in disposable Postgres and the Publish DDL approach is documented.
- Completion report separates code merged, deployed SHA, production schema verified, bounded activation authorized, production run executed, and runtime result. No production counts are claimed from dev data.
