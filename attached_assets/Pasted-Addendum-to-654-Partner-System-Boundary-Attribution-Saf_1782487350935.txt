Addendum to 654 — Partner System Boundary + Attribution Safety Corrections

Apply these corrections before building Wave 11.

Do not rewrite the whole plan. This addendum tightens the confirmed preflight findings.

⸻

1. Do not merge affiliate partners and org partners accidentally

The codebase has two separate systems:

Individual affiliate partners:
- table: partners
- referral code: partners.affiliateCode
- portal: /partner-portal
- dashboard endpoint: /api/partner/dashboard/:code
- commission source: partners.commissionPercent
- payout source: partners.totalPayouts
Organization partners:
- table: partner_organizations
- org code/slug: partner_organizations.slug
- portal: /partner-org/:slug
- dashboard endpoint: /api/partner-org/dashboard
- commission source: partner_organizations.commissionRate

Build must keep these systems distinct.

Do not assume partners.affiliateCode maps directly to partner_organizations.id.

Do not write contacts.partnerOrgId unless the referral code resolves to a real partner_organizations record.

For individual affiliate referrals, persist:

contacts.referralSource
contacts.promoCode
referrals table record via existing trackReferral()

For organization partner referrals, persist:

contacts.referralSource
contacts.promoCode
contacts.partnerOrgId
deals.partnerOrgId where supported

Kill line:

Stop if the implementation treats every affiliateCode as a partnerOrgId.

⸻

2. resolveReferralAttribution() must return partner type explicitly

The helper must distinguish:

type ReferralAttributionResult = {
  referralSource?: string;
  promoCode?: string;
  partnerType?: "affiliate_partner" | "partner_org" | "merchant_referral" | "none";
  partnerId?: number;
  partnerOrgId?: number;
  source: "url_ref" | "cookie" | "co_branded_proposal" | "merchant_referral" | "manual" | "none";
};

Rules:

* If code resolves to partners.affiliateCode, return partnerType = "affiliate_partner" and partnerId.
* If code resolves to partner_organizations.slug, return partnerType = "partner_org" and partnerOrgId.
* If both systems could match the same code, prefer the more explicit source or fail with a logged ambiguity. Do not guess silently.
* Normalize codes case-insensitively.
* Validate active/approved status before attribution.

⸻

3. Partner portal KPI target must be clarified

The existing PartnerPortal.tsx is for individual affiliate partners, not necessarily org partners.

For /partner-portal, KPI source should be:

partners table + referrals table + contacts/deals matched by promoCode / partnerId where supported

Do not show org-level partner_organizations.commissionRate in /partner-portal unless the authenticated partner is actually linked to an org.

For /partner-org/:slug, KPI source should be:

partner_organizations + contacts.partnerOrgId + deals.partnerOrgId + residual JOINs

If this wave only upgrades /partner-portal, final report must clearly state that /partner-org/:slug remains secondary or unchanged.

Kill line:

Stop if /partner-portal shows org-level data without verified partner-org membership.

⸻

4. Residual By Partner should be org-partner only unless affiliate linkage is proven

The confirmed JOIN path is:

residual_import_rows → deals.partnerOrgId → partner_organizations
merchant_residuals → deals.partnerOrgId → partner_organizations

That means the residual “By Partner” breakdown is reliable for organization partners only.

Do not include individual affiliate partners in residual breakdown unless there is a verified link from deal/residual row to partners.id or affiliate code.

Required copy:

By Partner reflects merchants linked to partner organizations through deal attribution.

If affiliate partner residuals are desired, report the schema gap instead of inventing the linkage.

8. Partner approval sequence trigger must target the right entity

The plan says partner approval handler enrolls the primary partner contact.

Clarify which system this applies to:

* If approving an individual partners record, enroll that partner/contact.
* If approving a partner_organizations record, enroll the primary org contact/admin only.
* Do not enroll every org member.
* Dedupe by partner/contact + partner-referral sequence family.

Kill line:

Stop if partner approval enrollment cannot identify a single primary contact safely.

9. Public form attribution must not break existing trackReferral()

trackReferral() currently inserts into the referrals table and is used fire-and-forget.

Do not remove it unless the new helper fully replaces that behavior.

Preferred:

resolveReferralAttribution() handles contact/deal attribution fields.
trackReferral() continues recording referral event rows.

Both should share normalized code resolution if feasible.

Final report must confirm referrals table behavior still works.
