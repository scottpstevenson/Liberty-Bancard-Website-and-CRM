What & Why

Liberty now has:

* Wave 1A contactability enforcement
* Wave 1B Channel Safety Matrix
* Wave 2 consent capture in progress/completed
* Wave 5 offer routing

Wave 6 creates the compliant SDR sequence architecture.

The goal is to build ten reusable campaign/sequence families, segmented by consent and lifecycle, while guaranteeing that a campaign enrollment or worker bug cannot bypass Wave 1A contactability.

This task creates sequence families, seed templates, enrollment guards, dashboard visibility, and offer-route sequence suggestions.

It must not enable SMS/AI voice/ringless voicemail at scale. It must not create GHL workflows. It must not auto-enroll contacts based only on offer route.

⸻

Core Principle

Sequence architecture can suggest and prepare. Wave 1A still decides every send.

Sequence enrollment has one guard.

Sequence worker has another guard.

No campaign setting, operator action, offer route, or GHL field may bypass evaluateContactability().

⸻

Channel Semantics

Use these exact channel meanings:

email

Commercial or transactional-looking SDR email. Must preserve existing unsubscribe/compliance footer behavior. Must respect email opt-out, bounce, DNC, doNotContact, and Wave 1A contactability.

manual_call_task

A human task only. It must not place a call. It must not trigger AI voice, autodial, RVM, or GHL voice workflow.

sms

Automated/text message step. May exist only as a template/paused step where appropriate and must be blocked unless:

* contact has valid pewc_full_automation
* SMS feature flag is enabled
* Wave 1A evaluateContactability() allows the step at execution time
* quiet hours and all suppressions pass

Explicitly out of scope for seeded sequence steps

* voice_ai
* ringless_vm
* autodialed/prerecorded/artificial voice steps

Do not seed voice/RVM steps in this wave.

Enrollment Guard

Create a reusable helper:

canEnrollContactInSequence(contact, campaign): {
  allowed: boolean;
  reason?: string;
  eligibleConsentTiers?: string[];
  contactConsentTier?: string;
  campaignFamily?: string;
}

The guard checks:

* contact exists
* campaign exists
* campaign is not archived/deleted
* contact is not DNC
* contact is not doNotContact
* campaign eligible consent/lifecycle rules
* campaign channel rules are compatible with contact consent tier
* live merchant / partner-only sequences are only used for those lifecycle groups

If blocked:

* return 400 from enrollment endpoint
* do not create enrollment
* write blocked audit log / auditChange entry with reason
* include safe reason in API response

Examples:

* cold lead into PEWC-only campaign → blocked
* cold lead into closed-won onboarding → blocked
* normal merchant prospect into partner-referral → blocked
* warm_no_pewc into SMS-only sequence → blocked
* live merchant into merchant-referral → allowed if suppressions pass

* do not duplicate logic

  write blocked audit/auditChange
  mark step skipped/blocked according to existing pattern
  advance safely according to sequence semantics
if allowed:
  send step

Kill Lines

Stop and report before build if:

* campaigns table or equivalent sequence table cannot be identified.
* sequence enrollment route cannot be identified.
* sequence worker send/trigger points cannot be identified.
* Wave 1A evaluateContactability() is missing or not importable.
* manual call task implementation would place or trigger a call.
* SMS step execution cannot be gated through Wave 1A.
* seed script would create active SMS/voice/RVM sends.
* campaign schema changes would break existing campaigns.
* idempotent seeding cannot be guaranteed.
* enrollment guard cannot write a blocked audit/auditChange entry.
* sequence dashboard location cannot be found.
* email templates would remove or bypass unsubscribe/compliance footer behavior.
* offer-route suggestion requires automatic enrollment.
* closed-won/merchant-referral sequences cannot reliably identify live merchants.
* partner-referral sequences cannot reliably identify approved partners.
* application-abandoned/no-show triggers do not exist and the task would need to invent event automation.
* the task would enable GHL workflows, SMS, AI voice, ringless voicemail, or automated calls.
