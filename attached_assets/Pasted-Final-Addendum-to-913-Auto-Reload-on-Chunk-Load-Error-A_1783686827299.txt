Final Addendum to #913 — Auto-Reload on Chunk Load Error

Approved to build.

Goal

When ErrorBoundary catches a deployment-related chunk load failure:

first chunk failure
→ automatically reload once
→ do not show the error card before reload

If the same tab still fails after that reload:

show the existing “Page failed to load” fallback card

Non-chunk errors must behave exactly as they do today.

Required implementation

In:

ErrorBoundary.tsx

handle the reload from componentDidCatch() or another side-effect-safe lifecycle method.

Do not call window.location.reload() from:

getDerivedStateFromError()
render()

because those methods should remain side-effect free.

Chunk error detection

Reuse the existing isChunkLoadError logic.

Do not broaden it so aggressively that normal runtime exceptions cause reloads.

It should continue detecting only known chunk/dynamic-import failures, such as existing supported patterns for:

ChunkLoadError
Loading chunk ... failed
Failed to fetch dynamically imported module
Importing a module script failed

Use the project’s current detector as the source of truth.

Reload guard

Use a session-scoped guard, but make it specific and recoverable.

Recommended key:

chunk_reload_attempted

Recommended value:

{
  attemptedAt: number;
  errorKey?: string;
}

At minimum, store a timestamp.

Behavior:

if chunk error and no recent guard:
  write guard
  reload immediately
else:
  show existing chunk error fallback

A recent guard should mean the reload attempt occurred within a short safety window, for example:

30–120 seconds

This prevents infinite loops without disabling auto-recovery for the rest of a long browser session.

Clear guard after successful boot

Once the new app bundle mounts successfully, clear the stale guard.

Preferred options:

clear it from the application root after successful mount

or, if scope must remain strictly inside ErrorBoundary.tsx:

clear it after the boundary mounts successfully and no chunk error has occurred

Do not clear it immediately before the reload, because that would recreate the loop.

If clearing from outside ErrorBoundary.tsx would violate the explicit task scope, use a timestamp expiry inside the boundary instead.

Fallback behavior

When the guard is already active/recent:

do not reload again
render the existing “Page failed to load” card unchanged

Preserve:

Reload page button
existing text
existing styling
existing error details behavior

Non-chunk error path

Do not change:

“Something went wrong” card
“Report Issue” button
“Show error details” toggle
non-chunk logging/reporting

A normal application error must never trigger automatic reload through this task.

Storage safety

Wrap sessionStorage access in try/catch.

Some environments can throw due to:

privacy mode
storage restrictions
test environments
SSR/non-browser execution

If storage access fails:

do not enter an uncontrolled reload loop
fall back to the existing error UI

Also guard browser globals:

typeof window !== "undefined"

Optional reload URL hardening

Use:

window.location.reload();

Do not append cache-busting query parameters unless there is evidence they are required.

The browser should fetch the current HTML after deployment; adding query parameters can create noisy URLs and duplicate analytics entries.

Kill lines

STOP if reload is triggered from render() or getDerivedStateFromError().
STOP if non-chunk errors cause an automatic reload.
STOP if the guard can create an infinite reload loop.
STOP if one old reload attempt disables chunk recovery for the entire browser session indefinitely.
STOP if sessionStorage failure crashes the ErrorBoundary.
STOP if the existing chunk fallback card is removed.
STOP if the existing non-chunk error card or Report Issue path changes.
STOP if Vite config, service workers, or unrelated pages are modified.

Validation

Add or extend the focused ErrorBoundary test.

Required cases:

1. First ChunkLoadError with no guard:
   - session guard is written
   - window.location.reload() called once
   - fallback card is not relied on before reload
2. ChunkLoadError with recent guard:
   - reload is not called
   - existing “Page failed to load” card renders
3. Expired guard:
   - reload may be attempted again
4. Non-chunk error:
   - reload is not called
   - existing “Something went wrong” UI renders
   - Report Issue remains available
   - error details toggle remains available
5. sessionStorage.getItem throws:
   - no reload loop
   - fallback UI renders safely
6. sessionStorage.setItem throws:
   - no uncontrolled reload
   - fallback UI renders safely

Also verify manually:

simulate stale chunk error
confirm one automatic reload
simulate repeated failure after reload
confirm fallback card appears
trigger normal ErrorBoundary exception
confirm no auto-reload
