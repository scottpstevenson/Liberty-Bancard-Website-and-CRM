Verdict: NOT BUILD-READY

The preflight is much better, but the build plan contains three direct contradictions:

1. It promises durable enrollment, then permits setImmediate, which is not durable.
2. It wants convert-batch to return final enrollment outcomes immediately, while enrollment runs asynchronously in BullMQ.
3. The proposed worker calls the eligibility service and then calls autoEnrollFromTrigger(), which calls the same eligibility service again.

Corrections to send back

1. Remove the setImmediate fallback.
A setImmediate wrapper with failure auditing is still an unmanaged,
non-restart-safe background operation.
If Redis/BullMQ is unavailable:
- contact creation succeeds;
- enrollment status is recorded as "deferred" or "queue_unavailable";
- no promotional enrollment is attempted;
- the condition is observable and retryable.
Do not silently downgrade a durable workflow to an in-memory promise.
2. Separate enqueue outcomes from enrollment outcomes.
The contact-creation route cannot truthfully return:
enrolled: number
blockedByReason: ...
immediately after placing an asynchronous BullMQ job.
For convert-batch, return:
{
  contactId,
  enrollmentEvaluation: {
    status: "queued" | "already_queued" | "blocked_prequeue" | "queue_failed",
    jobId?: string,
    reasonCodes?: string[]
  }
}
The final worker outcome must be persisted/audited and exposed through a separate
status read if the UI needs it.
Do not report "enrolled" until the worker has actually completed enrollment.
3. Avoid evaluating eligibility twice.
Choose one canonical execution flow:
enqueuePromotionalEnrollmentEvaluation(...)
  -> worker
  -> autoEnrollFromTrigger(...)
autoEnrollFromTrigger() should call
evaluatePromotionalEnrollmentEligibility() exactly once internally.
The caller and worker should not pre-evaluate and then invoke a function that
repeats the same database and contactability checks.
A lightweight prequeue validation may reject malformed jobs, but it is not the
authoritative eligibility decision.
4. Verify ownership of the existing sequences queue.
Before adding job type "promotional_enrollment_eval", provide file:line evidence for:
- queue producer
- worker registration
- job dispatch/type handling
- retry/backoff settings
- dead-letter or terminal failure behavior
- jobId deduplication behavior
- startup behavior when Redis is unavailable
Do not assume arbitrary job types can be added safely to an existing queue.
5. Correct the idempotency-key lifetime.
A permanent key based only on:
contactId + triggerType + formType
can suppress legitimate future events forever.
Define whether deduplication applies to:
- the same source event/submission;
- an active pending job;
- the same sequence enrollment;
- a bounded time window.
Prefer a stable source event identifier such as submissionId, import event ID,
or contact-creation audit ID.
Sequence-enrollment uniqueness must remain enforced by the canonical enrollment
records, not only BullMQ job IDs.
6. Do not classify "completed enrollment" generically as a duplicate without
preserving existing sequence semantics.
Confirm whether a contact that completed a sequence may ever be eligible for:
- a different sequence under the same trigger;
- a new campaign/version;
- a later legitimate resubmission.
The eligibility service should return candidate sequences and evaluate
deduplication per sequence, rather than rejecting the entire contact merely
because one enrollment is completed.
7. Keep channel resolution in one layer.
evaluatePromotionalEnrollmentEligibility() may determine contact-level channel
availability, but the sequence-specific channel decision remains owned by
autoEnrollFromTrigger().
Do not make the new service independently infer a generic email/SMS/voice path
that can disagree with the actual selected sequence.
Recommended service result:
{
  eligible: boolean;
  reasonCodes: PromotionalEligibilityReason[];
  contactabilityByChannel: {
    email?: ContactabilityResult;
    sms?: ContactabilityResult;
    voice?: ContactabilityResult;
  };
}
Then autoEnrollFromTrigger selects candidates using the same decisions.
8. Do not call every opted-out block "resubmission."
The eligibility service receives persisted contact state but may not know that
the current job came from a resubmission.
Use a generic reason code:
existing_opt_out
Use:
existing_opt_out_preserved_on_resubmission
only when the durable job includes a verified source event showing that this
was a repeated form submission.
9. Audit every current caller before replacing it.
The listed call sites include materially different triggers:
- public website forms
- manual CRM creation
- prospect conversion
- imports
- daily outreach
- statement-upload workflow
Document each trigger's:
- source event ID
- intended sequence family
- current error behavior
- whether delayed evaluation changes business behavior
- whether it is transactional or promotional
Do not bulk-replace all calls with one generic job payload without this mapping.
10. Add persistent execution observability.
Every job must produce a terminal state:
- enrolled
- blocked
- no_matching_sequence
- already_enrolled
- failed
- deferred_queue_unavailable
Persist:
- job/event ID
- contactId
- trigger
- reason codes
- enrollment IDs created
- attempts
- createdAt/completedAt
An audit failure row alone is insufficient for reliable retry and operator status.

Kill lines

STOP if setImmediate remains an accepted fallback for durable enrollment.
STOP if an asynchronous route response claims the contact was enrolled before
the worker completes.
STOP if eligibility is executed twice for one worker attempt.
STOP if the existing sequences queue cannot prove support for the new job type,
retry policy, and dispatch behavior.
STOP if a permanent contactId+trigger job key suppresses future legitimate events.
STOP if contact-level eligibility rejects all enrollment because one unrelated
sequence was completed.
STOP if channel ownership is duplicated between the eligibility service and
autoEnrollFromTrigger.
STOP if every opt-out block is mislabeled as a form resubmission.
STOP if queue unavailability causes promotional enrollment to execute in memory.

Validation required

- Contact creation succeeds while Redis is unavailable, but promotional
  enrollment is recorded as deferred and does not run in memory.
- Duplicate delivery of the same source event creates one evaluation job.
- A later distinct source event is not incorrectly suppressed by the old job ID.
- Worker performs one authoritative eligibility evaluation.
- Eligible contact creates exactly one enrollment per applicable sequence.
- Existing enrollment in sequence A does not block legitimate sequence B.
- Opted-out/DNC contacts produce stable typed reason codes.
- Queue retry after process restart completes without duplicate enrollment.
- Terminal worker outcome is queryable independently from the creation response.
- convert-batch distinguishes creation success, evaluation queued, blocked,
  deferred, and queue failure without falsely reporting final enrollment.

Final status: NOT BUILD-READY

The correct architecture is a durable promotional-enrollment evaluation job with one authoritative gate and persisted outcomes. Remove the in-memory fallback and resolve the asynchronous-response contract before implementation.
