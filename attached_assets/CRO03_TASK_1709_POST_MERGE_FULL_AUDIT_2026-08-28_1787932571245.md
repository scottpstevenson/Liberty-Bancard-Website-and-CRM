## 5. Blocking Correction Groups

### P0-01 — Exact-SHA CI and server certification are not green

The reported local 33-assertion disposable result is useful isolated evidence, but it does not replace the failed exact-SHA workflow. The role-guard timeout is an unresolved gate, not evidence of authorization correctness.

**Fix and proof:** repair the stale readiness test, run every deterministic suite on the exact correction SHA, run the disposable PostgreSQL/isolated Redis integration capability, run the provider-denied server-required capability, and require one completely green exact-SHA workflow.

### P0-02 — Batch membership does not freeze the actual enrichment recipe

The selection hash freezes sorted contact IDs, not the fields and decisions that determine execution. Membership stores identifiers and a CRO-02 dependency fingerprint, but not a versioned subject snapshot containing company identity, geography, website/phone/email/title generations, gap vector, purpose, policy version, and route plan. Provider routing is recalculated from the current contact row during execution.

A contact change after batch creation can therefore change which providers run. That breaks immutable membership, exact replay, and cost predictability.

**Fix and proof:** persist a versioned subject snapshot and complete provider/source route plan per item at batch creation. Include purpose and policy/recipe version in idempotency. Revalidation may supersede an item, but must never silently reroute it. Test mutations between creation, claim, retry, and projection.

### P0-03 — Outscraper is unreachable for the state that selects it, and its matching is unsafe

The current route selects Outscraper when a contact lacks a linked business but has enough company/location information for discovery. CRO-02 provider pre-spend policy requires a verified contact-business link. A subject that selects Outscraper therefore fails before transport, while a subject that passes the link gate no longer selects Outscraper.

Even if activated, the adapter accepts up to 25 Maps results and projects the first result without deterministic entity matching.

**Fix and proof:** create a narrow discovery-stage policy that permits a governed unresolved business-link candidate without weakening the general CRO-02 spend gate. Score all Outscraper results against frozen legal/DBA name, address, city, domain, phone, category, and place ID. Require a unique confidence threshold; preserve alternatives and project nothing on ambiguity. Add an end-to-end fixture proving one unresolved South Florida business can be discovered, resolved, linked, and only then enriched.

### P0-04 — Apollo can attach the first unrelated search result to a contact

The current contact loader does not supply the required stable organization identity and the Apollo execution path falls back to a generic industry term. It then takes the first returned result. The request is not anchored to a resolved company/domain and the returned person or organization is not matched back to the frozen target.

If live transport were enabled, this could project another company’s email, phone, title, or address into the target contact.

**Fix and proof:** query Apollo only after stable organization resolution using domain and/or normalized legal/DBA identity plus geography. Score every returned organization/person against the frozen subject, require a unique threshold, preserve conflicting candidates, and produce no canonical mutation on ambiguous or unmatched results.

### P0-05 — Provider lineage, outcomes, retry behavior, and economics are incomplete

The live Apollo/Outscraper path creates provider-operation/run records but does not consistently create the required shared provider attempts and immutable observations. Live candidates can have no observation ID. Serper produces a candidate without complete CRO-03 operation/attempt/observation/economics lineage.

Adapter exceptions collapse 429, timeout, 5xx, invalid response, disabled, and missing-key states into generic failures. Missing credentials can become `no_result` with consumed billing even when no call occurred. Retry/backoff and attempt counts are not a complete durable state machine. Apollo/Outscraper reserve and consume a fixed unit that is not reconciled to actual provider billing, and monetary/receipt references remain incomplete.

**Fix and proof:** require `operation → attempt → immutable observation → candidate` for every provider outcome, including no-result and errors. Normalize typed outcomes, persist retry/backoff state, separate not-configured/disabled/no-result/ambiguous-billing, reconcile provider-specific billed units, and link request/receipt hashes. Reuse Serper and ZeroBounce’s existing authorities through explicit compatibility links rather than creating competing budget owners.

### P0-06 — Batch terminal counts and dispositions can be false

Superseded items are terminal but are not represented in the batch terminal-count equation. When no outstanding items remain, the batch can be labeled completed even when all items failed.

**Fix and proof:** add an explicit superseded count/disposition through an additive migration, calculate completed/failed/partially-completed/cancelled states truthfully, and enforce:

`total = blocked + completed + failed + cancelled + superseded`

Test all-failed, mixed-result, cancellation-race, stale-graph, and superseded-only batches.

### P0-07 — Sunbiz, SDR, AI, and legacy enrichment were shut down rather than converged

The merge removed or disabled legacy enrichment workers and schedulers and made multiple Sunbiz, SDR discovery/re-enrichment, prospect enrichment, and bulk-enrichment routes return stable 503 responses. Existing client pages still call those routes. No equivalent CRO-03 source adapters or UI cutover were completed.

This contradicts the task’s source-convergence objective and removes parts of the user’s existing South Florida candidate-discovery workflow without a governed replacement.

**Fix and proof:** keep unsafe legacy writers disabled, but add source adapters that convert Sunbiz, SDR discovery, public-web, and AI extraction into immutable observations/candidates under the factory. Alternatively, route them through one governed canonical-intake command. Update every affected client to the replacement API and truthful loading/blocked/empty states. Remove unreachable code only after its replacement passes parity tests.

## 6. Acceptance-Level Corrections

### P1-01 — The public-web “safe egress” implementation is not used

**Correction:** wire it through a registered public-web source after implementing address pinning or a strict allowlisted dispatcher, then test redirects, IPv4/IPv6 private ranges, DNS rebinding, size limits, content types, timeouts, and redacted errors.

### P1-02 — Comparison normalization is conflated with canonical display data

Generic normalization lowercases candidate values. Using that value for encrypted canonical projection can degrade addresses, cities, titles, categories, and URLs.

**Correction:** store a field-specific comparison-normalized value/hash separately from the canonical display candidate. Use canonicalizers appropriate to email, phone, domain/URL, address, person name, title, city, state, and category.

### P1-03 — CSV import attribution can overstate Apollo/Outscraper evidence

The convergence path can reconstruct candidates from a contact’s current canonical fields after import and label them with the import provider. That can attribute pre-existing/default values to Apollo or Outscraper instead of the exact accepted row evidence.

**Correction:** preserve accepted per-row, per-field import observations and link each candidate to that immutable source. Never infer provider provenance from the post-import contact row.

### P1-04 — Legacy provider-usage views remain competing or stale projections

Historical Apollo/Outscraper usage settings and UI paths remain while the new economics ledger is the intended authority. The new adapters do not consistently update the old projection.

**Correction:** retire the old read model or implement an explicit compatibility projection from the CRO-03 ledger. Do not maintain two spend authorities.

### P1-05 — ZeroBounce handoff is labeled complete before validation completes

Creating a ZeroBounce validation intent is not the same as receiving a successful validation. CRO-03 needs a durable back-link from the delegated validation to its final outcome.

**Correction:** mark the item `validation_pending` or equivalent, link the ZeroBounce operation/observation and exact email generation, and only record final validation success when the existing ZeroBounce authority completes.
