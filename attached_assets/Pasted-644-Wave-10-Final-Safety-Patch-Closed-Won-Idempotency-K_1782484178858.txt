P1 — Fix Closed Won Welcome Idempotency Scope

Problem

server/routes/deals.ts currently checks and writes a contact-level merchant_welcome_sent audit marker.

Current behavior:

Deal #1 closes for Contact A → merchant_welcome_sent written on contact
Deal #2 closes for Contact A → welcome email/GHL workflow skipped forever

This blocks legitimate second-location, second-MID, re-board, or multi-business onboarding for the same contact.

Required Fix

Remove the permanent contact-level welcome suppression from the Closed Won handler.

Use deal/source-deal/application-level idempotency instead.

Required behavior:

* Re-firing Closed Won on the same deal does not resend welcome email.
* Closing a distinct second deal for the same contact can send the correct onboarding welcome.
* Onboarding deal is not duplicated.
* SLA tasks are not duplicated.
* GHL merchant-approved workflow is not duplicated for the same source deal.
* Existing deal-level audit marker remains the primary idempotency guard.

Preferred logic:

Check merchant_welcome_sent for entityType="deal", entityId=updated.id.
If present, skip welcome/GHL send for this deal.
If absent, allow sendMerchantWelcomeEmail for this deal.
After successful send, write merchant_welcome_sent for entityType="deal", entityId=updated.id.
Do not write permanent contact-level merchant_welcome_sent.

If the codebase has a stronger source application/source deal idempotency marker, use that. Do not use permanent contact-level suppression.

Optional only if business requires cross-deal suppression:

Use a short time-bounded contact-level guard, such as same contact welcomed within the last 24 hours.

Do not add this unless clearly needed.

⸻

P2 — Abandon Recovery Internal Marker Timing

Problem

abandon_recovery_sent is written before enrollment succeeds. If enrollment fails repeatedly, the cron can create repeated internal alert markers/noise while never writing the success marker.

Required Fix

Keep enrollment safety unchanged.

Preferred:

* write abandon_recovery_attempted before attempting enrollment, if monitoring needs an attempt log
* write abandon_recovery_enrolled only after successful enrollment
* do not write abandon_recovery_sent before successful enrollment unless the name truly means “attempted”

Do not weaken:

* sequence eligibility checks
* contactability gates
* family-level enrollment dedupe
* direct-send prohibition

No email/SMS should be sent directly from this job.

⸻

P2 — Replace KYC CTA Regex With Explicit Server Flag

Problem

MerchantPortal currently shows the KYC upload CTA using broad client regex:

/kyc|document|identif|passport|license|verif/i

False positives:

Document equipment order
Verify pricing with merchant
Verify contact info
Identify equipment needs

This can show “Upload KYC documents” on non-KYC tasks.

Required Fix

Do not drive KYC CTA visibility from broad client regex.

Preferred:

Add server-side boolean to portal task payload:

isKycUploadTask: boolean

Set it server-side using explicit task matching.

Acceptable matching:

KYC Documents Collected
KYC
Identity Verification
Photo ID
Driver License
Passport
EIN Letter
Voided Check
Bank Statement

Do not match generic words alone:

document
verify
verification
identify
identification

unless paired with KYC/document category context.

MerchantPortal should render the KYC upload CTA only when:

task.isKycUploadTask === true

Do not expose internal notes or sensitive task metadata.
