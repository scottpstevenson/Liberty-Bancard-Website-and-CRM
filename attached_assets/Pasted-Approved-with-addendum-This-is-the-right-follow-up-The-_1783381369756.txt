Final Addendum to #775 — Prevent Silent 500s on Date Saves

Approved to build.

This task should audit and harden update/mutation paths that pass raw request bodies into storage update methods containing timestamp/date columns.

The goal is:

bad date payload → clean 400 validation error
valid date string → coerced Date before Drizzle write
no valid client action → 500 "value.toISOString is not a function"

⸻

Required audit

Start from:

server/storage.ts

Enumerate update methods that accept partial insert/update payloads, especially:

updateContact
updateTask
updateTicket
updateDeal
updateCalendarEvent
updateMerchant
updateDocument
updatePartner
updateWorkflow
updateSequence

Then inspect routes that call those methods with:

req.body
{ ...req.body }
raw parsed JSON payload
Partial<Insert...>

Focus only on models with date/timestamp columns.

⸻

Preferred fix pattern

Use route-boundary validation where practical:

z.object({
  dueDate: z.coerce.date().optional().nullable(),
  startTime: z.coerce.date().optional().nullable(),
  endTime: z.coerce.date().optional().nullable(),
  followUpAt: z.coerce.date().optional().nullable(),
})

For existing storage methods already used by many routes, adding a small defensive coercion helper inside storage is acceptable as a belt-and-suspenders guard.

Preferred layered model:

route schema validates/coerces known fields
storage defensively normalizes timestamp fields before Drizzle update
malformed dates return 400 where route validation exists
storage never passes raw invalid strings into timestamp columns

⸻

Required behavior

For every hardened endpoint:

valid ISO date string → saved successfully
valid Date instance → saved successfully
null date → handled if field allows null
empty string → clean 400 or converted to null only if that matches existing semantics
invalid date string → clean 400, not 500

Do not silently convert invalid dates to new Date() or current time.

⸻

Kill lines

STOP if any audited update route can still throw value.toISOString is not a function from a raw string date.
STOP if invalid date strings are silently replaced with the current date/time.
STOP if this task changes business semantics for due dates, event dates, follow-up dates, or timestamps.
STOP if this task rewrites storage architecture broadly.
STOP if this task changes already-fixed updateDeal or updateCalendarEvent behavior regressively.
STOP if raw req.body is passed into timestamp-bearing update methods without validation/coercion.

⸻

Out of scope

Do not:

redesign storage architecture
change database schema
change calendar/deal/task/contact business logic
change timezone semantics beyond preserving existing behavior
add new date fields
rewrite all routes unrelated to date-bearing updates

⸻

Validation

Run:

npx tsc --noEmit --skipLibCheck
npx tsx scripts/smoke-role-guards.ts

Add targeted tests or route-level checks for at least:

deal update with ISO date string
calendar event update with ISO date string
task update with dueDate string, if applicable
contact/ticket follow-up date update, if applicable
invalid date payload returns 400 instead of 500

Also run a grep audit:

grep -R "storage.update" server/routes server | grep "req.body"
grep -R ".update(.*set" server/storage server/storage.ts
grep -R "toISOString is not a function" .

Final verdict: build #775. This is a good hardening task, but keep it targeted: find timestamp-bearing update paths, coerce/validate at the boundary, and make bad dates return clean 400s instead of hidden Drizzle 500s.
