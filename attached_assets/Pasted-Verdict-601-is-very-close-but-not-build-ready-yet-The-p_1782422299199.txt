⸻

P0 — Task/manual call steps cannot fully bypass contactability

This line is unsafe:

Confirm "task" steps pass through without contactability check

I understand the intent: task is a human CRM task, not an automated call. That part is correct.

But a task can still be a contact attempt. If someone becomes doNotContact, DNC, opted out, or otherwise suppressed after enrollment, the worker should not keep creating manual call tasks for them.

Wave 1A already has the correct channel for this:

manual_call

That channel allows manual human tasks when doNotAutoContact is true, but still blocks true DNC/doNotContact/hard suppression.

So the worker should not treat task as “no check.” It should map:

task → manual_call

before creating a CRM task.

Required patch

Worker Gate (b) must include task → manual_call mapping before task creation.
Manual call task semantics:
- task does not place a call
- task does not invoke AI voice
- task does not invoke autodialing
- task does not trigger ringless voicemail
- but task creation must still pass evaluateContactability(contact, "manual_call", { mode: "enforcement", source: "sequence_worker" })
This ensures doNotContact/DNC/opted-out contacts do not keep receiving manual follow-up tasks after enrollment.

This is release-blocking. Without it, a contact who opts out after enrollment could still get new “call this person” CRM tasks.

⸻

P1 — Mixed-channel sequences need optional SMS semantics

Some families are valid for both warm_no_pewc and pewc_full_automation, but include optional SMS steps.

Example:

statement-uploaded
booked-appointment
no-show-recovery
proposal-sent
application-abandoned

These should allow warm leads into the sequence for email/task steps, while SMS steps get skipped by Wave 1A.

So the enrollment guard must not blindly say:

campaign has sms in channelsAllowed
→ warm_no_pewc blocked

That would over-block useful sequences.

Required patch

channelsAllowed means the sequence may contain templates for those channels, not that every enrolled contact must qualify for every channel.
Enrollment guard should block warm_no_pewc only when the sequence is PEWC-only or SMS-only.
For mixed sequences:
- warm_no_pewc may enroll
- email/task steps may execute if allowed
- sms steps are skipped/blocked at worker execution by evaluateContactability()

Optional metadata if needed:

smsPolicy: "optional_pewc_only"

or simply use explicit eligibleConsentTiers + worker gate.

⸻

P1 — Paused seeds vs enrollment tests need clarity

Wave 6 seeds should be created as:

status = "paused"

Correct.

But the existing enrollment route blocks non-active sequences:

status !== "active" → block

Also correct.

So validation should not expect direct enrollment into newly seeded paused sequences unless the test activates a test copy.

Required patch

Seeded Wave 6 families must remain paused.
Enrollment guard tests should either:
1. use a test fixture sequence with status = "active", or
2. temporarily activate a test copy in the test setup.
Do not change the production seed status to active just to make enrollment tests pass.

⸻

P1 — channelsAllowed / triggerConfig.outboundChannels must stay consistent

Preflight says existing worker reads:

triggerConfig.outboundChannels

The new schema adds:

channelsAllowed

This creates possible drift.

Required patch

When seeding Wave 6 families, keep followUpSequences.channelsAllowed and triggerConfig.outboundChannels identical.
If both exist, the worker remains backward-compatible with triggerConfig.outboundChannels, while the dashboard and guard can read the normalized channelsAllowed field.
Add validation that mismatches are flagged or normalized.
