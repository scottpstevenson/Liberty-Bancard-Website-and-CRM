Final Addendum to #773 — Boarding Persistent Failure Alerts + Chargeback List PDF Access

Approved to build.

This task is a narrow follow-up to #760. Keep it limited to persistent boarding failure visibility and list-row PDF access for chargebacks.

⸻

Part A — Persistent boarding failure alerts

Required behavior

When POST /api/boarding/refresh-all detects repeated/persistent failures for the same deal, create an internal task or notification so the failure is not only visible in the toast shown to the person who clicked Refresh All.

Do not alert on a single first-time/transient failure.

Persistence rule

Use an existing internal task/notification mechanism if one exists.

Preferred alert target:

assigned owner of the deal
or
admin/manager queue if no owner exists

Threshold rule

Define an explicit threshold before creating an alert, for example:

same deal fails boarding refresh 2+ consecutive times

or:

same deal has failed boarding refresh within the last 24 hours and fails again

Use whichever matches existing data available.

Do not create duplicate alerts repeatedly for the same active failure.

De-dupe rule

Before creating a new task/notification, check for an existing open alert for the same deal and failure type.

Use a stable marker if task descriptions are used:

boarding_refresh_failure:deal_id:<id>

or a structured metadata field if available.

Required result states

Bulk refresh response should still return per-deal results:

succeeded
failed
skipped

But persistent failures should additionally report:

alertCreated: true/false
existingAlert: true/false

Kill lines

STOP if every first-time boarding refresh failure creates a task/notification.
STOP if repeated failures only appear in the toast/HTTP response and are not persisted anywhere.
STOP if duplicate open alerts are created every time Refresh All is clicked.
STOP if this task changes boarding provider/status mapping rules.
STOP if this task changes provider credentials, API keys, or env flags.

⸻

Part B — Chargeback list-view PDF access

Required behavior

Every chargeback row in the list/table view should expose a PDF action without requiring the user to open the detail page first.

Allowed actions:

Download PDF
Preview PDF

The row action must call the existing endpoint:

GET /api/chargebacks/:id/pdf

Do not create a duplicate PDF generation endpoint.

Auth/security guard

The list-row action must preserve existing auth and role checks from the PDF endpoint.

Do not expose PDF links as public static URLs.

UI guard

The action should be visible but not clutter the table.

Acceptable placements:

row action menu
small PDF icon button
Download PDF button in existing actions column

Kill lines

STOP if list-view PDF access uses a new duplicate endpoint instead of the existing /api/chargebacks/:id/pdf endpoint.
STOP if PDF access bypasses existing chargeback auth/role checks.
STOP if reps still must open the detail page to download/preview evidence PDF.
STOP if this task changes chargeback dispute workflow logic.

⸻

Out of scope

Do not:

redesign Boarding Tracker
redesign Chargebacks
change boarding status mapping/business rules
change chargeback PDF contents
change chargeback evidence generation logic
add new chargeback workflow states
create new notification infrastructure if existing tasks/notifications can be reused
