What & Why

The platform currently captures some frontend lead events and UTM parameters, but it does not yet have a complete source-to-conversion analytics system.

Wave 8 creates a consistent event taxonomy across:

* frontend CTA clicks
* form steps
* statement upload funnel
* PEWC interactions from Wave 2
* thank-you pages
* server-side CRM milestones
* contactability/channel events from Wave 1A
* sequence events from Wave 6
* offer route events from Wave 5
* booking attribution from GHL where technically possible

The business goal is to answer:

* Which pages create leads?
* Which sources create appointments?
* Which campaigns create statement uploads?
* Which offers lead to closed won?
* Which forms capture PEWC best?
* Which pages generate calls and bookings?
* Where are prospects dropping off?

This task must create measurement infrastructure without changing compliance, contactability, offer routing, sequence enrollment, or GHL workflow behavior.

Core Rules

1. No PII in analytics platforms

Never send raw phone, email, full name, address, statement file name, or contact notes to GA4, Meta Pixel, or client-side analytics.

Allowed dimensions:

* form_id
* page_path
* page_type
* offer_route
* vertical
* consent_tier
* lifecycle_stage
* utm_source
* utm_medium
* utm_campaign
* utm_content
* utm_term
* gclid_present
* fbclid_present
* msclkid_present
* coarse volume ranges
* coarse savings ranges
* event IDs / anonymous session IDs

2. One event wrapper, no duplicate systems

Do not create a third analytics system.

Use the existing tracking.ts / analytics.ts patterns.

If both exist and overlap, create one canonical public API in tracking.ts and have legacy helpers delegate to it.

Avoid duplicate GA4/fbq firing.

3. Client events and server events are different

Client events:

* CTA clicks
* file selected
* form abandoned
* PEWC checkbox interaction
* thank-you page view

Server events:

* contact created
* PEWC captured
* statement received
* appointment booked
* sequence step sent/blocked
* channel blocked/allowed
* offer route assigned
* proposal generated
* deal stage changed
* closed won

Do not put all client analytics into compliance audit logs.

4. Audit log separation

Compliance/security audit logs should not become a noisy clickstream table.

Preferred:

* use existing analytics/event table if present
* otherwise create a dedicated analytics_events or crm_events table for analytics milestones

Use audit_logs only if the repo already uses it for CRM event telemetry and the schema/capacity is appropriate.

Compliance-critical events may still also write to their existing audit logs.

5. Booking attribution must fail honestly

Do not assume GHL calendar bookings can be attributed through Replit unless verified.

Possible approaches:

* append UTM/session parameters to GHL booking URL if GHL preserves them
* use a bookingTrackingId generated by Replit and appended to the booking URL
* receive a GHL booking webhook and match by bookingTrackingId, GHL contact ID, email/phone if safely available server-side, or time-window/contact match
* use a Replit redirect/callback only if GHL supports redirecting after booking

Do not pass raw contact_id in public booking URLs unless signed/opaque and verified safe.

* statement_upload_failed only after failed API response

* UTM values
* page path

4. Form abandonment

Create:

Requirements:

* fires only if user entered meaningful data

* no raw form values in payload

* does not block navigation
* does not spam on minor field focus/blur
* supports multi-step forms
* ignores completed/submitted forms
* uses navigator.sendBeacon or lightweight fetch if existing pattern supports it
* degrades safely if unavailable

Apply only to high-value forms in this wave:

* /upload-statement
* /free-analysis
* /get-started
* /merchant-application

Booking Attribution Bridge

Kill Lines

Stop and report before build if:

* existing analytics helpers cannot be identified.
* GA4/fbq wrappers are unclear and adding events would duplicate tracking.
* no safe event storage exists and migration pattern is unclear.
* implementing analytics would require raw phone/email/name in client-side events.
* booking attribution requires exposing raw contact ID in public URL.
* GHL booking cannot redirect/webhook and the task would fake appointment attribution anyway.
* form abandonment would capture raw form values.
* beforeunload tracking would block navigation or create spammy duplicate events.
* dashboard counts would require pretending visitor data exists when it does not.
* adding eventType to audit_logs would pollute compliance audit logs or break existing audit behavior.
* server event recording would throw and break form submissions, sequence sends, or contactability enforcement.
* the task would rewrite major forms instead of surgical event hooks.
* the task would touch SMS/AI voice/RVM enablement.
* the task would change compliance rules or consent-tier behavior.
