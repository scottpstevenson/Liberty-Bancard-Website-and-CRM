What & Why

Every new Liberty Bancard lead should be routed to the offer most likely to convert them.

The platform already has lead enrichment and a primaryOfferPath concept, but offer routing appears inconsistent. Some leads may get AI scoring without a clear offer path surfaced to reps or synced to GHL.

This wave creates a canonical Offer Router that assigns:

* best offer route
* confidence score
* recommended next action
* concise rationale
* deterministic processor-match reason when obvious
* AI-assisted reasoning when ambiguous

The goal is to improve conversion by making every contact/deal immediately actionable:

* beat current processor
* upload statement
* book call
* check free terminal eligibility
* explore compliant fee-offset review
* start application
* route to industry-specific review

⸻

Core Principle

Deterministic first. AI second. Human override audited.

Obvious processor matches should not wait for AI.

AI should help with ambiguous leads, not replace hard rules.

Human overrides should be allowed only in the CRM/admin UI, role-gated, and audit logged.

Offer Route Criteria

Deterministic processor detection

If currentProvider, processor, website tech, statement text, notes, or enrichment fields contain processor signals, assign route deterministically:

* Square → beat_square
* Stripe → beat_stripe
* Clover → beat_clover
* Toast → beat_toast
* PayPal → beat_paypal

Processor matching should be:

* case-insensitive
* punctuation-tolerant
* avoid false positives where possible
* explain source field used
* assign high confidence when match is strong

Suggested confidence:

* exact provider field match: 95
* strong statement/website tech match: 85–90
* fuzzy text mention: 70–80

Free smart terminal route

Assign or suggest free_smart_terminal when:

* lead requests equipment/terminal/POS
* needTerminal = true
* current equipment is missing/old
* business type strongly benefits from terminals/POS
* estimated monthly volume suggests potential eligibility
* source offer/page is /free-smart-terminal or offer=free-terminal

Do not imply guaranteed approval or free equipment.

Recommended next action:

* check_terminal_eligibility
* book_appointment
* upload_statement

Free statement analysis route

Assign free_statement_analysis when:

* lead uploaded a statement
* source page is /upload-statement
* lead asks for rate review
* provider is unknown but processing volume exists
* high-intent inbound without known competitor

Recommended next action:

* upload_statement if no file exists
* book_appointment if statement exists
* request_free_analysis

Cash discount / surcharge / dual-pricing review

Assign one of:

* compliant_cash_discount_review
* compliant_surcharge_review
* dual_pricing_review

Only as a review path when:

* lead came from /0-percent-processing
* source offer references Liberty Zero™
* vertical commonly fits fee-offset review such as restaurant, retail, salon, service business
* lead asks about reducing/offsetting processing fees

Do not claim this is approved, guaranteed, universally legal, or suitable for every merchant.

Recommended next action:

* explore_fee_offset_review
* book_appointment
* upload_statement

Industry-specific rate review

Assign industry_specific_rate_review when:

* vertical is known
* no strong processor match
* no terminal/fee-offset signal
* industry page/source generated the lead
* merchant type has specific processing needs

Recommended next action:

* book_appointment
* upload_statement
* request_free_analysis

Merchant application

Assign merchant_application only when:

* lead is already in application intent
* source is /merchant-application
* deal stage indicates verbal commit / application started
* user explicitly wants to sign up

Do not route cold/incomplete leads directly to application unless intent is explicit.

Partner referral

Assign partner_referral when:

* sourceCategory is partner/referral
* source page is /partners
* lead is CPA/bookkeeper/consultant/insurance/affiliate type
* form is partner signup or referral portal

Offer Router Output Shape

Create a shared output type if repo patterns support it:

type OfferRoutingResult = {
  offerRoute: OfferRoute;
  offerConfidence: number; // 0-100
  recommendedNextAction: RecommendedNextAction;
  offerReasoning: string;
  routingSource: "deterministic_processor" | "deterministic_source" | "deterministic_rules" | "ai_router" | "manual_override";
  matchedSignals: string[];
  processorDetected?: string | null;
  shouldUpdateContact: boolean;
};

Rules:

* offerConfidence must be clamped 0–100.
* offerReasoning must be concise and rep-readable.
* matchedSignals must not include sensitive/raw private data unnecessarily.
* shouldUpdateContact = false for dry-run/preview endpoints unless update requested.

Backend Architecture

Shared service

Create or update:

server/services/offer-router.ts

or nearest existing service layer.

Exports:

detectProcessorSignals(input): ProcessorDetectionResult
routeOfferDeterministic(input): OfferRoutingResult | null
routeOfferWithAi(input): Promise<OfferRoutingResult>
routeOffer(input, options): Promise<OfferRoutingResult>

Routing order:

1. explicit manual override, if applicable
2. deterministic processor match
3. deterministic source/offer parameter match
4. deterministic terminal/fee-offset/application/partner signals
5. AI fallback for ambiguous leads
6. safe default: free_statement_analysis or industry_specific_rate_review

The service should be reusable by:

* enrichment endpoint
* contact route-offer endpoint
* public form creation pipeline
* future sequence routing

AI Router Prompt

If using OpenAI/AI enrichment, create or update the prompt in the existing prompt file, likely:

* server/services/sdr/enrichment-prompts.ts

Prompt requirements:

* output strict JSON only
* use canonical offer route values only
* use canonical recommended action values only
* no unsupported savings claims
* no legal advice
* no guarantee of free terminal approval
* cash discount/surcharge/dual pricing routes must be “review” routes
* include confidence and concise reasoning
* include matched signals
* if ambiguous, default to free statement analysis or industry-specific review

AI output must be validated with zod or existing validation pattern.

Invalid AI output must fail safely to a deterministic/default route.

Do not remove existing enrichment fields.

2. Offer route endpoint

Create:

POST /api/contacts/:id/route-offer

Access:

* admin
* manager
* agent if existing policy allows contact enrichment actions

Request:

{
  dryRun?: boolean;
  forceAi?: boolean;
  updateContact?: boolean;
}

Behavior:

* loads contact
* runs offer router
* returns result
* updates contact only if updateContact = true
* default should be dry-run or no update unless existing UX requires update
* no GHL workflow trigger
* no sequence enrollment
* no outreach

3. Manual override endpoint

Use existing contact update endpoint if safe, or add:

PATCH /api/contacts/:id/offer-route

Access:

* admin
* manager
* agent if allowed

Request:

{
  offerRoute: OfferRoute;
  recommendedNextAction?: RecommendedNextAction;
  reason: string;
}

Behavior:

* validates canonical offer route
* writes primaryOfferPath
* sets offerConfidence = 100 or null/manual
* sets routingSource = manual_override
* writes audit log or contact note
* does not trigger workflows
* syncs to GHL only through existing contact sync/upsert path if already appropriate
