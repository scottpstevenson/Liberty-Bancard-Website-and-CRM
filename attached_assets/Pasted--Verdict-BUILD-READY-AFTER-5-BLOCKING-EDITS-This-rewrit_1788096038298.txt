## P0-2 — TTL presence alone cannot prove a complete fleet

A Redis heartbeat registry can show observed processes and identify mixed SHAs among them. It cannot prove that every Replit autoscale replica registered, because an entirely missing process leaves no key.

Replace fleet-complete language with this exact contract:

* `scope: "local_process"` — one responding process
* `scope: "observed_fleet"` — all nonexpired Redis members found during a bounded complete scan
* `completeness: "verified"` only when an authoritative expected process count or deployment inventory is available and reconciles
* Otherwise `completeness: "unknown"`—never fleet-ready
* Mixed SHA, duplicate identity, stale heartbeat, Redis failure, truncated scan, or expected-count mismatch produces `degraded`
* An unobservable missing replica remains an operations verification gap

Use the existing shared Redis connection—do not create another connection. Custom fleet and alert keys must have an explicit namespace derived from the disposable `TEST_REDIS_PREFIX` in test/CI and a fixed Liberty runtime namespace in production. BullMQ’s `prefix` does not automatically namespace arbitrary application keys.

A safe implementation contract is:

* Heartbeat every 15 seconds
* TTL of 60 seconds
* Best-effort deletion on graceful shutdown
* Full bounded `SCAN`, with `complete: false` if the maximum key budget is exceeded
* No hostnames, Redis URLs, credentials, or infrastructure IDs returned to operators
* Public liveness unaffected by Redis/fleet unavailability
* Authenticated readiness becomes unverified/degraded

Update the kill line from “local evidence described as fleet-complete” to:

> **KILL LINE:** Observed Redis membership is described as a complete deployed fleet without reconciliation to authoritative expected process inventory.

## P0-4 — Alert idempotency needs an exact database contract

The current prompt says the durable alert feed must not duplicate, but `persistAlert()` writes ordinary `audit_logs` rows. `audit_logs.entity_key` is indexed but not unique, and `persistAlert()` swallows errors.

Redis can coordinate transport attempts, but it cannot by itself guarantee idempotent durable database persistence across a crash between PostgreSQL and Redis.

Specify this design:

1. Calculate a normalized, sanitized incident fingerprint.
2. Atomically claim the transport attempt in namespaced Redis.
3. Persist the durable feed through a PostgreSQL transaction using:

   * `pg_advisory_xact_lock()` derived from the fingerprint; and
   * lookup/insert by `action='system_alert'` and `entity_key=<fingerprint:cooldown-bucket>`.
4. Return the existing audit-log ID when the feed event already exists.
5. Store no raw provider response.
6. Track feed and external transport independently.

Required result shape:

```ts
{
  incidentFingerprint,
  claimStatus: "claimed" | "suppressed" | "unavailable",
  feedStatus: "persisted" | "already_present" | "failed",
  transportStatus: "delivered" | "failed" | "not_configured" | "not_attempted",
  alertLogId?: number,
  attemptedAt?: string,
  completedAt?: string,
  retryAfter?: string
}
```

Cooldown semantics:

* A persisted admin-feed event can satisfy durable internal delivery even when Slack is not configured.
* A configured Slack failure receives a shorter transport-retry lease.
* Retrying Slack must not create a second feed record.
* A different incident fingerprint must not be suppressed.
* `getRecentAlerts()` must return an explicit unavailable/degraded result on database failure—not `[]`, which falsely means “no alerts.”
