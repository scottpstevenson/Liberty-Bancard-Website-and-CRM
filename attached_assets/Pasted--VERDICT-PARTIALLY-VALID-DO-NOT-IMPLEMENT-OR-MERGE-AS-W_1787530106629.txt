# P0 Corrections

## P0-1 — Cover the complete Contact Detail authorization surface

The task currently scopes authorization mainly to:

* `server/routes/contacts.ts`
* `server/routes/deals.ts`

That is insufficient. Contact Detail independently calls endpoints across multiple route modules. Denying the parent contact request does not secure those routes.

Create one reusable server-side authorization owner, for example:

* `requireContactAccess(contactId, user)`
* `requireDealAccess(dealId, user)`

Policy:

* Agent contact reads: assigned to the agent’s email or unassigned.
* Agent deal reads: owned by the agent’s email or unassigned.
* Manager/admin: unrestricted within existing tenant boundaries.
* Use one consistent 403 or non-enumerating 404 policy.
* Never trust a request-body contact/deal ID without resolving and authorizing it.

Apply it to all applicable reads and mutations, including at minimum:

* `server/routes/crm-operations.ts:18-136`

# P1 Corrections

## P1-1 — Do not equate contactability with outreach queue eligibility

The Ready-for-Outreach query does not simply call the general contactability engine. Presenting a contactability dry-run as “queue eligibility” can diverge from the actual queue.

Create one reusable server-side queue membership/count predicate preserving the existing rules, then use it for:

* Queue list
* Queue count
* Daily Briefing outreach-ready count
* Safe queue membership reason codes

Contact Detail should display two distinct concepts:

* Channel/contactability status
* Ready-for-Outreach membership and reason

Do not reproduce either rule set in React.

## P1-2 — Correct Daily Briefing identity and count logic

`server/routes/daily-briefing.ts` uses `userId` against ownership columns that store email:

* `assigned_to = userId`
* `owner = userId`

Use `req.user.email` for contact/deal ownership.

Replace or rename `hotLeadsCount`:

* Preferred: `outreachReadyCount`, calculated using the shared queue predicate and linked to `/dashboard/outreach-queue`.
* Alternatively, retain “hot leads” as a separate metric and stop claiming it matches Ready for Outreach.

Do not silently turn failed section queries into trustworthy zeroes. Return section degradation metadata or fail the briefing.

Refresh should invalidate and regenerate the briefing, returning the fresh payload. `Overview.tsx` must show pending and failure states and update its query cache from the response.

## P1-3 — Replace the Inbox total contract

`server/routes/inbox.ts:187-454` fetches independently capped windows, filters in memory, swallows source failures, and then returns:

```ts
total: items.length
```

That is not a global filtered total.

Use an explicit contract such as:

```json
{
  "items": [],
  "pageInfo": {
    "nextCursor": null,
    "hasMoreKnown": false
  },
  "resultScope": "fetched_window",
  "knownFilteredTotal": 0,
  "complete": false,
  "sources": [
    {
      "source": "ghl_sms",
      "status": "ok",
      "fetched": 40,
      "truncated": true
    }
  ]
}
```

Validate channel, filter, limit and cursor. Invalid values return `400` with a stable reason code.

Use a deterministic composite cursor such as timestamp + source + source ID. A timestamp-only cursor can skip or duplicate tied messages.

## P1-4 — Correct queue-history and DLQ scope

Remove “paginate queue history” from the task. `getJobHistory()` returns fixed 24-hour buckets at `queue-manager.ts:1627-1640`.

The real queue problems are:

* Queue routes call `getQueueManager()` despite comments requiring non-starting readiness access.
* DLQ reads only the first 50 failed jobs per queue.
* Per-queue failures are swallowed.
* Raw `job.data` and stack traces are returned.
* The UI can render an unavailable DLQ as “all queues healthy.”

These should be owned by the BT-09 queue-runtime correction. If #1667 must ship first, include these prerequisites:

* Use `requireQueueManagerReady()` for HTTP reads.
* Return explicit `not_initialized`/`degraded` state.
* Return redacted DLQ DTOs; never raw `job.data` or stack traces.
* Do not calculate a “total” from the currently sampled first 50 jobs.
* Surface per-queue read failures.
* Render unavailable/unknown separately from empty/healthy.

## P1-6 — Add strict route-level pagination validation

Current `Number()`/`parseInt()` handling allows NaN, decimals or inconsistent defaulting.

For each changed endpoint:

* Require positive integer `limit`.
* Require nonnegative integer `offset` or page.
* Apply a documented per-route maximum.
* Return `400 INVALID_PAGINATION` for malformed, decimal, negative, zero or over-limit input.
* Apply identical scope and filters to data and count queries.
* Preserve `{data,total,limit,offset}` where consumers depend on it.

Do not change the global storage maximum in `server/storage/_shared.ts`; use route-specific limits. Consumers currently requesting large values such as `limit=500` must paginate or use a reviewed picker endpoint.

## P1-7 — Fix aggregate Contact Detail correctness

`GET /api/contacts/:id/detail` retrieves capped/global deals, tickets and tasks and filters them in application memory.

Replace this with contact-scoped storage queries. This prevents:

* Incomplete results after the global cap
* Unnecessary global reads
* Accidental data exposure during aggregation
