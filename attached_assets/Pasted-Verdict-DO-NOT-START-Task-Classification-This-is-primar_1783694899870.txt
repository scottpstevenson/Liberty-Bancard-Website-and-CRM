Verdict

DO NOT START

Task Classification

This is primarily an Infrastructure / Background Worker reliability task with secondary Admin UX and observability enhancements.

It is not a simple bug fix. The proposed implementation changes job-lock ownership, stale-lock recovery, privileged operator controls, worker failure behavior, and production job concurrency.

The current plan is unsafe because it treats “older than 15 minutes” as proof that a lock is stale and allows an operator to clear it without proving that the original worker is dead. That can create two concurrent enrichment jobs mutating the same contacts.

False Assumptions

1. The worker is stuck for one of two reasons

The task assumes:

1. a stale job lock, or
2. a missing/invalid Serper key.

That is an unsupported binary diagnosis.

Other plausible causes include:

* BullMQ worker not running.
* Redis unavailable.
* Queue paused.
* Job never enqueued.
* API process and worker process using different environments.
* Database connection exhaustion.
* An unhandled promise that leaves UI state running.
* OpenAI authentication or rate-limit failures.
* Serper rate limits.
* Queue retry delay.
* A dead-lettered or failed job.
* Invalid contact-selection query.
* Every candidate being skipped as ineligible.
* Transaction rollbacks.
* Counter state not persisted.
* Frontend polling stale or querying the wrong job.
* Multiple job registries or duplicate canonical owners.
* Worker deployment version mismatch.
* OOM restart loops.
* Lock acquisition succeeding while queue submission fails.
* Job submission succeeding while status initialization fails.

The task must diagnose before prescribing recovery architecture.

2. A finally block protects against OOM crashes

False.

A finally block runs when execution unwinds normally through JavaScript control flow. It does not reliably execute when:

* the process is killed,
* the container is evicted,
* the host crashes,
* the runtime is terminated,
* the process suffers an unrecoverable OOM,
* the machine loses power.

A finally block is useful for ordinary exceptions, but it cannot make an in-memory lock release crash-safe.

3. Any lock older than 15 minutes is stale

False unless the maximum valid job duration is proven.

A batch could legitimately exceed 15 minutes due to:

* provider latency,
* rate limiting,
* retries,
* large input payloads,
* database slowness,
* reduced worker concurrency,
* throttling,
* degraded external services.

Age alone is not safe evidence of abandonment.

4. Resetting the row to idle is safe

False.

If the original worker is still alive, resetting the row permits a second worker to acquire the job while the first continues processing.

Possible consequences:

* duplicate API spend,
* duplicate classification attempts,
* conflicting contact writes,
* score overwrites,
* inaccurate counters,
* duplicate audit history,
* database contention,
* rate-limit spikes,
* lost completion state.

5. Deleting the lock row is equivalent to releasing ownership

False.

Deleting the row destroys diagnostic state and may bypass ownership or fencing semantics. It can also allow an old worker to “complete” after a new worker has acquired the same logical job.

6. Environment-variable presence proves API health

False.

This only proves that a nonempty string may exist in one process’s environment.

It does not prove:

* the credential is valid,
* the worker process received it,
* the account is active,
* quota remains,
* the expected model or API is available,
* outbound networking works,
* the credential has required permissions.

The endpoint should call this configuration presence, not API health.

7. Re-enabling the button after a reset is sufficient

False.

The system must prove the old execution can no longer commit writes before permitting a new execution.

8. A single contact exception currently bricks the queue

Unverified.

The worker may already catch contact-level errors. The actual failure could happen outside the per-contact loop, during status persistence, lock renewal, queue acknowledgement, or finalization.

9. “Processed” should only increment on success

Potentially false.

The correct counter model may require separate values:

* attempted,
* succeeded,
* classified,
* skipped,
* failed,
* retried.

A job that attempts ten contacts and fails all ten should not remain at 0 processed, because that falsely appears stuck.

10. Writing at least one vertical proves the worker is fixed

False.

That is too weak to validate:

* complete batch handling,
* lock lifecycle,
* retries,
* counter accuracy,
* concurrency,
* restart safety,
* partial failure behavior,
* idempotency.

⸻

Root Cause

The immediate root cause is unknown.

The broader architectural problem appears to be that enrichment execution lacks a trustworthy, observable job state model that distinguishes:

* requested,
* queued,
* lock acquired,
* running,
* making progress,
* retrying,
* failed,
* abandoned,
* canceled,
* succeeded.

The proposed task conflates three different concerns:

1. Credential configuration
2. Worker/job health
3. Lock ownership and recovery

A manually resettable timestamp lock is not a complete background-job architecture.

The likely UI defect is that a boolean “running” state remains visible without authoritative progress, heartbeat, failure reason, or worker ownership information.

⸻

Correct Architecture

1. Diagnose the actual execution path first

Trace the complete flow:

UI request
→ API authorization
→ job creation/enqueue
→ queue or scheduler
→ worker pickup
→ lock acquisition
→ candidate selection
→ provider calls
→ contact writes
→ progress persistence
→ completion/failure
→ lock release
→ UI polling

For every transition, identify the persisted source of truth.

Do not add recovery controls until the canonical owner is known.

2. Use a lease, not a permanent boolean lock

The job registry should use a renewable lease with at least:

* jobName
* status
* ownerId or execution ID
* leaseToken or fencing token
* startedAt
* heartbeatAt
* leaseExpiresAt
* attempt
* progress
* lastError
* finishedAt

A worker should:

1. Acquire the lease atomically.
2. Receive a unique execution/fencing token.
3. Renew the lease periodically.
4. Include that token when persisting progress and completion.
5. Stop writing if lease renewal fails or ownership changes.

A replacement worker may acquire only an expired lease through an atomic compare-and-set operation.

3. Add fencing

Lease expiry by itself is insufficient.

An old worker can recover after the lease expires and continue writing. Every mutation or progress update must be conditional on the worker still owning the current execution token, or the enrichment writes themselves must be idempotent and version-aware.

At minimum:

UPDATE background_jobs
SET ...
WHERE job_name = ?
  AND execution_token = ?

For contact writes, determine whether stale-worker writes must also be fenced using:

* job execution ID,
* enrichment version,
* optimistic version,
* or an idempotent per-contact attempt record.

4. Replace “Reset Lock” with controlled recovery

The operator action should not blindly reset a row.

Safer semantics:

“Mark Abandoned and Allow Retry”

It should be available only when all of the following are true:

* lease is expired,
* heartbeat is stale,
* execution has not completed,
* no active queue job or worker ownership can be found, where inspectable,
* the operator has the required role,
* the action uses an atomic ownership/version check.

The action should:

* mark the old execution abandoned,
* preserve its diagnostics,
* record actor and reason,
* revoke or supersede the old fencing token,
* create or permit a new execution,
* never delete historical state.

5. Separate configuration status from provider connectivity

The endpoint may safely expose:

{
  "configuration": {
    "serperPresent": true,
    "openAiPresent": true
  }
}

Do not label this “healthy.”

A real connectivity check would require controlled external calls and must address:

* cost,
* rate limits,
* timeouts,
* secret scope,
* auditability,
* false alarms,
* whether it runs from the same process/environment as the worker.

A safer initial UI label is:

Serper credential: Configured
OpenAI credential: Configured

Also show worker/job telemetry separately:

Worker status
Queue status
Current execution
Last heartbeat
Last progress
Last error

6. Model progress truthfully

Persist at least:

* total candidates,
* attempted,
* succeeded,
* classified,
* skipped,
* failed,
* current cursor or last processed ID,
* last progress timestamp.

Contact-level errors should increment attempted and failed, not leave the job looking idle.

The batch should define whether it:

* continues after contact-level errors,
* retries transient failures,
* stops after an error threshold,
* resumes from persisted progress,
* or creates a new attempt.

7. Make contact enrichment idempotent

The task must determine whether rerunning the same contact can:

* overwrite human-edited verticals,
* lower or replace newer scores,
* duplicate provider usage,
* append duplicate activities,
* trigger downstream enrollment,
* retrigger GHL synchronization,
* alter lead-routing state.

The enrichment operation needs a clear ownership and overwrite policy before retry or stale-job recovery can be considered safe.

Kill Lines

* STOP if the actual failure mode has not been identified from logs, queue state, job records, and code flow.
* STOP if the implementation assumes only a stale lock or missing Serper credential can cause the symptom.
* STOP if a lock can be cleared based only on elapsed wall-clock time.
* STOP if a live worker could continue after an operator reset.
* STOP if recovery can permit two enrichment executions to mutate contacts concurrently.
* STOP if the job lock lacks an execution owner or fencing token.
* STOP if an old worker can update progress or completion after a replacement job starts.
* STOP if the recovery action deletes the job record or destroys diagnostic history.
* STOP if a finally block is presented as protection against process death or OOM termination.
* STOP if the stale threshold is hardcoded without evidence from maximum legitimate execution time and heartbeat behavior.
* STOP if API-key presence is labeled as provider health.

* STOP if the UI re-enables enrichment before old ownership is revoked.

Automated tests

Lease and concurrency

* Two workers attempting acquisition result in exactly one owner.
* An unexpired lease cannot be taken over.
* An expired lease can be taken over atomically.
* The old owner cannot renew after takeover.
* The old owner cannot mark the new execution complete.
* The old owner cannot update job progress after takeover.
* Recovery preserves the abandoned execution record.
* Two concurrent operator recovery requests do not create duplicate replacement jobs.

Failure and restart

* Contact-level provider error increments attempted and failed.
* One contact failure does not incorrectly terminate the batch when continuation is intended.
* Fatal batch error persists failure status and diagnostics.
* Normal exceptions release or expire ownership correctly.
* Process restart resumes or safely retries from persisted state.
* No contact is processed twice unless explicitly permitted.
* Retry does not overwrite protected newer data.

Authorization and security

* Unauthenticated access is rejected.
* Dashboard-only users cannot invoke recovery unless authorized.
* Manager and admin behavior matches approved role policy.
* Secrets are never returned.
* Logs and audit records do not contain secrets.
* Recovery produces an audit event with actor, execution, reason, and timestamp.

UI

* Configured credentials display as “Configured,” not “Healthy.”
* Missing credentials disable or warn before job submission according to existing policy.
* Running job shows last heartbeat and progress.
* Failed job shows an actionable failure state.
* Expired lease shows controlled recovery only to authorized roles.
* Loading and network errors do not appear as missing credentials.
* UI cannot start a second active execution.
