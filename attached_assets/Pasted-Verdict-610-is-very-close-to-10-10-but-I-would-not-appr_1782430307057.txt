Verdict

#610 is very close to 10/10, but I would not approve Build mode until 4 patches are added.

The plan is excellent overall. It correctly fixes the stale assumptions:

server/routes/ghl.ts → wrong
server/routes/integrations.ts → correct
/api/ghl/webhook → wrong
/api/webhooks/ghl → correct
/dashboard/ghl-sync → wrong
/dashboard/ghl-settings → correct
HMAC for GHL workflow permission-check → wrong
Bearer secret for workflow HTTP action → correct

The architecture is also right:

Replit = permission source of truth
GHL = execution layer
permission fields + permission-check endpoint = external workflow guardrails
dryRun only = no audit/rate-limit contamination
opt-outs from GHL can tighten but never loosen restrictions

But there are a few hidden risks that need to be patched.

⸻

P0 Patch 1 — Manual call guidance is too loose

This line is dangerous:

manual_call tasks do not require this gate

Correct version:

manual_call tasks do not require PEWC, SMS consent, AI voice consent, or RVM consent — but they still must honor doNotContact, DNC, opted_out, and suppression state.

If a GHL-native workflow creates manual call tasks, it should still branch on either:

lb_can_manual_call === "true"

or call:

POST /api/ghl/permission-check
channel = "manual_call"

Otherwise GHL could keep creating “call this person” tasks for DNC/opted-out contacts.

Patch

In GhlSequenceGuide.tsx, do not say manual_call tasks do not require the guard.
Say:
Manual call tasks do not require PEWC and must never trigger AI voice, autodialing, or ringless voicemail. However, GHL-native workflows that create manual call tasks must still check lb_can_manual_call or call /api/ghl/permission-check with channel="manual_call" so DNC/doNotContact/opted-out contacts are not assigned follow-up tasks.

⸻

P0 Patch 2 — Custom field 422 handling must match actual GHL write behavior

The plan says:

Wrap the field-write HTTP call in per-field try/catch

But preflight says the existing pattern is:

addCF(key, value)
customFields: [{ key, field_value }]

If addCF() only builds an array and the upsert sends one combined request, there is no real per-field try/catch. A missing new field could still make the entire contact upsert fail with 422.

This needs a precise implementation rule.

Patch

Before implementing field error handling, verify whether GHL custom fields are written:
1. as part of one contact upsert payload, or
2. through a separate per-field/custom-field update call.
If the repo only sends one combined upsert payload, do not claim per-field try/catch exists. Instead:
- keep the base contact upsert path from failing because optional Wave 7 permission fields are missing,
- log the 422 with the attempted field keys,
- preserve existing GHL sync behavior for already-working fields,
- and report that external GHL field creation is required.
If a per-field update helper exists, use it for the new Wave 7 lb_* fields so one missing field does not abort the entire sync.

This is important. A missing lb_can_sms field in GHL settings should not break the entire contact sync.

⸻

P1 Patch 3 — Permission-check auth must fail closed if secret is missing

The plan says use bearer auth. Good. But it must also say what happens if GHL_WEBHOOK_SECRET is missing.

Patch

If GHL_WEBHOOK_SECRET is missing/empty, /api/ghl/permission-check must return 503 or 401 fail-closed and log configuration_missing. It must never allow requests because the secret is unset.

Also, constant-time compare should be implemented safely:

Only use timingSafeEqual after confirming both buffers are the same length, otherwise return unauthorized without throwing.

⸻

P1 Patch 4 — Opt-out webhook should not require contact match to preserve evidence

The current plan says look up contact by ghlContactId in all handlers. Correct. But if no Replit contact is found, the event should still be logged as an inbound GHL event/error.

Patch

If an opt-out webhook event cannot be mapped to a Replit contact, return 200 to GHL but write a ghlActivityLog warning with eventType, ghlContactId, and reason="contact_not_found". Do not silently drop the event.

This helps find contacts created directly inside GHL that have not synced back.

⸻

P1 Patch 5 — Permission field sync should avoid repeated expensive dry runs if Wave 1A payload already exists

The plan says use ghlPermissionPayload if available or call evaluateContactability() five times.

That is fine, but lock the order:

Prefer existing Wave 1A ghlPermissionPayload from the current contactability evaluation if already available in the caller context.
If not available, compute a five-channel dry-run matrix.
Do not call enforcement mode.
Do not write consent audit logs.
Do not count these as outbound attempts.

⸻

P1 Patch 6 — Dashboard should label external GHL config gap clearly

The plan says external GHL fields must exist. Good. The dashboard should show this as a real operational warning if 422s happen.

Patch:

If recent 422 field write errors exist for lb_* permission fields, GhlSettings.tsx must display a warning: "One or more Replit permission fields are missing or misconfigured in GHL. External GHL workflows may not be safe until these fields are created and workflows branch on them."

⸻
