Verdict: NOT BUILD-READY — ARCHITECTURE PREFLIGHT REQUIRED

The goal is correct, but the proposed architecture would likely lose rescoring events, misstate current score behavior, and fail to cover bulk-created contacts.

Blocking corrections

1. Verify the claimed leadScore = null state

Earlier schema evidence showed contacts.lead_score defaults to 0, not NULL.

The task must distinguish:

* never scored: lastScoredAt IS NULL;
* legitimately scored zero: leadScore = 0 AND lastScoredAt IS NOT NULL;
* stale score: scoring model/input changed after lastScoredAt.

Do not use leadScore IS NULL or leadScore = 0 as the trigger authority.

2. writeContact() is not universal across all intake paths

The existing bulk CSV path was previously confirmed to use bulk inserts rather than writeContact() per row.

Therefore this claim is false:

Hooking writeContact() makes the trigger universal across every intake path.

The task must either:

* add one canonical post-write batch enqueue after bulk inserts; or
* explicitly scope this task to contacts created through writeContact() and list uncovered paths.

Do not claim CSV coverage unless the bulk importer is actually wired.

3. A durable DB row is required

BullMQ persistence alone is insufficient because Redis can be unavailable before the job is accepted.

Create a dedicated table, such as contact_lead_scoring_jobs, with:

id
contactId
requestedGeneration
processedGeneration
status
triggerSources
enqueueAttempts
executionAttempts
nextAttemptAt
lastErrorCode
createdAt
updatedAt
completedAt

Required states should distinguish:

pending_enqueue
queued
processing
retry_wait
completed
contact_not_found
deferred_queue_unavailable
failed_terminal

Do not use system_settings for per-contact durable work.

4. Contact-only idempotency can suppress legitimate future rescoring

A permanent BullMQ key like:

contact-lead-scoring:<contactId>

may prevent a later meaningful mutation from producing a new job.

Use coalescing generation semantics:

* each relevant request increments or advances requestedGeneration;
* one active job per contact processes the latest generation;
* after scoring, set processedGeneration;
* if another request arrived while processing, enqueue/run again.

This prevents duplicate simultaneous work without losing newer scoring requests.

5. Last-writer-wins is not a sufficient race policy

A mass backfill may read old contact inputs, then overwrite a newer per-contact score after the contact changes.

Use an input-version guard. For example:

1. Read the contact and capture a canonical scoring-input timestamp/version.
2. Compute the score.
3. Update only when the current scoring-input version still matches.
4. If it changed, mark the job dirty/retry.

At minimum, use the timestamp representing the last mutation to any scoring-dependent field—not generic updatedAt if unrelated writes modify it.

The batch backfill and per-contact scorer must share this guarded write method. That may require a small targeted change to the batch job despite the current “do not modify” instruction.

6. Define the exact scoring-dependent fields

Create and export:

LEAD_SCORING_DEPENDENT_FIELDS

The set must match the actual inputs used by the existing scoring algorithm, including related data if applicable:

* contact fields;
* deals;
* email logs;
* call logs;
* sequence/enrollment history;
* engagement history.

A contact-create hook alone will immediately produce incomplete behavioral scores if the algorithm depends on activity that happens later.

This task should establish the architecture, but later mutation/event triggers must be explicitly mapped.

7. Verify the single-contact function does not introduce N+1 or side effects

Do not blindly call scoreContactPageBulk([contactId]) unless preflight confirms:

* it accepts IDs rather than full rows;
* it performs safe bounded reads;
* it writes all score components and lastScoredAt;
* it does not trigger GHL, enrollment, routing, notifications, or outbound work;
* it uses the same algorithm and tier semantics as the mass scorer.

Create one canonical persistence function used by both batch and single-contact scoring.

8. Prove the enrichment queue is the correct owner

Before adding contact_lead_scoring, provide file:line evidence for:

* queue producer;
* job dispatcher;
* retry/backoff policy;
* stable jobId behavior;
* worker concurrency;
* terminal failure handling;
* Redis-unavailable startup behavior.

Do not add an arbitrary job type to ENRICHMENT merely because readiness scoring already runs there.

9. Do not repeat the existing non-durable catch pattern

The brief says to hook it into writeContact() using the same try/catch pattern as readiness.

The correct contract is:

* contact transaction commits;
* await enqueueLeadScoringRequest(...);
* the enqueue service first persists the durable DB request;
* Redis failure transitions it to deferred_queue_unavailable;
* contact creation still succeeds.

A catch that only logs after failing before durable persistence is unacceptable.

10. Recovery must be included

A deferred_queue_unavailable row needs the same recovery guarantees established for promotional enrollment:

* recurring bounded recovery;
* atomic claim with FOR UPDATE SKIP LOCKED;
* stable BullMQ identity;
* exponential backoff;
* retry cap;
* terminal state;
* aggregate observability.

Otherwise the task merely creates another abandoned-job table.

Corrected architecture

requestContactLeadScoring(contactId, triggerSource)
  → atomically upsert/coalesce durable DB request
  → attempt BullMQ enqueue with stable job identity
  → Redis unavailable: persist deferred state
  → return queued / coalesced / deferred
BullMQ worker
  → claim the durable request
  → load current scoring inputs and input version
  → run canonical existing scoring algorithm
  → guarded score update
  → mark generation processed
  → rerun if a newer generation arrived

Kill lines

* STOP if never-scored detection relies on leadScore = 0 or NULL.
* STOP if writeContact() is claimed to cover bulk CSV imports without evidence.
* STOP if BullMQ is the only durable source of truth.
* STOP if contact-only dedup permanently suppresses later rescoring.
* STOP if stale input can overwrite a newer score through last-writer-wins.
* STOP if the batch and per-contact paths use different scoring persistence semantics.
* STOP if Redis failure is handled only by logging.
* STOP if deferred requests have no recurring recovery worker.
* STOP if scoring triggers enrollment, GHL, routing, or outbound work.
* STOP if this task changes the behavioral scoring model or tier thresholds.

The correct task is a durable, coalescing, version-guarded per-contact scoring request system—not simply a new BullMQ job plus a writeContact() hook.
