Verdict: NOT BUILD-READY

The direction is right, but the proposed score still allows unsafe merges and does not solve multi-candidate ambiguity.

Blocking corrections

1. Correct the stated risk.
An exact-phone matcher will not match a transposed digit. The real risks are:
- shared business or call-center numbers;
- recycled numbers;
- parent/franchise numbers;
- duplicate merchant rows carrying the same phone;
- incorrect phone data already stored locally.
Keep the task focused on false exact-phone ownership, not approximate phone matching.
2. Score every candidate, not only the first phone result.
findMatchingMerchant() must collect all plausible candidates from:
- exact normalized phone;
- existing fuzzy-name + state search.
Compute a score for each, sort deterministically, and evaluate the best candidate.
Do not replace “return first phone match” with “score the first phone match.”
3. Add an ambiguity-margin rule.
A candidate above 60 is not safe when another candidate scores nearly the same.
Required outcomes:
- accepted: best score meets threshold and clearly exceeds runner-up;
- low_confidence: best score below threshold;
- ambiguous: multiple candidates fall within a defined margin;
- unmatched: no candidate signals exist.
Example:
REGISTRY_MATCH_THRESHOLD = 60
REGISTRY_MATCH_MARGIN = 15
Accept only when:
best.score >= 60
AND best.score - secondBest.score >= 15
Otherwise, do not update a merchant.
4. Do not allow name + state alone to become an accidental new matching policy.
With the proposed weights:
strong name = 50
state = 10
total = 60
That means a strong-name/state match is accepted with no phone, even though this task is described as hardening the phone path.
The existing fuzzy-name path uses its own verified threshold and tie-breakers. Preserve it unless explicitly redesigning it.
Recommended phone-path contract:
- exact normalized phone: required for this path;
- weak name similarity: supporting evidence;
- strong name similarity: stronger supporting evidence;
- state match: supporting evidence;
- phone alone never sufficient.
Do not silently replace the existing second-tier fuzzy matcher with a new weighted algorithm.
5. Require corroborating business identity for an automatic phone match.
A safe minimum could be:
- exact phone + compatible name; or
- exact phone + state + another confirmed business identifier.
Phone + state alone should not automatically merge.
Define how absent legal/business names are handled. Missing evidence is not the same as contradictory evidence.
6. Distinguish missing and conflicting evidence.
The scoring result should record component outcomes such as:
{
  phone: "exact" | "missing" | "different",
  name: "strong" | "moderate" | "weak" | "missing",
  state: "same" | "different" | "missing"
}
A strongly conflicting company name should apply a penalty or force review. It should not merely earn zero name points while phone evidence still dominates.
7. Make the scoring helper pure and typed.
Export a pure function returning:
{
  score: number;
  basis: RegistryMatchBasis[];
  contradictions: RegistryMatchContradiction[];
  outcome: "accepted" | "low_confidence" | "ambiguous" | "unmatched";
}
Do not encode matchBasis only as an unstructured comma-separated text string.
If the existing schema convention requires text, serialize stable reason codes, not prose.
8. Verify registry_import_log already logs all outcomes.
The Phase 3 audit stated that registryImportLog receives matched, unmatched, and skipped rows.
The task now claims only matched rows are logged.
Verify the live implementation before changing it. Add low_confidence and ambiguous outcomes without duplicating existing logging or changing unrelated statuses.
9. Verify status constraints and consumers before adding new values.
Search every reader of registryImportLog.status.
Confirm that:
- low_confidence
- ambiguous
will not break dashboards, aggregates, exports, or status validation.
Add any schema/type changes needed, but do not silently insert unknown statuses into a closed contract.
10. Persist the selected candidate and runner-up evidence.
For reviewed cases, logs should include at least:
- matchedMerchantId, when accepted;
- candidateMerchantId for rejected best candidate;
- matchConfidence;
- matchBasis;
- contradiction codes;
- runnerUpMerchantId and runnerUpConfidence when ambiguous;
- matching algorithm version.
This makes later review and algorithm changes auditable.
11. Validate score ranges with real production distributions before finalizing 60.
Run a read-only sample against historical registry rows and report:
- number automatically accepted;
- number low-confidence;
- number ambiguous;
- false-positive samples;
- percentage whose prior phone-only match would now be blocked.
Do not treat 40/30/50/10 and threshold 60 as proven merely because they are intuitive.

Corrected matching flow

A. Normalize the registry phone using the canonical phone helper.
B. Fetch all exact-phone candidates, not one row.
C. For every candidate:
   - confirm exact phone;
   - calculate name similarity;
   - compare state;
   - identify contradictions;
   - compute typed score and evidence.
D. Rank candidates deterministically.
E. Accept only when:
   - required corroborating evidence is present;
   - best score meets threshold;
   - ambiguity margin is satisfied;
   - no disqualifying contradiction exists.
F. Otherwise:
   - ambiguous when candidates are too close;
   - low_confidence when evidence is insufficient;
   - unmatched when no candidate exists.
G. Only accepted results may update sdrMerchants.

Kill lines

STOP if only the first exact-phone database result is scored.
STOP if exact phone alone can update a merchant.
STOP if phone + state without corroborating identity can update a merchant.
STOP if strong name + state silently becomes a replacement for the existing fuzzy-name path.
STOP if two similarly scored candidates are resolved by array order or lowest ID.
STOP if contradictory business names merely earn zero points without affecting eligibility.
STOP if low-confidence or ambiguous records modify sdrMerchants.
STOP if new registryImportLog statuses are added without auditing every consumer.
STOP if matchBasis is arbitrary prose that cannot be aggregated reliably.
STOP if the proposed threshold ships without a production-data distribution review.

Required validation

- One exact-phone candidate with a conflicting name is not applied.
- Exact phone plus strong compatible name is applied.
- Exact phone plus moderate compatible name and matching state follows the documented threshold.
- Exact phone plus state but incompatible name is not applied.
- Two merchants sharing the same phone and similar scores produce ambiguous.
- Best candidate exceeding the runner-up by the required margin can be accepted.
- Missing name does not get treated as a name contradiction.
- Existing fuzzy-name-only matching behavior remains unchanged.
- low_confidence and ambiguous rows are logged with stable evidence codes.
- No merchant fields change for rejected outcomes.
- Accepted log includes merchant ID, confidence, basis, and algorithm version.
- All existing registry import status consumers continue to work.

Final status: NOT BUILD-READY

The correct fix is not merely adding points to the existing first phone match. It needs all-candidate scoring, corroboration requirements, contradiction handling, and an ambiguity margin before an automatic merchant update is safe.
