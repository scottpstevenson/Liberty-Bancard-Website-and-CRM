Final Addendum to #884 — Confirm GHL Sync Preserves CSV-Applied Opt-Outs

Approved to build.

Goal

Add test coverage proving that when CSV import applies an opt-out/DNC state, the next GHL sync sends restrictive Liberty Bancard custom fields to GHL.

The important safety invariant:

CSV import must not only preserve local opt-out state.
It must also ensure downstream GHL sync does not erase or omit that opt-out signal.

Required behavior

After CSV import applies an opt-out to a contact, the next GHL sync upsert payload must include the restrictive custom fields, such as:

lb_opted_out_email = true
lb_do_not_contact = true, if applicable
lb_consent_tier = opted_out / do_not_contact, if mapped
lb_email_status = unsubscribed / opted_out, if mapped

Use the actual field names already configured in:

server/services/ghl-sync.ts

Do not invent new GHL custom field names unless the mapping already supports them.

Test location

Extend:

scripts/test-csv-import-opt-out-preservation.ts

Preferred over creating a separate test because this test should prove the full chain:

CSV import optOutApplied
→ local contact restrictive fields set
→ GHL sync payload includes restrictive fields

Test setup

Create or use a fixture contact.

Then simulate CSV import row that applies opt-out, for example:

emailStatus = unsubscribed / opted_out
consentTier = opted_out
optedOutEmail = true
doNotContact = true

After import, assert local DB fields remain restrictive.

Then run the existing GHL sync path with a mocked GHL client.

Mock GHL client requirement

Use the existing GHL sync service:

server/services/ghl-sync.ts

Mock the actual outbound GHL client/upsert function.

Do not call real GHL.

Assert the captured payload includes restrictive fields.

Required assertions

The test must assert:

CSV import applies opt-out locally
suppressNewLeadAutoEnrollmentForContact is called or suppression state exists
GHL sync attempts an upsert/update for the contact
GHL payload includes opted-out email custom field
GHL payload includes do-not-contact custom field when local DNC is true
GHL payload does not set contactable/subscribed values over restrictive local state
no sequence enrollment is created
no outbound email/SMS/voice/ringless is sent

Important distinction

This task should not require GHL sync to run because of the opt-out. It only verifies that if the contact is picked up by the normal GHL sync loop, the payload preserves consent state.

Do not change sync scheduling unless the test reveals the payload builder cannot represent opt-out fields.

Payload builder guard

If GHL sync has a central payload builder, test that helper directly and one service-level sync path.

Preferred coverage:

1. unit/helper assertion: contact → GHL payload contains lb opt-out fields
2. integration smoke: CSV import → mock GHL sync captures restrictive payload

Kill lines

STOP if the test calls real GHL.
STOP if GHL sync payload omits local optedOutEmail=true.
STOP if GHL sync payload omits local doNotContact=true when applicable.
STOP if GHL sync converts opted_out/unsubscribed back to subscribed/active.
STOP if CSV import preserves opt-out locally but GHL payload does not export it.
STOP if this task weakens contactability or consent logic.
STOP if this task creates sequence enrollments.
STOP if this task sends outbound.
STOP if this task triggers real GHL workflows instead of mocked sync.

Scope protection

sequence worker
new lead auto-enroll job
contactability rules
CAN-SPAM/unsubscribe footer
GHL workflow activation
deal creation
stage progression
SMS/voice/ringless flags

Only patch ghl-sync.ts if the test proves the opt-out fields are missing from the payload.
