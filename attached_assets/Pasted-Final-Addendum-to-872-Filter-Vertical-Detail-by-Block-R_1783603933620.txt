Final Addendum to #872 — Filter Vertical Detail by Block Reason

Approved to build.

Goal

Let admins filter the expanded vertical blocked-contact list by a specific block reason.

Example:

Restaurant → only no_email rows
Salon/Spa → only suppressed rows
Auto Repair → only no_sequence_mapped rows

Backend

Update:

GET /api/admin/pipeline/stage-health/vertical-detail

to accept optional query param:

blockReason

Allowed values should match the stable machine reason keys already used by the detail endpoint:

all
DNC
opted_out
suppressed
no_email
no_sequence_mapped
already_enrolled
contactability_blocked
sequence_inactive
unknown

Use the actual existing casing from the backend. Prefer lowercase machine keys if already established:

dnc
opted_out
suppressed
no_email
no_sequence_mapped
already_enrolled
contactability_blocked
sequence_inactive
unknown

Required behavior

Default:

blockReason omitted or blockReason=all
→ existing behavior

Filtered:

blockReason=no_email
→ only rows whose computed primary block reason is no_email

The filter must be applied against the same computed block-reason logic used by the detail rows and aggregate counts.

Do not create a second, inconsistent reason calculator.

Important backend guard

If block reason is computed in TypeScript after loading rows, it is acceptable to filter after computation only if pagination still behaves correctly.

Preferred:

compute block reason in the query or in a shared helper before slicing/pagination
then paginate filtered results

Avoid this bug:

fetch first 50 rows
then filter to no_email
→ user sees only 3 rows even though there are 200 no_email rows later

Correct order:

load/compute eligible vertical rows
apply blockReason filter
then apply limit/offset

Pagination

Keep existing pagination rules:

default limit 50
max 200
offset supported

Response should include enough metadata for filtered paging:

{
  total: number;
  limit: number;
  offset: number;
  blockReason: string;
  rows: [...]
}

total should mean the total matching the selected reason, not the total across all reasons.

VerticalDetailPanel

Options:

All reasons
DNC
Opted out

Sequence inactive
Unknown

When selected:

re-fetch vertical detail with blockReason query param
reset offset/page to 0
show loading state
render filtered result count

UI copy

Show a small summary like:

Showing no_email blockers for Restaurant

or:

Showing all blocked contacts for Restaurant

Scope protection

Do not:

enroll contacts
edit contacts
suppress or unsuppress contacts
change mappings
toggle autoEnrollNewLeadDeals
change contactability logic
change suppression logic
create deals
trigger GHL sync
send outbound

Kill lines

STOP if filtering writes data.
STOP if filtering changes suppression/DNC/contactability state.
STOP if filtering triggers enrollment.
STOP if filtering changes vertical sequence mappings.
STOP if blockReason filtering is applied after pagination and hides matching rows.
STOP if invalid blockReason values cause a server error instead of a safe 400.
STOP if the backend uses different reason logic than the aggregate/detail rows.
STOP if role guards are weakened.

Validation

Extend:

scripts/test-stage-health-vertical-breakdown.ts

Test cases:

1. omitted blockReason returns all detail rows
2. blockReason=all returns all detail rows
3. blockReason=no_email returns only no_email rows
4. blockReason=dnc returns only DNC rows
5. blockReason=suppressed returns only suppressed rows
6. invalid blockReason returns safe 400
7. filtering happens before pagination
8. total reflects filtered count
9. UI resets pagination when reason changes
10. no enrollment/suppression/mapping mutation occurs
