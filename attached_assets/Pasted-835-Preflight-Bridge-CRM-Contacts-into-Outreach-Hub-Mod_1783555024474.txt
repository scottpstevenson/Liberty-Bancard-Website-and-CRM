835 Preflight — Bridge CRM Contacts into Outreach Hub

Mode

Read-only investigation and implementation plan only.

Do not change code.
Do not run migrations.
Do not create prospect rows.
Do not enqueue jobs.
Do not trigger outreach, sequence enrollment, deal creation, GHL workflows, or enrichment.

Goal

Determine the safest build plan for bridging CRM contacts into the Outreach Hub so the Hub can surface the full contacts pool, not only the smaller discovery/prospects pool.

The main question:

Should we materialize CRM contacts into the prospects table,
or should Outreach Hub use a read-through/union query that combines prospects + contacts?

Context

The current suspected gap:

prospects table: ~8,167 rows
contacts table: ~153,887 rows
contacts with linked prospect: ~942
Outreach Hub currently appears blind to most CRM contacts

We need to verify this with live code/data before building.

3. Confirm current prospect/contact bridge state

Run read-only queries.

Required counts:

SELECT count(*) FROM contacts;
SELECT count(*) FROM prospects;
SELECT count(*) FROM prospects WHERE contact_id IS NOT NULL;
SELECT count(*)
FROM contacts c
WHERE NOT EXISTS (
  SELECT 1 FROM prospects p WHERE p.contact_id = c.id
);

Also report:

SELECT vertical, count(*)
FROM contacts
GROUP BY vertical
ORDER BY count(*) DESC
LIMIT 25;

And if possible:

SELECT lead_source, count(*)
FROM contacts
GROUP BY lead_source
ORDER BY count(*) DESC
LIMIT 25;

6. Determine best implementation option

Compare two options.

Option A — Materialized bridge rows

CRM contacts without prospects get inserted into prospects with source/origin = crm_bridge.

Evaluate:

What schema change is needed?
Can uniqueness on contactId be safely enforced?
Will this inflate prospects table by ~153k rows?
Will existing Outreach Hub filters/actions work?
Which actions must be disabled for crm_bridge?
How to make job idempotent?

Option B — Read-through union

Outreach Hub backend query returns native prospects plus CRM contacts that lack prospects, without inserting 153k rows.

Evaluate:

What endpoint/query changes are needed?
Can UI distinguish discovery prospects vs CRM contacts?
Can search/filter/pagination still work?
Can sequence enroll actions use contactId directly?
Can convert action be hidden for contact-backed rows?
Would this avoid schema/table bloat?
