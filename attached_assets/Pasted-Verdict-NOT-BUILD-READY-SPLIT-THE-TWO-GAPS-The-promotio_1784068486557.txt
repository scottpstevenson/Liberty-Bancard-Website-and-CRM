SPLIT TASK #991 BEFORE BUILD

Create two tasks:

* 991A — Prospect-to-Contact Promotion Eligibility
* 991B — Canonical Vertical Resolution and Bridge Synchronization

Do not ship both behavioral changes in one task.

991A — Prospect-to-Contact Promotion Eligibility

1. Verify what is actually being scored

dataReadinessScore is a contacts model. Before implementation, confirm whether prospects contain:

* dataReadinessScore
* readinessBreakdown
* readinessModelVersion
* the exact fields required by computeDataReadinessScore()

Do not read a “linked contact’s” readiness before conversion; the purpose of conversion is to create the contact.

If prospects do not persist readiness, add a pure adapter:

computeProspectConversionReadiness(prospect)

It may reuse the readiness scoring rules, but it must not pretend a transient prospect score is the persisted contact readiness score.

Return it as conversionReadinessScore or previewReadinessScore.

2. Do not make readiness alone the promotion authority

Readiness measures data completeness, not:

* consent;
* contactability;
* identity confidence;
* duplicate-contact safety;
* permission to enroll.

The gate may block obviously incomplete records, but successful conversion must not imply promotional enrollment eligibility.

After conversion, promotional enrollment must still use the durable canonical enrollment job and current contactability checks.

3. Remove the query-string force override

Do not use:

?forceConvert=true

A query parameter is too weak for a compliance-sensitive bulk bypass.

Use an explicit request body:

{
  "prospectIds": [1, 2, 3],
  "override": {
    "enabled": true,
    "reason": "operator-reviewed"
  }
}

Requirements:

* admin-only;
* typed reason required;
* confirmation required in the UI;
* aggregate audit event with actor, prospect IDs/count, threshold, scores and reason;
* no override for unauthenticated, agent or manager roles unless explicitly approved.

The single-convert route needs the same protected override contract.

4. Do not use an unconstrained environment variable as policy authority

PROSPECT_CONVERSION_MIN_READINESS can change silently between processes and deployments.

Prefer a canonical server constant or persisted system setting with:

* integer validation from 0–100;
* default;
* audit history for changes;
* value returned in API responses.

If an environment variable remains, validate it once at startup and fail closed on invalid values. Do not parse it independently per request.

5. Preserve partial-success semantics precisely

Batch conversion must return per-row outcomes, not only aggregate counts:

{
  results: [
    {
      prospectId,
      status:
        | "converted"
        | "skipped_readiness"
        | "duplicate_contact"
        | "invalid"
        | "failed",
      score,
      threshold,
      contactId?,
      dealId?,
      reasonCode?
    }
  ],
  summary: {
    requested,
    converted,
    skipped,
    failed
  }
}

Do not return HTTP 200 while hiding conversion failures inside a generic skipped count.

Single conversion may return a typed 422 for an eligibility block rather than 400, because the request itself is valid.

6. Make conversion idempotent

Before creating a contact, verify the existing conversion contract:

* Does prospect.contactId already prevent re-conversion?
* Is email deduplication race-safe?
* Can two batch requests convert the same prospect concurrently?
* Is contact creation, prospect linkage and deal creation transactional?

The readiness check must not introduce a check-then-create race.

Use a database-level claim/transaction so one prospect produces one canonical conversion.

7. Do not compute inline with side effects or model drift

The readiness function used here must be:

* pure;
* versioned;
* safe for prospect-shaped data;
* free of DB writes;
* free of GHL, scoring, enrollment and notification calls.

Include the readiness model version in the response and audit record.

8. Define what happens after conversion

A conversion that passes readiness must:

1. create/link the contact safely;
2. persist normal contact readiness through the canonical contact writer/recalculation path;
3. enqueue promotional enrollment through the existing durable service only if that is current product behavior;
4. never call autoEnrollFromTrigger() directly.

Do not preserve the unsafe immediate enrollment behavior described in the task context.

991B — Canonical Vertical Resolution and Bridge Synchronization

1. Audit the actual vertical fields first

The proposed priority depends on fields that may not exist:

* contact.verticalOverride
* sdrMerchant.enrichmentSource
* source/confidence for contacts.vertical
* source/confidence for sdrMerchant.subvertical

Provide file:line evidence for every field before implementing the resolver.

If the database does not record vertical provenance and override state, the requested five-tier priority cannot be implemented reliably from values alone.

2. Do not infer authority from the current string value

A value such as "Healthcare" does not reveal whether it came from:

* an operator;
* a public form;
* GHL;
* CSV classification;
* enrichment.

The resolver needs metadata such as:

{
  value,
  source,
  confidence,
  manuallyOverridden,
  updatedAt
}

Without provenance, do not claim that operator override or enrichment reliably wins.

3. Preserve coarse and fine-grained taxonomy separately

contacts.vertical, sdrMerchants.vertical and sdrMerchants.subvertical may represent different levels.

Do not write "Med Spa" into a field whose consumers expect coarse values such as "Healthcare".

The canonical result should likely contain both:

{
  vertical: "Healthcare",
  subvertical: "Med Spa",
  source: "outscraper",
  confidence: 0.94
}

Audit every consumer before changing stored values, especially template selection and analytics.

4. Do not overwrite contact.vertical during a read/bridge operation by default

Bridging to SDR should not silently mutate the CRM’s canonical data merely because another table has a preferred value.

Safer first scope:

* resolve the effective SDR vertical;
* write it to the newly created sdrLeadState;
* record the resolution source and reason;
* leave contacts.vertical unchanged unless a dedicated synchronization policy authorizes the update.

Writing back to contacts requires:

* manual-override protection;
* source-confidence comparison;
* audit log;
* stale-write guard;
* downstream regression testing.

5. Keep one resolver pure

Implement a pure function such as:

resolveCanonicalVertical({
  contactVertical,
  contactVerticalSource,
  operatorOverride,
  merchantVertical,
  merchantSubvertical,
  merchantVerticalSource,
  merchantConfidence
})

Return:

{
  vertical,
  subvertical,
  source,
  confidence,
  reasonCode
}

The pure resolver must not write to either table.

A separate synchronization service owns any persisted changes.

6. “High confidence” must be data-backed

Do not classify all Serper, Outscraper or Apify results as high-confidence solely from the provider name.

Use the actual confidence/evidence fields if present.

If none exist, define conservative source-specific rules and clearly label them as provisional. Missing confidence must not be treated as high confidence.

7. Audit all bridge owners

Confirm the real function and every caller of bridgeContactsToSdr().

Verify whether other bridge/import paths independently set:

* sdrLeadState.vertical
* sdrMerchants.vertical
* sdrMerchants.subvertical

All bridge writers must use the same resolver or the drift remains.

Kill lines

* STOP if prospects are treated as having persisted contact readiness without schema evidence.
* STOP if readiness is treated as contactability or permission to enroll.
* STOP if an admin override is accepted through a query parameter without audit.
* STOP if concurrent conversions can create duplicate contacts or deals.
* STOP if immediate autoEnrollFromTrigger() remains in the conversion path.
* STOP if vertical priority is implemented without source/provenance evidence.
* STOP if fine-grained subvertical values overwrite coarse vertical fields.
* STOP if bridging silently overwrites an operator-controlled contact vertical.
* STOP if provider name alone is treated as high-confidence classification.
* STOP if only one of multiple bridge writers adopts the resolver.

Required validation for 991A

* Prospect below threshold is not converted and creates no contact/deal/enrollment.
* Prospect at the exact threshold follows the documented inclusive rule.
* Mixed batch returns one typed result per requested prospect.
* Two concurrent conversions of one prospect create one contact and one linkage.
* Duplicate-email prospect resolves through the canonical duplicate contract.
* Admin override requires role, reason and audit.
* Manager/agent cannot override.
* Successful conversion still passes through durable enrollment/contactability.
* Replaying the request is idempotent.
* Persisted contact readiness is calculated through the canonical post-create path.

Required validation for 991B

* Operator override wins only when an actual override flag/source exists.
* High-confidence enriched subvertical maps to the correct coarse vertical.
* Raw form input does not overwrite stronger evidence.
* GHL value is lowest authority only when its provenance is known.
* Missing provenance produces a conservative result, not a fabricated priority.
* Bridge writes effective SDR vertical without mutating CRM by default.
* Manual override remains unchanged.
* All template-selection consumers receive valid canonical taxonomy values.

Final status

Task #991 should not build as one task.

Proceed with 991A first, because it closes the direct unsafe bulk-promotion path. Build 991B only after the vertical provenance fields and taxonomy expectations are verified.
