Final Addendum to #871 — Prevent Double Enrollment from Overlapping Auto-Enroll Runs

Approved to build with a stronger requirement: protect both the job and the enrollment write.

Core Problem

runNewLeadAutoEnrollCheck() can be triggered by the SLA worker. If two SLA ticks overlap, both runs may evaluate the same New Lead deal/contact before either enrollment is visible to the other.

That can cause duplicate sequence enrollments unless the enrollment write is atomic/idempotent.

Required Fix

Implement two protections:

1. Re-entrancy guard for runNewLeadAutoEnrollCheck()
2. Atomic duplicate protection in createSequenceEnrollment()

Do not rely on only one.

Step 1 — Preflight Existing Constraints

Inspect:

shared/schema.ts
server/storage/automation.ts
migrations/

Confirm whether sequence_enrollments already has a unique index/constraint for:

contactId + sequenceId

or:

contactId + sequenceId + active/pending status

Run a read-only duplicate audit before adding any constraint:

SELECT contact_id, sequence_id, status, count(*)
FROM sequence_enrollments
GROUP BY contact_id, sequence_id, status
HAVING count(*) > 1
ORDER BY count(*) DESC;

Also audit active duplicate risk:

SELECT contact_id, sequence_id, count(*)
FROM sequence_enrollments
WHERE status IN ('active', 'pending', 'queued', 'running')
GROUP BY contact_id, sequence_id
HAVING count(*) > 1
ORDER BY count(*) DESC;

Use the actual status values from the schema/codebase.

Step 2 — Add Job Re-entrancy Guard

In:

server/services/new-lead-enrollment-job.ts

Add a guard for runNewLeadAutoEnrollCheck().

Preferred:

DB-backed lock / system_settings lock / advisory lock

Acceptable only for single-process deployment:

process-local _autoEnrollCheckRunning flag

But if the app can run more than one server instance, process-local is not enough.

Recommended behavior:

if auto-enroll check is already running:
  skip current tick
  write/log new_lead_auto_enrollment_tick_skipped_already_running

Do not throw and crash the SLA worker.

Step 3 — Make Enrollment Creation Idempotent

In:

server/storage/automation.ts
createSequenceEnrollment()

Ensure duplicate enrollment attempts for the same contact + sequence are safe.

Preferred behavior:

createSequenceEnrollment(contactId, sequenceId)
→ if active/pending enrollment already exists, return existing/skipped result
→ do not create duplicate row

Do not depend on a pre-check followed by insert without a DB-level guard. That is still race-prone.

DB Constraint / Index

If business rules allow only one enrollment per contact per sequence forever, add:

CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS idx_sequence_enrollments_contact_sequence_unique
ON sequence_enrollments(contact_id, sequence_id);

If historical/completed re-enrollment is allowed, add a partial unique index for active-like statuses only:

CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS idx_sequence_enrollments_active_contact_sequence_unique
ON sequence_enrollments(contact_id, sequence_id)
WHERE status IN ('active', 'pending', 'queued', 'running');

Use the actual status values in the codebase.

Kill line:

STOP if adding the index would fail because existing duplicate active enrollments already exist.

If duplicates exist, report them and do not blindly delete production data.

Atomic Insert Behavior

If using Postgres upsert/unique index:

INSERT ... ON CONFLICT DO NOTHING

or equivalent Drizzle pattern.

Return a clear result:

{
  created: boolean;
  enrollmentId?: number;
  skippedReason?: "already_enrolled";
}

Do not make duplicate attempts look like successful new enrollments.

Candidate Mode Safety

Confirm this does not break candidate-only mode:

autoEnrollNewLeadDeals=false
→ audit candidate_detected
→ no enrollment write attempted

Auto Mode Safety

Confirm:

autoEnrollNewLeadDeals=true
→ one enrollment created
→ second overlapping run skips or receives duplicate conflict safely

Kill Lines

STOP if overlapping runNewLeadAutoEnrollCheck() calls can create duplicate enrollments.
STOP if the fix only adds an in-memory flag but createSequenceEnrollment remains race-prone.
STOP if a DB unique index is added without auditing existing duplicates first.
STOP if duplicate conflicts crash the SLA worker.
STOP if duplicate skip is not audited/logged.
STOP if candidate mode starts creating enrollments.
STOP if this task changes send execution, contactability, GHL sync, deal creation, or CAN-SPAM logic.
STOP if SMS/voice/ringless behavior is changed.

Validation

Add or extend:

scripts/test-new-lead-enrollment-policy.ts

or create:

scripts/test-new-lead-enrollment-concurrency.ts

Required tests:

1. two parallel createSequenceEnrollment() calls for same contactId + sequenceId create only one row
2. second duplicate attempt returns/skips with already_enrolled
3. two parallel runNewLeadAutoEnrollCheck() calls do not create duplicate enrollments
4. candidate mode still writes candidate_detected audit and creates zero enrollments
5. auto mode creates exactly one enrollment
6. second auto mode run creates zero additional enrollments
7. duplicate skip does not crash SLA worker
8. no outbound sent
9. no GHL sync triggered
10. no deals created

Run:

npx tsx scripts/test-new-lead-enrollment-concurrency.ts
npx tsx scripts/test-new-lead-enrollment-policy.ts
npx tsx scripts/smoke-role-guards.ts
