Verdict: NOT BUILD-READY — 4 MATERIAL CORRECTIONS

The preflight found the real risk, but the proposed solution still has four production problems.

1. Do not make every public form silently update an existing contact

An email match does not automatically prove that the submitter should mutate that contact’s profile.

The existing-contact branch must define exactly which fields may be refreshed. At minimum:

* consent fields go through the channel-specific merge;
* protected compliance fields remain unchanged;
* identity/profile fields require an explicit allowlist;
* existing contact ownership and downstream deal behavior remain unchanged.

Do not pass arbitrary form fields into storage.updateContact() merely because the email matched.

2. Fix the GHL-first ordering, not only the local consent merge

The principal bug occurs before the local insert fails:

1. upsertGhlContact() receives incoming consent.
2. GHL is updated.
3. Local insert gets 23505.

An email prelookup must therefore happen before any GHL upsert.

For existing contacts:

* run the consent merge against persisted local state;
* build a protected, allowlisted GHL update payload;
* never send blocked consent values to GHL;
* perform the local update and consent audit atomically;
* synchronize only the permitted resulting state to GHL through the canonical update path.

Do not call writeContact({ mode: "ghl_upsert_first" }) and hope the later local guard repairs GHL.

3. doNotAutoContact is not automatically a consent-withdrawal signal

doNotAutoContact may prohibit automated outreach without representing withdrawal of the underlying channel consent.

Do not automatically block changing consentEmail or consentSms solely because doNotAutoContact === true unless the canonical compliance contract explicitly defines that behavior.

Keep these concepts separate:

* consent state: whether the person granted or withdrew channel consent;
* automation restriction: whether automated contact is permitted;
* global DNC: a stronger prohibition.

doNotAutoContact should continue blocking enrollment/send through contactability. It should not silently rewrite the consent-merge policy without verified semantics.

4. Do not use read-before-insert for audit idempotency

This is race-prone:

SELECT existing audit
if none:
  INSERT audit

Add the database constraint first and use targeted conflict handling.

A partial unique index should include contact identity as well as submission identity, for example:

CREATE UNIQUE INDEX consent_reenable_blocked_event_unique
ON consent_audit_logs (contact_id, form_id, channel)
WHERE action = 'consent_reenable_blocked';

Using only (form_id, channel) risks collisions if form IDs are not globally unique across contacts or form systems.
