Final Addendum to #865 — Confirm GHL Opt-Out Suppression Works Without GHL Contact ID

Approved to build with one correction: fallback matching must be deterministic, not fuzzy.

Required behavior

When a GHL opt_out webhook arrives:

If ghlContactId matches a CRM contact:
  suppress that contact
Else if webhook has an email:
  normalize email
  find CRM contact(s) by exact normalized email
  suppress matched contact(s)
Else if webhook has a phone and the system already supports exact normalized phone lookup:
  normalize phone
  find CRM contact(s) by exact normalized phone
  suppress matched contact(s)
Else:
  store webhook event
  write anomaly audit/alert
  do not guess

Core rule

GHL opt-out suppression must not depend exclusively on contacts.ghlContactId.

Contacts can opt out in GHL before the GHL contact ID is persisted locally. Those opt-outs still need to suppress future New Lead auto-enrollment when a deterministic identifier exists.

Do not use fuzzy matching

Not allowed:

name-only matching
company-only matching
partial email matching
partial phone matching
fuzzy name + company heuristics

Allowed:

exact normalized email
exact normalized phone if already canonicalized safely
ghlContactId

Implementation requirements

In:

server/services/sdr/webhook-handlers.ts

Update handleOptOut so it:

stores the webhook event/log regardless of match result
attempts ghlContactId lookup first
falls back to exact normalized email lookup
optionally falls back to exact normalized phone lookup
calls suppressNewLeadAutoEnrollmentForContact(contactId, reason)
sets contact opt-out fields if appropriate
writes audit log for matched suppression
writes anomaly audit/log for unmatched opt-out

Use existing contact update paths where possible so contactability and consent state remain canonical.

Suppression helper

Use the existing helper from #859:

suppressNewLeadAutoEnrollmentForContact(contactId, reason)

Reason should be specific:

ghl_opt_out
ghl_opt_out_email_match
ghl_opt_out_phone_match

Multiple contacts with same email

If exact normalized email matches multiple CRM contacts, suppress all matching contacts and audit that multiple matches occurred.

Do not pick one silently.

Audit metadata should include:

matchedBy: "email"
matchedCount
emailHash or redacted email if the project avoids raw PII in audit logs

Unmatched opt-out anomaly

If no CRM contact can be resolved, write an audit/action such as:

ghl_opt_out_unmatched_contact

Include safe metadata:

ghlContactId if present
email present yes/no
phone present yes/no
reason: no_contact_match

Do not drop the webhook silently.

New Lead auto-enrollment guard

Confirm:

server/services/new-lead-enrollment-job.ts

still skips contacts that are:

opted out
email unsubscribed
suppressed from New Lead auto-enrollment

The webhook fallback is a back-pressure path into that existing guard.

Kill lines

STOP if GHL opt-out suppression only works when ghlContactId is present.
STOP if unmatched GHL opt-outs are silently ignored.
STOP if fuzzy/name-only matching is used.
STOP if exact email match does not call suppressNewLeadAutoEnrollmentForContact.
STOP if multiple contacts with the same email cause only one to be suppressed without audit.
STOP if runNewLeadAutoEnrollCheck can re-enroll a contact after a matched GHL opt-out.
STOP if contactability/consent logic is weakened.
STOP if GHL opt-out handling sends outbound, creates deals, or triggers GHL sync.
