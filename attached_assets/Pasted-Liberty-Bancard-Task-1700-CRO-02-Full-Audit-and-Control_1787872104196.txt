6. P0 Correction Register

P0-01 — Separate commercial truth from readiness

Problem: Task #1700 makes resolved identity, source, and decision-maker relationship prerequisites for production promotion/readiness as though they were the same state.

Required correction: Preserve the five-value commercial class as real/test/demo/synthetic/unknown. Build provenance, identity, organization-link, relationship, and purpose decisions as separate versioned axes. A decision-maker relationship can gate a marketing policy but cannot determine whether a real merchant/user/support contact is production.

P0-02 — Freeze the class/reason vocabulary

Problem: The task lists unknown, untraceable, and legacy-unknown together as though all are root classes.

Required correction: Do not expand record_class for these conditions. Use stable, documented provenance/quarantine reason codes such as SOURCE_UNTRACEABLE, LEGACY_MAPPING_UNKNOWN, IDENTITY_COLLISION, REQUIRED_LINK_MISSING, and LINKED_ROOT_NON_PRODUCTION. Unknown class and unknown provenance must remain independently reportable.

P0-03 — Freeze the exact graph ownership matrix

Problem: “At minimum cover” leaves the executor free to add competing mutable class columns to applications, MIDs, tasks, campaign rows, imports, and event records.

Required correction: Adopt the root/derived/evidence/snapshot table in Section 5.2. Only canonical businesses join the existing contact/deal/prospect/legacy-company class roots. Derived records resolve or snapshot; ledger/evidence records do not become roots.

P0-04 — Freeze purpose-specific dependencies

Problem: “Every required linked root” is undefined and could block legitimate reporting/payout or allow unsafe outreach.

Required correction: Implement a versioned purpose-policy matrix at least for commercial reporting, financial payout, marketing pre-spend, marketing outreach handoff, transactional response, and internal test. Tests must prove both required and explicitly non-required dependencies.

P0-05 — Eliminate vacuous linked-root success

Problem: getLinkedClassesInTransaction() filters missing left joins out. A missing contact/company can become an empty array instead of a denial reason.

Required correction: For every purpose, explicitly validate: subject exists; required FK exists; referenced row exists; redirect resolves; class is acceptable; and graph version is current. Missing rows and links return stable fail-closed reasons. Never treat an empty dependency set as production unless the policy explicitly declares that dependency optional.

P0-06 — Make evidence typed, immutable, and subject-bound

Problem: Current command evidence is an allowlisted short JSON/string structure; source-event immutability and same-contact primary-pointer integrity are not fully enforced.

Required correction: Introduce typed evidence references with existence, subject, purpose, version/hash, and retention validation. Supported evidence types must be explicitly enumerated. Enforce that contacts.primary_source_event_id points to an event for the same contact. Make source-event identity/source/fingerprint fields immutable, permit only documented monotonic observation updates, and block silent deletion or mutation.

P0-07 — Establish one canonical business/link authority

Problem: The premise that one business-ingest owner already exists is false. Organization resolver, storage, SDR dedupe/re-enrichment, routes, and scripts write business rows or links.

Required correction: Inventory and classify every writer. Keep existing non-authority enrichment writers only for allowed descriptive fields. Route class projection, verified organization-link state, evidence, and graph versions through one authority. Omit new authority fields from insert/update schemas. A bare contacts.business_id is a compatibility projection, not proof; new verified link + evidence + projection must commit atomically or reconcile durably.

P0-08 — Define legacy-company mapping without copying

Problem: Legacy companies links are not canonical businesses links, and the current task does not specify mapping state.

Required correction: Add an explicit reviewed legacy_company ↔ canonical_business mapping/evidence contract with states verified, conflicted, legacy-unknown, and rejected. Existing unmapped rows remain fail closed for purposes that require canonical organization proof. Do not copy companies, guess from names/domains/phones, or revive legacy company write ownership.

P0-09 — Define identity readiness and its concurrency fence

Problem: BT-07 provides observations and reviewed merge, but the task leaves “resolved identity” undefined.

Required correction: Resolve active redirects to an effective contact with depth/cycle denial; detect eligible-token collisions across live contacts; classify unresolved/collision/conflict without merging; define whether each purpose requires at least one eligible identity; store a deterministic identity generation/fingerprint. Coordinate identity/provenance/business-link updates and classification execution with a shared subject-generation/advisory-lock protocol so concurrent inserts cannot evade row locks. No phone-only automatic merge.

P0-10 — Replace mutable decision-maker flags with one reviewed relationship authority

Problem: The same PATCH route is registered in contacts.ts and conversation-ai-config.ts; one path uses raw DB update; enrichment writes the fields from title heuristics; generic contact field authority does not protect them.

Required correction: Create one business-scoped contact relationship authority with exact states known_positive, known_negative, candidate, unknown, conflicted, evidence/reason, actor, policy version, and optimistic lock. Title heuristics may create candidate observations only. Migrate both endpoints and enrichment writes to this authority, remove duplicate route registration, protect compatibility projection fields from generic writers, apply current object authorization, and distinguish reviewed negative from unknown.

P0-11 — Make classification commands exact, dual-control, and atomic

Problem: Preview collisions are not payload-checked; approval does not enforce a different actor; execution is not locked/version-bound/atomic; executor identity is not stored separately.

Required correction:

Canonicalize and hash preview input; exact replay returns the same command, divergent collision returns privacy-safe 409.

Validate subject and evidence at preview and store policy version plus root/graph fingerprint.

Reject requester=approver at approval and execution.

Lock command and required graph roots in deterministic order; revalidate subject, evidence, fingerprint, policy, identity, and link generation.

Commit event, root projection, graph projection/snapshot, and executed command state in one transaction, or use a durable executing state with deterministic reconciliation.

Store requester, approver, and executor separately; execute with status/version predicate.

P0-12 — Freeze the consumer migration matrix

Problem: “Only consumers within CRO-02’s blast radius” is not executable. Direct or missing class checks remain in analytics, digest, KPI, portfolio, residual/payout, funnel, and pre-spend paths.

Required correction: CRO-02 must migrate the commercial-purpose portion of:

P0-13 — Preserve CRO-03/CRO-04 boundaries

Problem: Task language can be read as universally fixing campaign, sequence, Ready, provider selection, and enrollment in CRO-02.

Required correction: CRO-02 exposes a versioned commercial-purpose decision/snapshot. CRO-03 later consumes it for provider pre-spend/economics/activation. CRO-04 owns consent, suppression, deliverability, channel-qualified Ready/cohort membership, and every sequence-enrollment path. CRO-02 may replace only the commercial-class component and must not activate providers, campaigns, sequences, or outreach.

P0-14 — Correct authorization and graph exposure

Problem: Manager “team” scope invents tenancy that does not exist, and generic business routes are broadly authenticated.

Required correction: Preserve current single-tenant policy: admin/manager global; agents own/unassigned/owned-deal scope. Define business scope through authorized linked contacts/deals and COUNT(DISTINCT business_id). Mixed-owner business details must not leak. Keep graph/evidence fields out of generic business row responses or harden directly affected routes to dashboard role/object scope. New agent-readable aggregate APIs must not be hidden under admin-only routing. Preserve privacy-safe 404 and safe error/correlation contracts.

P0-15 — Unify and transactionally fence import accounting

Problem: Six durable dispositions exist, but response/UI mapping omits updated; lease verification and row insert can race; completion summary/update is not one transaction; finalized immutability is incomplete.

Required correction: Define one shared summary contract:

total = created + matched_noop + updated + rejected + deferred + failed

Use it in the ledger service, compatibility csv_imports projection, replay/normal responses, UI, and tests. Display updated separately. Lease-fence disposition insertion in one transaction; exact replay succeeds and divergent replay conflicts. Complete under one locked/snapshot transaction with status='running', claim token, expected row count, and immutable finalized state. Prove crash, expiry/reclaim, replay, and all-six-disposition cases.
