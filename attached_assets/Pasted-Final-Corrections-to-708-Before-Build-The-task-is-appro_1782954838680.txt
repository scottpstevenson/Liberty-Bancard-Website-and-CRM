That is not enough for the new request object unless the token is also resolvable from statement_requests.

Generate a prefilled URL that routes to the existing statement upload flow that already runs the full statement upload chain.

* contact/deal linkage

* statement_requests status

Option B — Extend token handler to support statement_requests tokens

Update the upload token handler so it can resolve:

statement_requests.uploadToken

Then, when a merchant uploads with that token, it must update the matching statement_requests row and run the same real processing path used for normal statement uploads.

2. Split Sales Prep read vs generate routes

Do not make GET /api/contacts/:id/sales-prep generate paid AI output.

Use two routes:

GET /api/contacts/:id/sales-prep

Returns:

* whether the contact is SDR-sourced
* cached sales prep if it exists
* cache metadata
* canGenerate: true/false

And:

POST /api/contacts/:id/sales-prep/generate

Generates only after an explicit button click, checks persistent cache first, then calls OpenAI only if needed.

Kill line:

STOP if a GET request can trigger a paid OpenAI generation.

Kill line:

STOP if ContactDetail page load, tab visibility checks, or React Query prefetch can trigger paid AI generation.

⸻

3. Rename sdrSourceId on statement_requests

Do not use ambiguous naming.

Use:

sdrLeadStateId

not:

sdrSourceId

Reason: the relationship is to sdrLeadState.id, not to a generic SDR source or merchant source.

Kill line:

STOP if a new field name makes it unclear whether it references sdrLeadState, sdrMerchants, or lead source metadata.

⸻

4. Abandoned task dedup should use a stable request marker

The tasks table has no task type. Do not dedupe only with broad title matching like:

title ILIKE '%statement%'

Use a stable marker in the task description, such as:

statement_request_id:<id>

Before creating a task, query for an open pending task with that marker.

Kill line:

STOP if the abandoned-statement worker can create duplicate tasks because dedupe relies only on a broad title match.

⸻

5. Sales Prep tab visibility must not require generating prep

The ContactDetail UI should determine SDR-sourced status using a lightweight check:

* existing loaded contact/SDR relation if already available
* or GET /api/contacts/:id/sales-prep returning sdrSourced and cached state only

The tab should not generate prep just to decide whether it should render.
