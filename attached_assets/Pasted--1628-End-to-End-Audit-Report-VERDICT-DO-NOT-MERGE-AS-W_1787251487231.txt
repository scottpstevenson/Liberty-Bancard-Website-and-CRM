### P0-2 — Do not directly wire the current pre-deploy runner into CI

`scripts/pre-deploy.ts` is not currently a CI-safe canonical gate:

* It requires a 40-character `RELEASE_SHA`, which CI does not set.
* It imports the database before establishing test isolation.
* It writes global pause-control rows and `pre_deploy_last_result`.
* It does not restore the exact original pause state.
* Server-dependent “mandatory” suites can be skipped and counted as success.
* It contains operator/live-health suites mixed with deterministic CI tests.
* Its isolated pause-cycle suite is opt-in and excluded from ordinary CI.
* It contains broad route exemptions that are stale after #1629.

Exact fix:

1. Refactor the suite manifest to declare capabilities such as:

```ts
type SuiteCapability =
  | "pure"
  | "database"
  | "redis"
  | "server"
  | "fake_provider"
  | "operator_only";
```

2. Separate deterministic required CI suites from operator/live probes.
3. A skipped required CI suite must fail the job, never count as passing.
4. Set and validate:

```yaml
RELEASE_SHA: ${{ github.sha }}
TEST_DATABASE_URL: postgresql://...
DATABASE_URL: ${{ env.TEST_DATABASE_URL }}
TEST_REDIS_PREFIX: ci-${{ github.run_id }}-${{ github.run_attempt }}
```

5. Add a disposable Redis service.
6. Require fake transports for every provider, not only GHL.
7. Add a runner unit test using a synthetic failing child process to prove exit-code propagation. Do not deliberately break a real production suite.

### P0-4 — Repair migration reproducibility before adding a replay gate

Verified migration problems:

* Journal: 145 entries, high-water `0141`, timestamp `1792400000000`.
* Root SQL files: 146.
* `migrations/0091_merchant_onboarding_stages.sql` is not journaled.
* Duplicate journal timestamps exist for `0020` and `0024/0025`.
* Entries from approximately `0084` onward are future-dated relative to the audit date.
* `0109_fearless_starhawk.sql` is a large snapshot that recreates many previously created tables with unguarded `CREATE TABLE`.

Do not rewrite applied migrations.

Exact fix:

1. Add a static migration-integrity validator that:

   * maps every journal entry to one SQL file;
   * reports unjournaled files unless explicitly classified;
   * verifies SHA-256 hashes;
   * requires each new `when` value to exceed the existing maximum;
   * detects duplicate/out-of-order timestamps;
   * separately recognizes guarded migration `0054`.

2. Establish a tested fresh-database bootstrap policy for `0109`. A likely safe design is:

   * on a provably empty database, apply vetted snapshot `0109`;
   * record the verified earlier migration hashes as baselined;
   * apply `0110+`;
   * retain the normal upgraded-database path for existing installations.

3. Test that design on disposable databases before changing the runner.

The task’s proposed assertion is incorrect:

```sql
SELECT COUNT(*) FROM drizzle.__drizzle_migrations
```

cannot simply equal journal count because the runner can add the guarded `0054` record and a baseline sentinel. Validate expected `(hash, created_at)` records and required schema objects instead.

`server/db-migrate.ts:35-41` already documents that guarded `0054` is outside vanilla Drizzle replay; no duplicate comment is needed.
