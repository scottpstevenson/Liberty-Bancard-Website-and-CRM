Verdict: NOT BUILD-READY

The stable-identity architecture is correct, but the deployment sequence cannot work as written.

The largest blocker: createSlaTask(... ON CONFLICT ...) is deployed before the unique index exists. PostgreSQL will reject that insert because no matching unique constraint/index exists yet.

There is also a direct lifecycle contradiction: the index predicate includes every non-deleted task, including completed tasks.

Corrections to send back

Correct the migration and deployment sequence before implementation.
1. Resolve completed-task semantics.
The proposed index:
WHERE deleted_at IS NULL
still protects completed tasks when completed_at is set but deleted_at remains NULL.
Therefore this statement is currently false:
“Completed tasks are NOT protected.”
Choose one invariant:
A. One non-deleted SLA task per deal.
   Completed tasks continue blocking until soft-deleted.
B. One incomplete SLA task per deal.
   Add the verified canonical incomplete condition to the index predicate, such as:
   completed_at IS NULL
   or the correct task-status predicate.
Do not claim that completing/closing a task clears the lock unless the actual completion path sets deleted_at.
2. Fix the impossible deployment ordering.
PostgreSQL ON CONFLICT inference requires the matching unique index to already exist.
This sequence will fail:
- deploy createSlaTask with ON CONFLICT
- create index later
Use a staged rollout:
Phase 1 — Expand schema and compatible writer
- Add nullable source and automation_key columns.
- Update schema/types.
- Update the SLA worker to populate both fields.
- Continue using the existing createTask path temporarily.
- Deploy and verify new SLA tasks carry the identity fields.
Phase 2 — Audit, backfill, and deduplicate
- Run dry-run backfill.
- Review exact matched rows.
- Backfill only confirmed SLA tasks.
- Soft-delete all conflicting active rows according to the chosen lifecycle.
- Verify zero conflicts.
Phase 3 — Add unique index
- Apply the partial unique index migration.
- Verify the index exists with the exact expected definition.
Phase 4 — Enable conflict-safe creation
- Add/deploy createSlaTask using ON CONFLICT DO NOTHING.
- Switch sla-worker.ts to the new method.
- Run concurrency tests.
Alternatively, use an explicit feature-compatible storage path that detects whether the index exists, but do not deploy an ON CONFLICT target before its index exists.
3. Do not require two SLA cycles before backfill/index creation.
Two clean cycles from the process guard do not prove the future database constraint.
The required verification before index creation is:
- new writer fields are populated correctly;
- backfill scope is reviewed;
- zero conflicting rows remain.
Two-cycle observation can remain additional monitoring, not a migration gate.
4. Correct the historical backfill claim.
The title pattern is being used as the historical attribution heuristic because old records have no source field.
State explicitly:
- title matching is allowed only for the reviewed historical backfill;
- it is not the future canonical identity;
- matching rows must be inspected for false positives before apply.
The current kill line saying title cannot be the only identity “anywhere in backfill logic” contradicts the proposed script.
5. Do not use broad LIKE if the historical format is exact.
Prefer a reviewed, anchored pattern that verifies the suffix is a valid deal ID.
Do not classify:
- manual tasks with similar text,
- malformed titles,
- unrelated title variants.
Report unmatched variants separately rather than silently backfilling them.
6. Do not use IF NOT EXISTS as a substitute for migration correctness.
CREATE UNIQUE INDEX IF NOT EXISTS can silently accept an existing index with the same name but the wrong columns or predicate.
After migration, verify the actual index definition from PostgreSQL.
The migration should fail loudly if an incompatible same-name object exists.
7. Clarify rollback.
Dropping the index leaves source/automation_key data intact, but rolling back the columns after deploying the new writer would break the application.
Define rollback per phase:
- writer rollback,
- index rollback,
- backfill data retention,
- column rollback only after all code stops referencing them.
8. Scope GHL handling before deduplication.
The audit must check every row selected for soft deletion, not only whether the overall dataset has some ghl_task_id values.
Any row with ghl_task_id must either:
- follow the canonical GHL deletion path, or
- be explicitly excluded pending a separate cleanup decision.
9. Use the exact partial-index conflict target.
Verify the ORM/SQL generated by createSlaTask matches the index predicate exactly enough for PostgreSQL inference.
Add an integration test against PostgreSQL; a mocked storage test is insufficient.
