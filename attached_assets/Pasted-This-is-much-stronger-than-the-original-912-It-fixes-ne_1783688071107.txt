BUILD-READY WITH CORRECTIONS

The architecture is now correct (provider chain, durable jobs, audit separation), but there are four remaining production issues that should be addressed before handing this to Replit.

⸻

1. Biggest issue: don’t hardcode the BullMQ queue

Right now it says:

use the enrichment queue

That assumes:

* enrichmentQueue is globally accessible
* it’s the correct queue
* inbound confirmations belong there

Those assumptions may not remain true.

Instead require:

Locate the canonical queue used for durable one-off delayed jobs. If the existing enrichment queue already owns delayed operational jobs, reuse it. Otherwise register the new job on the project’s existing delayed-job queue. Do not create a second queue.

That protects architecture.

⸻

2. Don’t hardcode the worker dispatch implementation

This section:

queue-manager.ts:365

Add

else if (job.name === ...)

That’s implementation-specific.

If they refactor to a switch statement or handler map your task becomes wrong.

Instead say:

Register a handler for the inbound-confirmation-followup job using the project’s existing BullMQ dispatch pattern.

Much safer.

⸻

3. The GHL upsert language is slightly dangerous

Currently you say:

best effort GHL upsert

That’s correct…

…but there’s one missing rule.

If GHL is down during the upsert…

SMTP should still send.

But you also don’t want GHL retries blocking SMTP.

I’d explicitly add:

GHL contact creation/update is best-effort only. Failure must be logged but must never prevent SMTP confirmation delivery. Do not retry GHL synchronously before attempting SMTP.

That removes ambiguity.

⸻

4. SubmissionId generation

Right now:

crypto.randomUUID()

That works…

…unless retries happen.

Imagine:

Form submitted

Server crashes

Retry

New UUID

Now BullMQ dedupe fails because the retry generated a different submissionId.

Much better:

If a stable submission identifier already exists for the inbound form submission (request ID, form submission ID, audit ID, etc.), reuse it. Generate a UUID only when no canonical submission identifier exists.

Otherwise retries become separate submissions.
