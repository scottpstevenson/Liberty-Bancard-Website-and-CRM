Addendum to 663 — Final Release QA Safety Corrections

Apply these corrections before building Wave 12.

Do not rewrite the full task. This addendum patches the remaining release-safety gaps.

⸻

1. Form integration tests must not touch live GHL

The current plan says test contacts will not reach real GHL because contactability blocks them and SDR/ORCHESTRATOR flags are off.

That is not sufficient.

Contactability blocks outbound communication. It does not automatically block CRM contact upsert, GHL sync queue jobs, workflow queue creation, or webhook side effects.

Required correction:

* scripts/test-forms.ts must run with a test/dry-run GHL mode, mocked GHL client, disabled GHL queue processing, or explicit test-record bypass.
* Public form tests must not create real GHL contacts, trigger real GHL workflows, or send real customer emails.
* If the repo has no safe GHL test mode, the script must assert that the sync job was queued/recorded without executing the external GHL call.

Kill line:

Stop if test-forms can create or update real contacts in GHL, trigger a real GHL workflow, or send a real external email/SMS/voice event.

Final report must explicitly state:

How live GHL sync was prevented during form integration tests.

⸻

2. Document access-token route must be ownership-guarded, not merely authenticated

The current Step 7 says:

GET /api/merchant-documents/:id/access-token — anon → 401, authenticated → 200

This is too broad.

Correct requirement:

GET /api/merchant-documents/:id/access-token
- anon → 401
- unrelated merchant → 403
- related merchant/owner → 200 only for allowed document scope/status
- agent → 200 only if role policy permits document access
- admin/manager → 200

No route that issues a file/access token should return 200 for every authenticated user.

Kill line:

Stop if any authenticated user can receive an access token for a document they do not own or are not role-authorized to access.

⸻

3. Compliance scanner must classify email separately

The outbound send list includes transactional/internal email senders:

sendGhlEmail
sendGhlEmailForMerchant
sendSmtpEmail
sendEmailReply
unifiedSendEmail

Not every email send should require the same consent/contactability rule as SMS/voice/RVM. For example, admin alerts, password/account emails, merchant transactional emails, and internal notifications may be valid without marketing consent.

Required correction:

The compliance scanner must classify email call sites into:

marketing / automated outreach
sequence email step
transactional merchant/customer email
internal/admin notification
low-level sender wrapper
test-only

Rules:

* marketing/automated outreach email must pass through sequence eligibility/contactability or approved consent logic.
* sequence email steps must be guarded by sequence-worker eligibility/contactability.
* transactional/internal email can be allowlisted only with reason.
* low-level wrappers can be allowlisted by file path.
* unknown email call sites should fail and require classification.

Do not create a scanner that blindly fails all transactional emails or blindly allowlists all email sends.

⸻

4. Static scan should not rely only on ±80 lines

The ±80-line search around call sites is acceptable as a fallback, but it is fragile.

Required improvement:

* detect enclosing function/block where feasible.
* report the exact send call and the nearest gating function found.
* support explicit allowlist entries with reason.
* fail ambiguous business-logic send sites.

Allowed allowlist format should include:

file
function/call site
channel
reason
review date or task id

Do not allow anonymous broad allowlists like “all of server/routes”.

6. Booking webhook test must not weaken webhook security

The booking test may POST to:

/api/webhooks/ghl/appointment-booked

Do not bypass webhook signature/security in production code just to make the test pass.

Acceptable options:

* use existing signed test fixture if webhook signature validation exists.
* call an internal test helper/service directly from the script.
* run with test-mode webhook verification only if already supported.
* assert the booking attribution function rather than opening an insecure public webhook path.

Kill line:

Stop if the test requires weakening webhook authentication/signature validation.

Required:

* do not block code correctness on OS-level package permissions without reporting.

12. Final GO / NO-GO verdict must not be automatic

Even if scripts pass, final report must provide:

GO
GO WITH CONDITIONS
NO-GO

Use:

* GO only if every critical script passes and no P0/P1 remains.
* GO WITH CONDITIONS if only non-blocking environment limitations exist, such as Playwright dependency failure but screenshots captured another way.
* NO-GO if any compliance, contactability, document guard, GHL live-send, queue, or feature flag gate fails.

Additional Kill Lines

Stop and report if:

* form tests can touch real GHL.
* document access-token route returns 200 for unrelated authenticated users.
* webhook tests require weakening webhook security.
* compliance scanner cannot classify transactional/internal email separately from marketing outreach.
* test cleanup cannot remove or isolate records from automation.
* feature flag matrix implies a flag is safe without listing prerequisites.
* queue health exposes raw payloads, secrets, EIN, SSN, bank data, tokens, or webhook bodies.
* go-live checklist has fewer or more than exactly 20 items.
