CROSS-SURFACE CONSISTENCY CHECKS (run all of these)
════════════════════════════════════════════════════════

1. TYPOGRAPHY + COLOR SWEEP (run this first, before any other check)
   Follow the protocol in §11 of .local/intelligence-sheet-design-system.md exactly.
   For every sheet listed above:
   - Is every fontSize a theme.typography token or a hardcoded number?
   - Is every fontWeight from theme.fontWeight or a hardcoded string ("600", "700")?
   - Is every color from theme.colors / cardStyles / semantic tokens, or a hardcoded hex/rgba?
   - Does the background match the canonical sheet surface token in the design spec?
   - Does the card hierarchy follow the 4-tier system in the design spec?
   Flag every deviation with file, line number, hardcoded value, and what it should be.

2. TIER GATE CONSISTENCY
   grep -rn "tierAtLeast\|tier ===\|tier !==\|isPremium\|isElite" artifacts/mobile/
   For every tier check found:
   a) Is it using tierAtLeast() from theme.ts, or a raw string comparison?
      Raw string comparisons are a P1 finding regardless of correctness.
   b) For every paywalled feature: does the server also enforce the same gate in
      entitlements.ts, or is it UI-only? UI-only gates with no server enforcement are P0.
   c) Does the same feature carry consistent gating across every surface it appears on?
      (e.g. a feature gated on "pro" in nutrition but "core" in coach is a P1.)

3. CONTINUITY WIRING (Home ↔ Train ↔ Coach ↔ Nutrition)
   Read continuityEngine.ts and coachContinuity.ts in full.
   For every field written by Train (via coachMemory, lastSessionSummary, or
   appendSessionSnapshot) — trace it forward: does it reach Home's deriveContinuityState()?
   Does it reach the LLM context via coachContextAdapters.ts?
   Any field written but never consumed on another surface is a P0 finding.
   Any field consumed on one surface but not another (where it should apply) is a P1.

4. COACH COPY vs. DATA CONSISTENCY
   For each data point assembled in coachContextAdapters.ts and coach-context.ts
   (readiness score, streak, weakest factor, protein compliance, HRV band, etc.):
   - Is the same value or label shown in the UI on the relevant surface?
   - If the LLM is told "readiness: 72 / Fair" but the UI shows "Good" — that is a P0.
   - If a field exists in the LLM context but has no corresponding UI element — note it
     as "context-only, no UI anchor" (P2, may be intentional).

5. UPGRADE SURFACE CONSISTENCY
   For every upgrade prompt, paywall gate, and LockedFeatureCard in the app:
   - Is shouldShowUpgrade() from upgradeEngine.ts used (not ad-hoc logic)?
   - Is navigateToUpgrade() from upgradeNavigation.ts used for the CTA tap?
   - Does the required tier in the mobile gate match the server gate in entitlements.ts?
   - Is the feature name / copy consistent between the gate and the upgrade screen?
   Deviations from the canonical helpers are P1. Tier mismatches vs. server are P0.

6. SHEET DESIGN SYSTEM CONSISTENCY
   Using the sheet list above and the master spec in intelligence-sheet-design-system.md:
   - Do all sheets share the same background surface token?
   - Do all sheet headers follow the same typography hierarchy?
   - Are stat/metric cards using the same card component or hardcoding their own styles?
   - Are destructive or accent colors consistent across sheets on the same surface?
   Flag any sheet that visually deviates from the master spec.

Severity definitions:
  P0 — broken wiring: field written but never read, server/client tier mismatch,
       continuity payload dropped, LLM context contradicts UI
  P1 — inconsistency that degrades product: raw tier string, hardcoded design token,
       upgrade helper bypassed, gate inconsistent across surfaces
  P2 — polish gap: minor typography deviation, copy that could be tighter,
       non-breaking cosmetic inconsistency

Do not report anything you cannot confirm with a file and line number.
If you cannot tell whether a deviation is intentional, mark it:
  [P2] [Unclear — needs owner review] with the evidence you found.
