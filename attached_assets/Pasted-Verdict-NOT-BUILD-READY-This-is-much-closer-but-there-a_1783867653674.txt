Verdict: NOT BUILD-READY

This is much closer, but there are several real blockers in the proposed schema and write flow. The biggest are:

* the provenance unique index is not actually idempotent when nullable fields are involved;
* GHL inbound is still being pushed toward a GHL-first writer;
* the existing contacts.sourceCategory compliance field would remain disconnected from the new primary-source fields;
* public provenance protection is incomplete;
* the contact/event foreign-key cycle requires an explicit transaction sequence.

Corrections to send back

1. Do not route GHL inbound through createContactGhlFirst().
That function owns GHL-upsert-first behavior. Calling it from syncContactFromGhl risks
echoing an inbound GHL mutation back to GHL.
Phase 973A must introduce an origin-aware canonical writer boundary, for example:
writeContact({
  mode: "ghl_upsert_first" | "ghl_inbound_no_echo" | "local_only",
  mutation,
  provenance,
  actor
})
Existing createContactGhlFirst() may delegate to this service in ghl_upsert_first mode.
syncContactFromGhl must use ghl_inbound_no_echo.
Do not merely add a provenance parameter to createContactGhlFirst() and call it from
the inbound sync.
2. Fix the contact_source_events idempotency key.
This proposed unique index is unsafe:
(contactId, sourceCategory, sourceType, sourceExternalId)
because sourceType and sourceExternalId may be NULL. PostgreSQL normally treats NULLs
as distinct, allowing repeated identical events with NULL sourceExternalId.
Persist a required non-null eventKey/sourceEventKey generated by the intake owner.
Examples:
website form:
  form:<formType>:<submissionId>
GHL inbound:
  ghl:<ghlContactId>:<sourceEventId or payload version>
CSV:
  import:<importExecutionId>:row:<sourceRowNumber or fingerprint>
Manual CRM:
  manual:<audit/contact-create-event-id>
Then enforce:
UNIQUE (contact_id, event_key)
Do not depend on nullable columns for idempotency.
3. Resolve the circular primary-source write transaction explicitly.
contact_source_events.contactId references contacts.id.
contacts.primarySourceEventId references contact_source_events.id.
A new contact therefore must be created in this order, inside one transaction:
A. insert contact with primarySourceEventId = NULL
B. insert source event using the new contactId
C. update contact primarySourceCategory, primarySourceType,
   primarySourceEventId = event.id
D. commit
If B or C fails, the contact and event must roll back together.
Do not create the contact and provenance event through separate uncoordinated calls.
4. Define the relationship between existing sourceCategory and the new fields.
contactability.ts and offer-router.ts actively read contacts.sourceCategory.
If new intake paths only set primarySourceCategory while sourceCategory stays NULL,
the existing compliance/routing behavior remains broken.
Required contract:
- primarySourceCategory = immutable first-known provenance owner
- sourceCategory = protected operational projection used by current compliance/routing
- on first creation, set both from the same server-controlled category
- later source events do not overwrite primarySourceCategory
- any permitted sourceCategory change requires a dedicated audited authority rule
Do not leave sourceCategory null for all newly created records.
Do not change the interpretation inside contactability.ts in this task, but ensure the
field it already reads is populated safely.
5. Protect provenance on every public create and update schema.
Omitting fields only from insertContactSchema is insufficient.
Audit and omit/prohibit:
- sourceCategory
- primarySourceCategory
- primarySourceType
- primarySourceEventId
- importExecutionId
- any source event or eventKey field
from:
- public create schemas
- PUT/PATCH contact schemas
- generic bulk-update schemas
- generic storage update whitelists
A client must not be able to modify provenance after creation.
6. Do not backfill legacy_unknown as permanently immutable provenance.
If all 154K contacts are set to primarySourceCategory = legacy_unknown and the field
can never change, later evidence-backed attribution becomes impossible.
Use this rule:
- legacy_unknown is a provisional system value
- it may be upgraded once by a dedicated audited backfill/correction process when
  reliable evidence exists
- ordinary contact updates and intake events cannot alter it
- later source arrivals append events but do not automatically replace it
Document confidence and inference method for any historical attribution.
7. Add a real FK for sunbiz_entities.importExecutionId.
“Reference by convention” is weaker than the task’s traceability requirement.
Unless a proven migration-order or lifecycle conflict prevents it, use:
sunbiz_entities.import_execution_id
  REFERENCES import_executions(id)
with the intended delete behavior, normally RESTRICT or SET NULL.
Do not rely on an unvalidated UUID convention.
8. Correct the intake-path file ownership before implementation.
The audit identified prospect CSV and COREVT upload ownership in:
server/routes/prospects.ts
The new plan assigns CSV and Sunbiz adoption to:
server/routes/imports.ts
These may be separate import paths.
List every actual importer that must create import_executions and provenance:

- POST /api/sunbiz/upload-corevt

Do not patch only imports.ts while leaving the two audited critical paths unchanged.
9. Do not create contacts one row at a time through GHL-first writes during CSV import.
The plan says the CSV path should call createContactGhlFirst for every inserted row.
That could:
- trigger 10K–100K serial GHL calls;
- create N+1 behavior;
- bypass existing bulk-import ownership;
- make retries difficult;
- produce partial imports.
Bulk contact imports need a batch-safe local canonical writer and separately controlled
GHL synchronization policy.
Preserve the actual import mode and blast-radius boundaries.

The proposed type omits actor fields, but later steps pass:

Use one explicit server-only type:

Validation required

- Forced source-event insertion failure leaves no orphan contact.
- sourceCategory and primarySourceCategory are both server-populated on first creation.
