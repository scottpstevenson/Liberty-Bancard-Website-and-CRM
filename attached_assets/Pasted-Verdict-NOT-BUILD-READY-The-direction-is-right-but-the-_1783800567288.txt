Verdict: NOT BUILD-READY

The direction is right, but the proposed scoring model mixes data completeness, sales qualification, and compliance state. That will make dataReadinessScore unstable and misleading.

The backfill design is also not restart-safe because it uses offset, and fire-and-forget recalculation can silently leave stale scores.

Corrections to send back

Rewrite Phase 2 around a strict data-readiness contract.
1. Remove non-completeness signals from dataReadinessScore.
These do not belong in a completeness score:
- consentTier not cold_no_consent
- lifecycleStage not prospect
- estimatedRevenue / annualRevenue present
Why:
- Consent is a legal/contactability state, not record completeness.
- “Prospect” is a valid lifecycle stage, not missing data.
- Revenue availability is enrichment depth or sales qualification, not basic campaign readiness.
A contact can be structurally complete while lacking consent.
A contact can have score 100 and still fail evaluateContactability().
Keep those dimensions separate.
2. Define the score around campaign-usable record fields only.
Recommended categories:
Identity:
- company name
- contact first or full name
Reachability:
- syntactically valid email
- usable phone
- website
Classification:
- canonical vertical
- city
- state
Optional enrichment depth:
- company size/revenue, only if explicitly labeled as enrichment completeness rather than core readiness.
Do not award points merely because a field is non-null. Validate blank strings, malformed email, placeholder values, and invalid phone values.
3. Rename the breakdown contract.
The proposed shape says:
Record<string, { points, reason }>
but it is unclear whether points means:
- points earned, or
- points lost.
Use an explicit structure such as:
{
  version: 1,
  components: {
    email: {
      maxPoints: 25,
      earnedPoints: 0,
      status: "missing" | "invalid" | "present",
      reasonCode: "missing_email"
    }
  },
  missingReasons: ["missing_email"]
}
Use stable reason codes for aggregation.
Do not aggregate freeform reason strings.
4. Version the scoring model.
Persist:
- dataReadinessScore
- readinessBreakdown
- readinessUpdatedAt
- readinessModelVersion
Without a version, future weight changes cannot identify stale records or trigger a controlled re-score.
5. Do not use OFFSET for a resumable backfill.
Use deterministic keyset pagination:
WHERE id > lastProcessedContactId
ORDER BY id
LIMIT 500
Persist:
- runId
- modelVersion
- status
- totalEligible
- processed
- updated
- skipped
- errors
- lastProcessedContactId
- startedAt
- lastHeartbeatAt
- completedAt
- lastError
OFFSET can skip or repeat rows when contacts are inserted or updated during the run.
6. Add atomic run ownership and fencing.
A system_settings progress blob plus an in-memory worker is not enough.
Prevent two backfills from running simultaneously.
Every progress mutation must verify the active runId.
A stale or replaced worker must stop if it loses ownership.
Define terminal states:
idle | running | complete | failed | interrupted
7. Do not make recalculation fire-and-forget.
This requirement is unsafe:
“fire-and-forget after the main write succeeds”
A process restart or rejected promise would leave readiness stale indefinitely.
Use one canonical recalculation owner:
Preferred:
- enqueue an idempotent readiness-recalculation job after the contact transaction commits.
Acceptable for single-record writes:
- compute synchronously in the same service transaction if sufficiently cheap.
For bulk imports:
- enqueue bounded batches using the existing queue infrastructure.
Do not create a second unmanaged background system.
8. Centralize mutation ownership.
Do not independently patch:
- POST contact route
- PUT contact route
- CSV completion
- GHL sync
Find the canonical contact create/update service and trigger readiness there.
Every caller that changes relevant fields must converge on one owner.
Otherwise one forgotten import or sync path will produce stale readiness.
9. Define which fields trigger recalculation.
Use one exported set of dependencies, for example:
READINESS_DEPENDENT_FIELDS = [
  "email",
  "phone",
  "phoneType",
  "firstName",
  "lastName",
  "companyName",
  "website",
  "vertical",
  "city",
  "state"
]
Do not recalculate on unrelated updates such as notes or assignment changes.
10. Separate threshold exclusion from contactability block reasons.
Audience preview must report distinct categories:
- excludedByReadiness
- blockedByContactability
- alreadyQueued
- queueable
Do not merge readiness failures into the existing contactability blockReasons object.
Readiness is a targeting filter.
Contactability is the compliance authority.
11. Preserve preview/apply parity.
readinessThreshold must be included in:
- persisted campaign targeting state
- preview targeting hash
- queue enforcement validation
- frozen criteria or snapshot used by apply
Changing the threshold after preview must invalidate the preview.
12. Clarify null-score behavior.
Campaign threshold filtering must define whether contacts with:
dataReadinessScore IS NULL
are:
- excluded, or
- scored on demand.
Recommended:
exclude them and report them as “not yet scored.”
Never treat NULL as zero silently.
13. Do not derive histograms from JSONB unless necessary.
The distribution should aggregate the integer dataReadinessScore column.
Top missing fields may aggregate stable reason codes from readinessBreakdown JSONB, but assess query cost and indexing before polling this endpoint.
Do not load all 154K breakdown blobs into Node memory.
14. Keep dashboard work out of the critical path if needed.
The release-critical outcome is:
- correct score model
- versioned persistence
- safe backfill
- reliable recalculation
- campaign threshold parity
The full dashboard and charts can be a second UI task if bundling them delays or complicates correctness.

Validation required

Scoring:
- Empty contact scores within 0–100 with deterministic missing codes.
- Fully complete contact scores 100.
- Invalid email does not earn email points.
- Blank company/vertical fields do not earn points.
- Consent, DNC, lifecycle stage, and leadScore do not affect readiness.
- Same input + model version always yields the same score.
Backfill:
- Two simultaneous starts create one active run.
- Forced crash resumes from lastProcessedContactId.
- Old runId cannot overwrite a replacement run.
- Batch failure does not advance the cursor.
- Re-running the same model is idempotent.
- Score and breakdown update together.
Recalculation:
- Relevant contact update recalculates readiness.
- Unrelated update does not.
- CSV and GHL mutations use the same canonical owner.
- Queue failure is observable and retryable.
- No stale readiness after a simulated process restart.
Campaign:
- NULL score is explicitly excluded and counted.
- Below-threshold contacts never reach evaluateContactability().
- Above-threshold contacts still must pass evaluateContactability().
- Threshold change invalidates the prior preview.
- Preview and queue use identical threshold criteria.
- leadScore remains byte-for-byte unchanged.
Aggregation:
- Histogram bucket totals reconcile to scored contacts.
- Missing-reason totals use stable reason codes.
- Statistics query remains database-bounded.
