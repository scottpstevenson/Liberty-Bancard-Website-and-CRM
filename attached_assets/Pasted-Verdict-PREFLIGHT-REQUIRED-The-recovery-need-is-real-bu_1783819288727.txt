Verdict: PREFLIGHT REQUIRED

The recovery need is real, but the proposed implementation may route enrollment work through the wrong queue and can create duplicate or runaway retries.

The task must first prove which queue canonically owns promotional_enrollment_eval. “ENRICHMENT queue” is not automatically correct just because it already has a processor.

Corrections to send back

Run a focused deferred-enrollment recovery preflight before implementation.
1. Confirm canonical queue ownership.
Provide file:line evidence for:
- where enqueuePromotionalEnrollment() normally enqueues successful jobs;
- the queue name;
- the registered worker/dispatcher;
- the exact job type;
- retry and backoff settings;
- terminal failure handling.
Deferred jobs must be re-enqueued into the same canonical promotional-enrollment
execution path.
Do not route enrollment jobs through ENRICHMENT unless that queue already owns and
dispatches promotional_enrollment_eval.
2. Define the database row as the recovery authority.
Document the current promotional_enrollment_jobs fields and status transitions.
Required durable states should distinguish:
- pending_enqueue
- queued
- processing
- enrolled
- blocked
- already_enrolled
- deferred_queue_unavailable
- retry_wait
- failed_terminal
Do not treat BullMQ job presence as the only source of truth.
3. Use atomic claim-and-recover semantics.
The recovery worker must not:
SELECT deferred rows
then enqueue
then UPDATE
without ownership protection.
Use an atomic claim such as:
UPDATE promotional_enrollment_jobs
SET status = 'pending_enqueue',
    recovery_owner = $runId,
    recovery_claimed_at = NOW()
WHERE id IN (
  SELECT id
  FROM promotional_enrollment_jobs
  WHERE status IN ('deferred_queue_unavailable', 'retry_wait')
    AND next_attempt_at <= NOW()
    AND attempts < max_attempts
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED
  LIMIT $batchSize
)
RETURNING *
This prevents overlapping workers from recovering the same row.
4. Do not increment attempts merely for polling.
Define attempts precisely.
Recommended:
- increment enqueueAttempts when a BullMQ enqueue attempt fails;
- worker execution attempts remain tracked separately by BullMQ or execution fields.
A successful re-enqueue should not consume all retry allowance before the enrollment
worker even runs.
5. Use bounded exponential backoff.
Persist nextAttemptAt and lastErrorCode.
Do not retry every deferred row continuously after Redis remains unavailable.
Required:
- bounded batch size;
- exponential or capped backoff;
- maximum attempts;
- terminal failed state;
- sanitized error messages.
6. Preserve the original idempotency identity.
Recovery must reuse the existing source-event/job identity.
Do not create a new logical enrollment event every time recovery runs.
The BullMQ jobId should remain derived from the persisted enrollment job/event ID,
so repeated recovery attempts cannot enqueue duplicate logical work.
7. Reconcile enqueue ambiguity.
Redis enqueue can succeed while the subsequent DB status update fails.
On the next recovery pass, the system must safely retry without creating duplicate
enrollment.
Use:
- stable BullMQ jobId;
- idempotent enrollment records;
- status reconciliation when BullMQ reports the job already exists.
“Job already exists” should usually transition the DB row to queued, not failed.
8. Recovery must not bypass eligibility.
The recovered worker must run the same authoritative
evaluatePromotionalEnrollmentEligibility() flow as a normal job.
Do not assume the contact is still eligible because it was eligible—or merely created—
during the outage.
Current DNC, opt-out, contactability, and sequence-enrollment state must be re-read.
9. Prefer a recurring recovery worker over startup-only recovery.
A startup hook alone does not help when Redis recovers without an application restart.
Use a bounded scheduled recovery tick, protected against overlap.
A startup invocation may run the same recovery function once for faster healing, but
must not be a separate implementation.
10. Define recovery observability.
Record per recovery run:
- claimed
- successfully re-enqueued
- already present in queue
- still unavailable
- terminally failed
- skipped because attempts exhausted
Use one aggregate audit event per run, not one noisy audit event per row.
Operator UI can be a follow-up; an auditable metric/status endpoint is sufficient for
this task.

Kill lines

STOP if promotional enrollment is placed on ENRICHMENT without proving that queue owns
the job type.
STOP if two recovery workers can claim the same deferred row.
STOP if recovery creates a new idempotency key or source event.
STOP if a successful Redis enqueue followed by a failed DB update can duplicate
enrollment.
STOP if polling itself consumes retry attempts.
STOP if retries have no nextAttemptAt/backoff or terminal failure state.
STOP if recovery trusts old eligibility instead of rechecking current contactability.
STOP if recovery runs only at startup.
STOP if Redis unavailability causes an in-memory enrollment fallback.

Validation

- Redis unavailable → enqueue writes one deferred DB row and no in-memory work runs.
- Redis recovers without app restart → scheduled recovery re-enqueues the row.
- Two simultaneous recovery ticks claim the row once.
- Repeated recovery uses the same BullMQ jobId.
- BullMQ “job already exists” reconciles the DB row to queued.
- Eligibility changed to DNC during outage → recovered job becomes blocked, not enrolled.
- Already-enrolled contact → recovery produces already_enrolled without duplication.
- Enqueue failure increments the correct counter and sets nextAttemptAt.
- Attempts exhausted → row becomes failed_terminal and stops retrying.
- Aggregate recovery audit contains exact reconciled counts.

Final status: PREFLIGHT REQUIRED

The task should become atomic deferred-job recovery through the existing promotional-enrollment queue, with stable job identity, backoff, overlap protection, eligibility recheck, and reconciliation for ambiguous enqueue outcomes.
