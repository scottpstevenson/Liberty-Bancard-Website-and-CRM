Addendum to Task 690 — Required Corrections Before Build

The task is approved directionally, but apply these corrections before implementation.

1. Suppression guard must check both merchant flag and SDR lead state

Do not rely only on sdr_merchants.doNotContactFlag.

The discovery insert guard must skip resurfacing a merchant if an existing exact/fuzzy match has any of:

* sdr_merchants.doNotContactFlag = true
* related sdr_lead_state.stage IN ('SUPPRESSED', 'DISCARDED')
* related sdr_lead_state.statusReason / event payload indicating human_suppressed or internal not-a-fit

Reason: Task #686 may record suppression through SDR lead state/audit trail, not only doNotContactFlag.

Kill line:

STOP if a merchant suppressed in the A-Lead Queue can reappear as an active discovered lead on a later discovery run.

2. businessId must be reliably resolved or created, not “best effort only”

The plan currently says to set businessId only if a matching businesses row can be found, otherwise leave null.

That is not enough.

If processorSignals is keyed by businessId, then SDR enrichment must guarantee a usable businessId before storing processor signals.

Required:

* look up existing canonical business by normalized domain / website / company + city where possible
* if no canonical business exists, use the existing canonical business creation/upsert pattern if one exists
* set sdr_merchants.businessId reliably
* if no safe canonical creation path exists, STOP and report that businessId linking must be split into a prerequisite subtask

Kill line:

STOP if processor detection runs but cannot store/query results because `sdr_merchants.businessId` remains null for most discovered merchants.

3. Verify detectProcessors() signature before calling it

Do not blindly call:

detectProcessors(merchant.id)

unless the function explicitly expects an SDR merchant ID.

Before implementation, inspect the detector signature and call it with the correct identifier:

* businessId, if it expects canonical business ID
* domain / website, if it expects a URL/domain
* contactId, only if it is CRM-contact-specific and needs an SDR wrapper
* sdrMerchantId only if the function supports SDR merchants directly

The call must be awaited and errors must be logged without killing the whole enrichment job.

Kill line:

STOP if `detectProcessors()` is called with an SDR merchant ID when the detector expects a canonical business ID, contact ID, domain, or URL.

4. Phone dedup must normalize both sides

Adding getContactByPhone(phone) is correct, but do not compare only exact formatted phone strings.

Normalize both the incoming phone and stored contact phone.

Required behavior:

* strip non-digits
* compare last 10 digits where possible
* return null, not throw, when there is no match
* support common stored formats like (954) 123-4567, 954-123-4567, +1 954 123 4567

Kill line:

STOP if phone dedup only works when stored and incoming phone strings have identical formatting.

5. Processor fingerprint tests should be pure, not dependent on live websites

The new smoke test should not require live external website fetches to pass.

Preferred:

* add a pure detector test with canned HTML/script/meta input
* or inject/mock the fetcher only inside the test path
* do not add production behavior that changes detector execution based on a broad TEST_MODE unless the existing test architecture already uses that pattern safely

Kill line:

STOP if the smoke test depends on live merchant websites being reachable from Replit.

6. Processor conversion analytics are not part of this task

Do not add getConversionByProcessor() dashboard surfacing here.

That belongs in the next activation/source-performance task after real leads flow through the queue.

This task is only:

* suppression rediscovery guard
* phone dedup
* reliable businessId linking
* processor detector wiring into SDR enrichment
* missing processor fingerprints
* targeted validation
