## Audit verdict

**BUILD-READY WITH BLOCKING CORRECTIONS. Do not execute Task #1730 unchanged.**

The overall CRO-03B architecture is correct, and it can remain one task. However, several factual errors, contradictory boundaries, and missing ownership rules could produce duplicate validation spend, unintended GHL work, or an incomplete “vertical slice” being called complete.

The audited baseline is correct:

* `main` / `origin/main`: `dfa10220c4736027fefa0a47981a48350e853b22`
* Migration head: `0187_cro03a_candidate_qualification`
* Migration integrity: 430 checks passed, with two historical warnings
* CI manifest: 93 registered suites
* Provider transport remains disabled

## Blocking corrections to the implementation contract

### 1. Resolve the CRO-03A scope contradiction

Section 5 requires CRO-03A scoring, provenance, cancellation, and recovery repairs, while Section 9 says rewriting CRO-03A fit is out of scope.

Replace that exclusion with:

> Historical CRO-03A migrations and immutable decisions are out of scope for mutation. Additive CRO-03A contract corrections required for a trustworthy CRO-03B feed are explicitly in scope and must be completed as Phase 0.

Do not modify migration `0187`. Introduce policy/algorithm version 2 additively.

### 2. Make the scoring algorithm part of the immutable policy

Changing constants while retaining `fitVersion: "v1"` would make historical decisions unreproducible.

Require:

* Immutable weight document containing `20/25/15/15/10/10/5`
* New fit algorithm version
* Policy hash covering weights, thresholds, vertical normalization, freshness rules, and component definitions
* Run and decision rows storing policy ID/version/hash and algorithm version
* Explicit identity component definition

Also correct current active-state behavior: missing entity status must not default to active, and a geography value such as `state="FL"` must never be interpreted as entity status. See [fit.ts](sandbox:/tmp/liberty-cro03b-audit.bVqohB/server/services/cro03a/fit.ts).

### 3. Correct freshness and timestamp provenance

The current immutable occurrence row can serve as the separate freshness/attestation record; a duplicate observation payload does not necessarily require another observation row.

The real defect is that census staging manufactures a new current timestamp and event key every time a source lacks a timestamp, making unchanged evidence appear newly fresh.

Require:

* Vocabulary: `source`, `import`, `ingestion_only`
* Separate `sourceObservedAt`, `importObservedAt`, and `ingestedAt`
* Stable source/import event identities
* A new occurrence only for a verified source event, import event, or explicit audited manual attestation
* No automatic freshness renewal merely because the census command ran again
* Database checks for the provenance vocabulary

### 4. Make source census deterministic

Current `.limit(limit)` reads have no stable ordering, cursor, or high-water mark.

Require:

* Stable source-specific ordering
* Durable cursor/high-water mark
* Replay-safe pagination
* No repeated arbitrary “first N” rows
* Census response reports the actual active policy version/hash, not hardcoded `policyVersion: 1`

### 5. Add real queue-owned recovery

Register CRO-03A qualification claim/recovery with the existing enrichment QueueManager tick.

Require:

* Global claim of queued or expired CRO-03A items
* Lease/fence recovery after restart
* Run reconciliation from the queue worker
* Removal of processing side effects from `GET /api/cro03a/runs/:id`
* No detached request promise as the only execution owner

The existing queue already owns CRO-03 item and mutation processing in [queue-manager.ts](sandbox:/tmp/liberty-cro03b-audit.bVqohB/server/services/queue-manager.ts).

### 6. Fix cancellation semantics

Cancellation must:

* Set `cancel_requested_at`
* Cancel only unclaimed/queued items
* Allow already claimed work to finish under its existing fence
* Reconcile the run only after claimed work becomes terminal
* Never clear an active worker’s claim token underneath it

### 7. Make handoff consumption atomic

The current append-only receipt alone is not a sufficient claim. Two workers could begin recipe work before either appends the terminal receipt.

Require one transaction that:

1. Locks the handoff.
2. Derives the consumer key server-side.
3. Creates or replays a unique recipe command for `(handoff_id, recipe_version)`.
4. Freezes handoff and recipe hashes.
5. Appends the admission receipt linked by a real FK to the recipe command.
6. Returns the original command on exact replay.
7. Rejects changed recipe/payload reuse.

Do not accept a caller-selected consumer key as authority. Distinguish an admission/acceptance receipt from a terminal recipe-completion receipt.

### 8. Define an exact provider/evidence ownership matrix

The prompt currently says all stages share operation, attempt, cost, and receipt lineage but does not define which authority owns billing.

Use this contract:

| Stage                         | Execution/accounting owner                                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Sunbiz/frozen source evidence | CRO-03B zero-cost internal evidence                                                                                 |
| First-party web/RDAP          | CRO-03B zero-cost external operation through SafeEgress                                                             |
| JSON-LD                       | Parser child evidence of the authorized page operation                                                              |
| Serper                        | SerperGateway owns budget/circuit/transport accounting; CRO-03B references its operation and must not reserve twice |
| Outscraper/Apollo             | CRO-03 provider context, reservation, attempt, receipt, and ledger                                                  |
| OpenAI enrichment             | Existing AI audit/token authority extended for CRO-03B; CRO-03B references that operation                           |
| ZeroBounce                    | Validation-intent worker owns the eventual operation and spend; CRO-03B creates only the intent/link                |

Extend the provider manifest and approved callers accordingly. Current CRO-03 providers cover only ZeroBounce, Serper, Outscraper, and Apollo in [contracts.ts](sandbox:/tmp/liberty-cro03b-audit.bVqohB/server/services/cro03/contracts.ts), while AI is approved only for Sunbiz classification in [provider-manifest.ts](sandbox:/tmp/liberty-cro03b-audit.bVqohB/server/services/provider-manifest.ts).

### 9. Specify the recipe instead of saying “execute conditionally”

Freeze an explicit recipe version containing, for every step:

* Required input fields
* Fields it may produce
* Authority/cost class
* Eligibility predicate
* Maximum attempts
* Evidence TTL
* Stop conditions
* Conflict outcome
* Next-step transitions

Recommended crawl boundary:

* Homepage plus same-site contact/about/team/location pages
* Maximum five pages
* Three redirects
* 512 KiB per page
* Same registrable domain
* HTML/JSON/text only
* Robots enforcement
* Durable per-domain rate limiting
* No PDFs, images, social pages, or arbitrary link traversal

RDAP must be domain corroboration only. It must not provide a default owner or marketing email.

### 10. Complete SafeEgress before calling crawling governed

Current SafeEgress validates DNS/IP, redirects, size, and content type, but does not implement robots, durable per-domain limits, or DNS-resolution pinning against rebinding.

Those must be explicit requirements and certified with injected transports. See [safe-egress.ts](sandbox:/tmp/liberty-cro03b-audit.bVqohB/server/services/cro03/safe-egress.ts).

### 11. Define exact matching and arbitration policy

Require immutable policy versions for:

* Field-specific source authority
* Candidate freshness and expiry
* Confidence thresholds
* Minimum winning margin
* Manual/protected precedence
* Stable sorted candidate-set hash
* High-authority conflict behavior
* Winner, no-winner, and review outcomes

For Outscraper, exact business name alone must not be a sufficient anchor. Require a strong anchor such as verified domain, place ID, phone, or address/location agreement plus threshold and margin.

For Apollo, replace “first person returned” with a versioned title policy, organization binding, person alternatives, and ambiguity review.

### 12. Correct canonical projection and GHL behavior

This is the most consequential omission.

The current contact mutation path calls `updateContactLocalFirst()`, which creates a pending GHL projection. That contradicts the task’s no-GHL boundary. Contact creation also strips `businessId`, and the contact/business authority currently requires an admin-reviewed verified link.

Require:

* A canonical `local_only` compare-and-set update mode that does not create GHL projection work
* CRO-03B-specific valid source/provenance contract
* Business identity resolution before contact creation
* Compare-and-set descriptive business updates
* An explicit CRO-03 system contact/business-link decision path for strong, non-ambiguous immutable evidence—or review without projection
* No direct `contacts.business_id` update
* Projection receipts tied to exact organization/contact writer results
* Crash recovery through stable source-event keys

Relevant owners are [contact-writer.ts](sandbox:/tmp/liberty-cro03b-audit.bVqohB/server/services/contact-writer.ts), [organization-resolver.ts](sandbox:/tmp/liberty-cro03b-audit.bVqohB/server/services/organization-resolver.ts), and [commercial-link-authority.ts](sandbox:/tmp/liberty-cro03b-audit.bVqohB/server/services/commercial-link-authority.ts).

### 13. Prevent duplicate ZeroBounce intents

The canonical contact writer automatically creates a `marketing_outreach` validation intent when an email is created or changed. CRO-03 then creates a separate `cro03_winning_email` intent.

Require an internal writer option that defers default validation for CRO-03 projection. After the winning email write succeeds:

1. Persist the projection receipt.
2. Create exactly one `cro03_winning_email` intent for its token hash and generation.
3. Reuse it on replay.
4. Prove no parallel default intent can cause duplicate ZeroBounce spend.

### 14. Fence every relevant legacy writer narrowly

For subjects with an admitted active CRO-03B recipe:

* JSON-LD, RDAP, contact-page, Serper, generic enrichment, Sunbiz enrichment, and free-enrichment workers must submit evidence into CRO-03B or skip with a durable reason.
* They must not write competing source/contact/business fields.
* Unrelated workflows may continue unchanged.

The current JSON-LD and RDAP paths directly insert SDR contact rows, so merely scanning Serper is insufficient.

### 15. Tighten authorization

Specify:

* Exact run cap—recommended maximum 250 handoffs per command
* Manager ownership derived from the original CRO-03A run, never request input
* Admin-only recipe/policy activation
* Admin-only protected-field override
* Conflict review admin-only unless a named existing authority explicitly permits manager review
* Consistent 404 behavior for cross-manager access
* No API acceptance of ranks, confidence, worker context, recipe hash, or operation IDs

## Certification corrections

Add explicit proofs for:

* Clean bootstrap, real `0187 → 0188+` upgrade, and migration replay
* Durable CRO-03A recovery without HTTP
* Cancellation with claimed work
* Cross-run handoff concurrency—expected to pass without code changes
* Atomic handoff admission and recipe replay
* Deterministic census pagination
* No `contact_provider_projections` created by CRO-03B
* No duplicate default/CRO-03 validation intents
* Exact fake-operation/attempt/receipt/ledger reconciliation
* Zero real transport/network calls
* Zero deal, campaign, enrollment, GHL, outbound-message, CR-04, CR-06, or pause mutations
* Legacy writer exclusion for active handoffs
* Full source → business → contact → projection receipt → winning-email intent recovery after every crash boundary

## Final corrected disposition

Keep Task #1730 as one build, but divide its execution into mandatory internal phases:

1. CRO-03A feed repair
2. Atomic handoff admission
3. Recipe/evidence lifecycle
4. Matching and arbitration
5. No-GHL canonical projection
6. Final-email intent
7. Legacy fences, UI, and certification

The executor must not stop after a “smallest complete vertical slice.” All seven phases are required before marking CRO-03B complete.

CRO-03B completion will mean **code-complete and provider-denied**, ready for CRO-03C. It will not mean Serper, Outscraper, Apollo, OpenAI, public crawling, or ZeroBounce are live in production yet.
