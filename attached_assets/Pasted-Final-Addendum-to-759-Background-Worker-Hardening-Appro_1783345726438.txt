Final Addendum to #759 — Background Worker Hardening

Approved to build.

This is a worker reliability and duplicate-run prevention task. Do not change the business logic of sequence processing, enrichment, or GHL sync.

⸻

Part A — Add error isolation to recurring worker ticks

Required behavior

The following calls must be isolated so one thrown error does not abort the rest of the tick:

processSequenceEnrollments
processEnrichmentQueue

They should follow the same try/catch or .catch() pattern already used by sibling sub-tasks in the same tick.

Required outcome

If one worker step throws:

error is logged with job/tick context
next sibling work still has a chance to run if applicable
health/system-setting bookkeeping still executes
tick does not silently die

Use finally where needed for health bookkeeping.

Kill lines

STOP if a thrown sequence-enrollment error can still skip post-tick health bookkeeping.
STOP if a thrown enrichment-queue error can still skip post-tick health bookkeeping.
STOP if errors are swallowed without structured logging.
STOP if this task changes sequence enrollment business rules.
STOP if this task changes enrichment matching/scoring logic.

⸻

Part B — Prevent duplicate GHL sync loops

Required behavior

Only one GHL sync mechanism may be active at a time:

BullMQ ghl-sync queue
or
legacy setInterval fallback

Never both.

Required preflight

Before deleting anything, verify:

Where BullMQ ghl-sync is initialized
Where legacy setInterval sync is initialized
Whether both can run in the same process
Whether production/staging always has BullMQ enabled
Whether legacy interval exists only as fallback or is still active by default

Preferred fix

If BullMQ is the current intended mechanism, gate the legacy interval behind an explicit fallback condition, for example:

only start legacy interval when BullMQ/queue manager is disabled or unavailable

or remove it only if confirmed safe.

Required logging

On startup, log exactly which GHL sync mechanism is active:

GHL sync mode: bullmq

or:

GHL sync mode: legacy_interval_fallback

If neither is active intentionally, log that too.

Kill lines

STOP if BullMQ and legacy setInterval GHL sync can both run in the same process.
STOP if GHL sync is fully disabled in an environment that previously relied on the legacy fallback.
STOP if this task changes GHL mapping, payload shape, contact sync logic, or custom field mapping.
STOP if this task triggers a live GHL sync during validation without explicit approval.
STOP if duplicate prevention relies only on comments instead of runtime gating.

⸻

Out of scope

Do not:

change BullMQ retry/backoff policy
add new background job types
change sequence enrollment eligibility rules
change enrichment provider logic
change GHL payload mapping
change GHL custom fields
run live syncs as part of validation

⸻

Validation

Run:

npx tsc --noEmit --skipLibCheck
npx tsx scripts/smoke-role-guards.ts

If worker tests exist, run the targeted worker/queue tests too.

Manual/inspection checks:

1. Inject or simulate processSequenceEnrollments throwing.
2. Confirm the error is logged and post-tick bookkeeping still runs.
3. Inject or simulate processEnrichmentQueue throwing.
4. Confirm the error is logged and post-tick bookkeeping still runs.
5. Start the server and confirm exactly one GHL sync mode is active.
6. Confirm BullMQ and legacy interval cannot both run.
7. Confirm no live GHL sync is triggered during validation unless explicitly approved.
