Part A — Chargebacks real PDF generation

Required behavior

The Chargebacks “Download PDF” action must generate an actual downloadable PDF file, not call window.print().

The generated PDF should include the chargeback evidence packet content already shown in the UI, such as:

merchant/deal/contact info
chargeback details
timeline/evidence summary
supporting notes
uploaded evidence/document references if available
generated timestamp

Implementation guard

Before adding a new dependency, check whether the app already has an existing PDF-generation pattern or library.

Preferred order:

1. Reuse existing server-side PDF utility if present.
2. Add a small server-side PDF generation helper specific to chargebacks.
3. Avoid broad/general PDF infrastructure unless already needed elsewhere.

The server route should return a real PDF response with appropriate headers:

Content-Type: application/pdf
Content-Disposition: attachment; filename="chargeback-evidence-<id>.pdf"

Security guard

The PDF route must preserve existing dashboard auth/role/ownership checks.

Do not expose raw document paths or unauthenticated evidence files.

Kill lines:

STOP if Download PDF still uses window.print().
STOP if the PDF route is unauthenticated.
STOP if the PDF exposes raw server file paths or private storage keys.
STOP if this task builds a broad PDF generation platform instead of the chargeback evidence PDF.
STOP if existing chargeback evidence data is removed or simplified just to make PDF generation easier.

⸻

Part B — Boarding Refresh All reliability

Required behavior

“Refresh All Statuses” must handle large in-flight queues reliably.

Do not use an unbounded client-side request storm.

Use one of these safe patterns:

server-side bulk refresh endpoint with per-deal results

or:

client-side limited concurrency, e.g. 3-5 requests at a time

Preferred: server-side bulk endpoint if the backend already owns the boarding status provider logic.

Result reporting

The action should return/report:

attempted
succeeded
failed
skipped
per-deal failure reason where available

The UI should not show full success if only some deals refreshed.

Allowed states:

success
partial_success
failed
no_op_with_reason

Not allowed:

spinner disappears with no clear result
one failed deal aborts the entire refresh
unbounded parallel API calls

Provider/rate-limit guard

If the boarding status API has rate limits or provider constraints, respect them with batching, backoff, or limited concurrency.

Do not change provider credentials or status semantics.

Kill lines:

STOP if Refresh All fires unbounded parallel requests.
STOP if one failed boarding status blocks all other deals from being attempted.
STOP if the UI reports success when some deals failed.
STOP if this task changes boarding status mapping/business rules.
STOP if this task changes API keys, provider credentials, or environment flags.
